Cycle 1 (`ba-spec-20260507-142952.md`) landed `pretool-cp-state-write-guard.py`, `tool-policy.v1.json` deny lists, and a component-aware structural matcher (`_is_cp_state_components`). The /close report's verbatim prescription:

> Extend `lib.bash_write_targets.extract_bash_write_paths` (or the guard hook itself) to track `cd` context so `cd <spec-dir> && cat > cp-state-foo.json` resolves to the post-cd absolute path; AND synthesize `dest_dir/basename(src)` when `cp`/`mv`/`install` target is a directory.

The current extractor at `/root/.claude/hooks/lib/bash_write_targets.py` is regex-based; it returns paths verbatim from `> FILE`, `>> FILE`, `tee`, `cp/mv DEST`, `sed -i FILE`, and `install DEST`. The 4 known failure modes:

- **F1 cd_relative**: `cd /dev/shm/.../specs/spec-X && cat > cp-state-ba.json << EOF\n{}\nEOF` — extractor returns `cp-state-ba.json` (relative). The guard's `os.path.abspath()` resolves against the hook's own cwd, not the shell's post-cd cwd. The structural check `parts[-3]=='specs'` then misses because the path has only one component.
- **F2 cp_to_dir**: `cp /tmp/cp-state-ba.json /dev/shm/.../specs/spec-X/` — extractor returns the destination directory (last positional). When dest is a directory, `cp` writes `dest/basename(src)`, but the extractor never synthesizes that path.
- **F3 mv_to_dir**: same as F2 with `mv`.
- **F4 install_to_dir**: same as F2 with `install -m 644 src dest_dir/`.

Codex (this cycle, fresh consultation `gpt-5.5 xhigh`, transcript `/var/tmp/codex-outputs/codex-output-4058520-1778181538.txt`) confirmed:
1. **Architecture verdict — Option B** (guard-local augmentation in `pretool-cp-state-write-guard.py`) has the smallest blast radius; keeps the shared `extract_bash_write_paths` extractor stable for its other consumers (`pretool-tool-policy.py`, `pretool-overnight-hook-guard.py`).
2. **Additional HIGH-RISK forms** that a buggy-but-cooperative subagent would naturally produce AND currently bypass:
   - `python3 -c "open('/spec-dir/cp-state-X.json','w').write(...)"` and `python3 - <<PY ... open/write_text PY` heredoc
   - `&> /spec-dir/cp-state-X.json` (combined-stream redirect) — current `_REDIRECT_OP_RE` matches `>>?` not `&>`
   - `dd of=/spec-dir/cp-state-X.json`
   - `curl -o /spec-dir/cp-state-X.json ...` and `wget -O /spec-dir/cp-state-X.json ...`
   - `git restore /spec-dir/cp-state-X.json`, `git checkout -- /spec-dir/cp-state-X.json`
   - `touch /spec-dir/cp-state-X.json` (not a write of bytes, but creates / `mtime`-bumps an empty cp-state, breaking spec-check's read+write contract)
   - `rsync /tmp/cp-state-ba.json /spec-dir/specs/spec-X/` (same dest-dir-synthesis problem as cp/mv)
   - `ln -sf /tmp/poison.json /spec-dir/cp-state-X.json` — **codex flagged HIGH-RISK**: `spec-check.py` uses regular `path.read_text()` / `path.write_text()` (no `O_NOFOLLOW`, no `lstat`). A symlink replaces the file; subsequent `spec-check.py` calls follow the symlink, reading/writing the attacker-controlled target.
3. **Extractor cd-tracking robustness**: linear `cd X && ...` and `cd X; ...` with multiple sequential `cd` is sufficient. Subshell `(cd X; ...)` and `cd $VAR` are NOT in the threat model (subagent is cooperative-but-buggy, not adversarial).

## Edge Cases & Risks

- **Risk 1 — false positive on `cd /tmp && cat > out.json`**: the cd-context tracker MUST only escalate to the guard when the post-cd cwd, joined with the relative target, satisfies the structural cp-state shape (`parts[-3]=='specs'` + basename `cp-state-*.json`). A redirect to `/tmp/out.json` after `cd /tmp` resolves to `/tmp/out.json` which has only 2 parts — not cp-state-shaped. Mitigated by structural check in `_is_cp_state_path` (unchanged from Cycle 1).
- **Risk 2 — false positive on `python3 -c "x=1"`**: the python-c scanner ONLY raises when the inline code substring contains `cp-state-` literal AND a `.json` literal AND an `open(`/`Path(...).write_text` opener. Pure non-cp-state python invocations are unaffected.
- **Risk 3 — heredoc body of `python3 - <<PY ... PY`**: the cycle-1 extractor strips heredoc payload bodies before extraction. The guard's python-c scanner must work on the ORIGINAL command text (NOT the heredoc-stripped form) for the heredoc-body case. Mitigated by independent regex on the unstripped command in the guard hook.
- **Risk 4 — `os.path.isdir(dest)` race condition**: between the guard call and the subagent's actual `cp` execution, the dest could change. The guard uses BOTH heuristics (`dest.endswith('/')` OR `os.path.isdir(dest)`) AND the basename-pattern heuristic (synthesize when `os.path.basename(src).startswith('cp-state-')`); if any of these fires, the synthesis happens and the structural check decides. Conservative: when in doubt, synthesize and let the structural check filter.
- **Risk 5 — overly aggressive `touch` block**: `touch /tmp/foo` MUST NOT be blocked. Only `touch <path>` whose path matches the cp-state structural shape is denied. The guard already has the shape check; the `touch` extractor just needs to add the path token to the candidate list.
- **Risk 6 — the cd-context tracker missing a known-safe form**: forms like `cd /tmp; mkdir x; cat > x/y.json` should NOT be blocked because `/tmp/x/y.json` is not cp-state-shaped. The structural check is the truth-source; the cd tracker just provides the right candidate path.
