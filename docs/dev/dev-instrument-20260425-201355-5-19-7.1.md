## Static analysis (already done — read-only)

### File 1: `packages/happy-cli/src/claude/session.ts:69-93`


- `keepAliveInterval` is a `NodeJS.Timeout` member.
- `clearInterval(this.keepAliveInterval)` ONLY in `cleanup()` (line 80).
- `cleanup()` is fired by upstream code when the Session object is being torn down (typically end of `runClaude` lifecycle).
- `onThinkingChange(thinking)` (line 85-88) sets `this.thinking = thinking` and fires one immediate `keepAlive` emit. Then the 2s timer continues using the new `this.thinking`.

**Static conclusion**: timer cadence is session-scoped (continuous while Session lives). H_F's "turn-scoped timer" framing is INCORRECT. What IS turn-scoped is the *value* of `this.thinking`.

### File 2: `packages/happy-cli/src/api/apiSession.ts:151-155`


### File 3: `packages/happy-cli/src/api/apiSession.ts:523-533`

```typescript

    if (process.env.DEBUG) { logger.debug(`[API] Sending keep alive message: ${thinking}`); }

        sid: this.sessionId,
        time: Date.now(),

```

- `socket.volatile.emit` — **silently dropped** if disconnected. This is a candidate explanation for "frozen lastUpdated 23:16:47": if the CLI's socket disconnected but reconnect attempts haven't yet succeeded, every 2s keepAlive is silently dropped. Server's `lastActiveAt` stops updating. App sees frozen timestamp.

### File 4: `packages/happy-cli/src/claude/claudeRemote.ts:135-144` + 162, 175, 192, 238

```typescript

const updateThinking = (newThinking: boolean) => {
    if (thinking !== newThinking) {

        logger.debug(`[claudeRemote] Thinking state changed to: ${thinking}`);

    }

// ...

    updateThinking(true);  // line 175

    updateThinking(false);  // line 192 — turn end
```

**Critical observation**: `updateThinking(true)` is called at:
- `query()` invocation (line 162)
- SDK system init (line 175)

It is NEVER called between turns inside `nextMessage()`. So when bg-task wakes claude, the SDK stream resumes... but does it actually resume? The `result` message sets thinking=false at line 192, then `await opts.nextMessage()` at 208 BLOCKS the for-await iterator. If `result` actually means "turn end and SDK terminates", then bg-task wake would require a NEW `query()` call — which this code doesn't do. If `result` means "current segment end and SDK continues streaming", then thinking would never re-flip to true even though claude is producing text.

**This is the H_F variant that actually matches user evidence**: bg-task wake produces text (via JSONL log scanner) that gets sent to server as `new-message` — but `thinking` stays false because `updateThinking(true)` is not re-fired on the resumed SDK stream. The 2s keepAlive ticks keep firing with `thinking=false`, so app never sees babbling indicator.

## Refined H_F (post-static-analysis)

### Original H_F (from Section 4):
> keepAlive setInterval is turn-scoped — collapses after Stop hook fires.

**Status**: REFUTED by source reading. setInterval is session-scoped.

### Refined H_F (consistent with both source reading AND user evidence):

**H_F.1**: After turn ends (`updateThinking(false)` at line 192), if claude resumes from a bg-task `<task-notification>` injection, the SDK stream MAY continue producing `assistant` messages — BUT `updateThinking(true)` is NOT re-called inside this resumption path. So `keepAlive` continues ticking with stale `thinking=false`. App's `session.thinking` stays false → no babbling indicator → user observes "online" only.

**H_F.2**: If claude resumes via a NEW `query()` invocation (not within current code's structure), the same problem occurs because the current code doesn't await any signal that would trigger a new `query()` call between user prompts.

**H_F.3 (transport explanation for "frozen lastUpdated")**: If the CLI's socket disconnects (e.g., page-refresh of web client doesn't disturb CLI socket, but app server's view of CLI heartbeat depends on `lastActiveAt` which is updated by `session-alive` events). If `socket.volatile.emit` silently drops while reconnecting, server's `lastActiveAt` freezes. This is independent of the thinking issue — it would cause the user-visible "Last Updated 23:16:47" frozen.

**H_F.1 + H_F.3 are both consistent with user-observable symptoms**:
- H_F.1 → no babbling indicator (✓ user reported)
- H_F.3 → frozen lastUpdated (✓ user screenshot)
- H_F.1 → bg-task text messages still arrive (via session-scanner), but get rendered after user's next prompt because the app only catches up via fast-path or invalidate (✓ user reported)
