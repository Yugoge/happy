# BA Specification: Codex Tool-Call Popup — Description vs Command Separation (§5.7)

**Request ID**: dev-20260424-143000-9
**Created**: 2026-04-24T14:30:00Z

## Goal

Separate `Description` from the raw command in Codex tool-call detail panels. Currently both `Description` and `Input Parameters.description` display the same raw `/bin/bash -lc "..."` string because `tool.description` is populated from `input.description` (which Codex sets to the bash command). When no real model-provided description is available, `Description` must either be hidden or show a short synthesized summary ("Running bash"), and must never echo the raw command.

## Context

The Codex flavor's `exec_command` tool calls arrive via the ACP protocol path in `typesRaw.ts`. Two channels feed `tool.description`:
1. **ACP `tool-call` path** (lines 1023–1040): `description: null` — description never set here.
2. **Reducer Phase 2 / general `message` path** (lines 800–807): extracts `description` from `c.input.description` if present. For Codex bash, `input.description` appears to carry the same raw `/bin/bash -lc "..."` string as `input.command`.

`ToolFullView.tsx` renders `Description` section from `tool.description` (line 22) and `Input Parameters` section from `JSON.stringify(tool.input, null, 2)` (line 42), which includes `input.description`. When these share the same raw-command source, both fields show identical content — the bug.

This spec applies to all Codex tools (per §5.15), not just `exec_command`/`CodexBash`. The fix is also a prerequisite for §5.15's "raw description, not raw arguments" requirement.

Dependency: §5.6 (Codex popup unification) may be landing in the same cycle. This fix lives in `ToolFullView.tsx` (detail panel layer), which is shared by all tools and does NOT depend on §5.6 (inline card layer). The two fixes are orthogonal and can merge without conflict.

## Requirements (MoSCoW)

### Must Have

- R1: When `tool.description` is null, empty, or identical to `tool.input.command` (or any other raw-command field in `tool.input`), the `Description` section in `ToolFullView` must NOT render (hide it entirely).
- R2: When `tool.description` is a real model-provided natural-language summary (non-null, non-empty, and NOT identical to `tool.input.command`), it must render as the `Description` section — unchanged from today's behavior.
- R3: Applies to ALL tools that go through `ToolFullView` — not just `CodexBash`. (Claude Code tools are unaffected because their `tool.description` is sourced from `envelope.ev.description` which is a proper description, not a command.)

### Should Have

- R4: When `tool.description` is null/empty but the tool is a recognizable bash/exec type (tool name is `CodexBash`, `Bash`, `execute`, `shell`), show a short synthesized fallback: "Running bash" (i18n key `tools.fullView.runningBash`).
- R5: For other tool types where `tool.description` is null, hide the `Description` section (no fallback needed — the tool name in the header already identifies it).

### Could Have

- R6: In `ToolInputSection`, if `tool.input.description` is present AND is identical to `tool.description` (already shown above or hidden due to R1), omit `description` from the input JSON display to avoid redundancy.

### Won't Have (Non-Goals)

- Changing how `tool.description` is populated in `typesRaw.ts` or `reducer.ts` — the fix is render-layer only.
- Modifying the Claude Code description path (it works correctly today).
- Changing `CodexBashView.tsx` (inline card) — this fix is for `ToolFullView.tsx` (detail panel).

## Requirements Decomposition

| ID | Source phrase (verbatim from user) | Acceptance criterion |
|----|-----------------------------------|---------------------|
| R1 | "Description block and Input Parameters.description both duplicate the full /bin/bash -lc string" | `ToolFullView.ToolDescriptionSection` is hidden when `tool.description` is null, empty, or equals `tool.input?.command` |
| R2 | "Description must show the actual description field (the model-provided natural-language summary)" | When `tool.description` is a real summary (non-null, non-empty, differs from `tool.input?.command`), it renders in the Description section unchanged |
| R3 | "The raw command belongs in the Input Parameters / command code block only" | The raw command appears only in the Input Parameters section (via `tool.input`), never in the Description section |

## Edge Cases & Risks

- **Null vs empty string**: `tool.description` can be `null` (ACP path) or potentially `""`. Both must be treated as absent.
- **Identical-to-command detection**: `input.command` for Codex bash is the raw `/bin/bash -lc "..."` string. Comparison must be a strict equality check after trim — do not use substring matching.
- **Other tools**: `ToolFullView` is used by ALL tool types. Guard must not accidentally hide legitimate descriptions for Claude Code tools (where `tool.description` is sourced from `envelope.ev.description`).
- **§5.6 interaction**: §5.6 may unify inline cards but `ToolFullView` (detail panel) is separate. No conflict expected, but dev should verify the unified Codex inline view still correctly passes the `tool` prop to `ToolFullView`.
- **R6 (Could Have) risks**: removing `description` from the JSON input display changes the dev-mode raw JSON view too (unless guarded). Low-risk but coordinate with `ToolRawJsonSection` which shows all fields unconditionally.
- **i18n**: R4 requires a new i18n key `tools.fullView.runningBash` → "Running bash" in all 9 language files. Skip if R4 is deferred.

## Acceptance Criteria

### AC1: Description hidden for Codex bash with no real description

- GIVEN a Codex session with a `CodexBash` / `exec_command` tool call where `tool.description` is null or equals `tool.input.command`
- WHEN the user opens the right-side detail panel for that tool call
- THEN the `Description` section header and content are NOT rendered; `Input Parameters` section renders the raw input JSON including `command`

### AC2: Description shown for tool calls with a real description

- GIVEN any tool call (Claude Code Bash, Codex, or other) where `tool.description` is a non-empty string that differs from `tool.input?.command`
- WHEN the user opens the right-side detail panel
- THEN the `Description` section renders the `tool.description` value as before

### AC3: (Should Have) Synthesized fallback for bash tools

- GIVEN a `CodexBash` or `Bash` tool call where `tool.description` is null or absent
- WHEN the user opens the right-side detail panel
- THEN the `Description` section shows "Running bash" (i18n: `tools.fullView.runningBash`) instead of hiding entirely

### AC4: Applies across all viewport sizes

- GIVEN the above scenarios
- WHEN tested at both 1280x720 (desktop) and 390x844 (mobile)
- THEN behavior is identical
