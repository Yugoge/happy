# BA Specification: AskUserQuestion Answer Persistence + Subagent Sidebar Data Flow

**Request ID**: dev-20260407-0830
**Created**: 2026-04-07T08:30:00Z

## Goal

Fix two data flow bugs: (1) AskUserQuestion answers are lost on page refresh because they only live in a module-level Map, and (2) subagent messages are missing from the sidebar because the session protocol sidechain linking has a fundamental mismatch between CUID2 subagent IDs and the reducer's sidechain lookup keys.

## Context

These are Bugs #74 and #75 from the right sidebar feature (2026-04-06). Both involve data being generated correctly at one stage of the pipeline but lost before reaching the UI.

---

## Problem 1: AskUserQuestion Answer Persistence

### Data Flow Trace (Current)

**Step 1 - App: User selects answer**
- `AskUserQuestionView.tsx:handleSubmit` (line 215) builds:
  - `responseText`: human-readable string like `"Theme: Dark\nLayout: Grid"`
  - `answersRecord`: structured object like `{ "Theme": "Dark", "Layout": "Grid" }`
- Calls `sessionAllow(sessionId, tool.permission.id, undefined, undefined, undefined, responseText, answersRecord)` (line 257)

**Step 2 - App: ops.ts sends RPC**
- `ops.ts:sessionAllow` (line 339) does TWO things:
  1. Stores `answers` in module-level `permissionAnswersStore` Map (line 341-343) -- THIS IS THE ONLY LOCAL PERSISTENCE
  2. Sends RPC: `apiSocket.sessionRPC(sessionId, 'permission', { id, approved: true, reason: responseText, answers: answersRecord })` (line 344-345)

**Step 3 - CLI: permissionHandler.ts receives RPC**
- `permissionHandler.ts:setupClientHandler` (line 425) receives the response
- Stores response in `this.responses` Map (line 437)
- Calls `handlePermissionResponse` (line 441)
- `handlePermissionResponse` (line 123-137): For AskUserQuestion specifically:
  - Builds `updatedInput = { ...baseInput, answers: response.answers }` (line 131-136)
  - Resolves the pending promise with `{ behavior: 'allow', updatedInput }` (line 131)
- **CRITICAL**: The `answers` are merged into `updatedInput` which goes back to Claude SDK as the tool input
- Then moves request to `completedRequests` in agentState (line 444-466) -- but `answers` are NOT stored in completedRequests

**Step 4 - Claude SDK processes the tool result**
- Claude SDK receives `{ behavior: 'allow', updatedInput: { questions: [...], answers: {...} } }`
- SDK creates a `tool_result` message in the JSONL with `content: "..."` (text summary of the result)
- The `answers` object that was in `updatedInput` is consumed by Claude as input context but is NOT echoed back in the `tool_result` content

**Step 5 - sessionProtocolMapper.ts processes tool_result**
- When the `tool_result` block for AskUserQuestion appears in the user message:
  - `enrichToolResultOutput` (line 54-72) checks if the tool is a file content tool -- AskUserQuestion is NOT in `FILE_CONTENT_TOOLS`
  - Falls back to `extractToolResultOutput` which extracts the text content from the `tool_result` block
  - The output is just a text string (Claude's response to having the answers), NOT the structured answers object
- The `tool-call-end` envelope emitted has `output: <text string>` with NO answers data

**Step 6 - App: normalizer converts envelope to NormalizedMessage**
- `typesRaw.ts:normalizeSessionEnvelope` for `tool-call-end` (line 664-681):
  - Creates `tool-result` content with `content: envelope.ev.output ?? null`
  - This is just the text output, no answers

**Step 7 - App: reducer creates ToolCall message**
- Phase 3 (tool results, line 833-888):
  - `message.tool.result = c.content` -- this is the text output
  - `message.tool.permission` -- updated from `c.permissions` but `c.permissions` does NOT have an `answers` field

**Step 8 - App: AskUserQuestionView tries to show saved answers**
- On remount (line 269-303), tries to read answers from:
  1. `(tool.result as any)?.answers` -- undefined (result is text string)
  2. `tool.permission?.answers` -- undefined (permission never gets answers)
  3. `getPermissionAnswers(tool.permission.id)` -- works ONLY if `permissionAnswersStore` Map still exists (same page session)

### WHERE DATA IS LOST

**Primary loss point**: CLI `permissionHandler.ts` line 444-466. When moving the request to `completedRequests` in agentState, the `answers` field from the RPC response is NOT included. The `completedRequests` entry only gets: `{ ...request, completedAt, status, reason, mode, allowedTools }`.

**Secondary loss point**: Claude SDK does not echo `updatedInput.answers` back in the `tool_result`. The answers go INTO Claude as input but never come OUT as result content.

**Tertiary loss point**: The `tool-call-end` envelope from sessionProtocolMapper has no mechanism to carry answers data.

### Correct Fix Direction

The answers need to be persisted in the message stream. Two viable approaches:

**Approach A (CLI-side, recommended)**: In `permissionHandler.ts` line 444-466, include `answers` in the `completedRequests` agentState entry. Then in the reducer, when processing `completedRequests`, copy `answers` to `message.tool.permission.answers`. The `ToolCall.permission` type already has an `answers?: Record<string, string>` field (typesMessage.ts line 22).

**Approach B (Full pipeline)**: Have the CLI emit a custom envelope or modify the `tool-call-end` output to include answers. More invasive.

## Problem 2: Subagent Sidebar Missing Messages

### Data Flow Trace (Session Protocol Path)

**Step 1 - CLI: sessionProtocolMapper creates envelopes for Agent/Task tool**
- When Claude calls Agent/Task tool (line 547-600):
  - `tool_use` block detected, `isSubagentTool(name)` returns true
  - `sessionSubagentForCall = ensureSessionSubagentIdForProviderSubagent(state, call)` -- creates a CUID2 ID
  - For `Task` tool: `shouldHideParentToolCall` returns true
  - Emits `tool-call-start` with `call: sessionSubagentForCall` (the CUID2, NOT the original tool_use_id)
  - The `args` include `sessionSubagent: sessionSubagentForCall`

**Step 2 - CLI: Subagent messages get envelope.subagent field**
- When subagent emits text/tool_use/etc (line 531-607):
  - `resolveProviderSubagent(message, state)` finds the provider subagent ID
  - `getSessionSubagentIdForProviderSubagent` maps it to the CUID2 session subagent
  - All envelopes get `subagent: <CUID2>` in their metadata

**Step 3 - App: typesRaw.ts normalizes session envelopes**
- `normalizeSessionEnvelope` (line 538-721):
  - `parentUUID = envelope.subagent ?? null` (line 553) -- this is the CUID2
  - `isSidechain = parentUUID !== null` (line 554) -- true for all subagent messages
  - For `tool-call-start`: content has `parentUUID: <CUID2>`, `id: envelope.ev.call`
  - For `text`: content has `parentUUID: <CUID2>`, `uuid: envelope.id`

**Step 4 - App: reducerTracer.ts traces sidechain relationships**
- `traceMessages` processes each message:
  - For the Task/Agent `tool-call-start` message (non-sidechain, since it's the PARENT):
    - `getToolCallParentIds(content)` returns `[content.id, content.input.sessionSubagent]` (line 117-124)
    - Both the tool call id AND the CUID2 sessionSubagent are registered in `toolCallToMessageId` (line 185-186)
    - `processOrphans(state, parentId, message.id)` is called for each -- flushes any buffered children
  - For subagent messages (`isSidechain: true`):
    - `parentUuid = getParentUuid(message)` -- returns the CUID2
    - Looks up `state.uuidToSidechainId.get(parentUuid)` OR `state.toolCallToMessageId.get(parentUuid)` (line 257)
    - If the parent tool-call-start was already processed, `toolCallToMessageId.get(CUID2)` returns the message.id of the tool call
    - This becomes the `sidechainId`
    - If parent NOT yet processed: message is buffered as orphan at `orphanMessages.get(CUID2)`

**Step 5 - App: reducer.ts Phase 4 processes sidechains**
- `sidechainMessages` are messages that have `msg.sidechainId` set
- For each: `state.sidechains.get(msg.sidechainId)` gets the sidechain array
- New messages are appended to the array
- `convertReducerMessageToMessage` (line 1174-1227) builds children:
  - `children = reducerMsg.realID ? state.sidechains.get(reducerMsg.realID) || [] : [];` (line 1199)

### WHERE DATA IS LOST

**The Critical Mismatch**: The sidechain lookup at line 1199 uses `reducerMsg.realID` as the key. But `sidechainId` from the tracer is set to the tool-call-start message's `message.id` (the NormalizedMessage id, which is the envelope id). Meanwhile, `reducerMsg.realID` is also set from the NormalizedMessage id (line 659 or 799).

So the question is: does `reducerMsg.realID` of the Agent/Task tool-call message EQUAL the `sidechainId` that the tracer assigns?

**Tracing the IDs**:
1. Tool-call-start envelope has `id: <envelope_id_A>` and `ev.call: <CUID2>` (or original tool_use_id for non-hidden tools)
2. Normalizer creates NormalizedMessage with `id: <envelope_id_A>`, content `[{ type: 'tool-call', id: <CUID2_or_call_id> }]`
3. Tracer registers `toolCallToMessageId.set(<CUID2>, <envelope_id_A>)` and `toolCallToMessageId.set(<call_id>, <envelope_id_A>)`
4. When subagent message arrives with `parentUUID: <CUID2>`, tracer looks up `toolCallToMessageId.get(<CUID2>)` and gets `<envelope_id_A>`
5. So `sidechainId = <envelope_id_A>`
6. Reducer Phase 4 stores messages in `state.sidechains.set(<envelope_id_A>, [...])`
7. `convertReducerMessageToMessage` looks up `state.sidechains.get(reducerMsg.realID)`
8. `reducerMsg.realID` for the tool-call message = the NormalizedMessage id = `<envelope_id_A>` (set in Phase 2, line 799)

**This SHOULD match**. So why are messages missing?

**The ACTUAL root cause is message ORDERING and the orphan buffer**:

For the **session protocol path** (live streaming), messages arrive one-at-a-time. The sequence is:
1. Tool-call-start for Agent (parent) arrives, processed by tracer, registered in `toolCallToMessageId`
2. Subagent text messages arrive with `parentUUID: <CUID2>`, tracer finds match, assigns `sidechainId`
3. Works correctly for LIVE messages

But for **restored sessions** (page refresh, session resume), ALL messages arrive at once in a single `reducer()` call. The `traceMessages` function processes them in order. If the ordering in the message array puts subagent messages BEFORE their parent tool-call-start, the parent is not yet in `toolCallToMessageId` when the child is processed, so the child goes into the orphan buffer. When the parent tool-call-start IS processed later, `processOrphans` is called (line 190-191) which DOES flush the orphans.

**However**, there is a subtle bug: when `processOrphans` is called from the `getToolCallParentIds` loop (line 185-191), it uses `message.id` (the NormalizedMessage.id) as the `sidechainId`. But the orphans were buffered under key `parentUuid` which is the CUID2. The `processOrphans(state, parentId, message.id)` call at line 190 passes `parentId` (which iterates over the tool call parent IDs including the CUID2) and `message.id` (the sidechainId). This looks correct.

**The REAL issue is likely in Phase 4 of the reducer**: The `sidechainMessages` are processed and stored in `state.sidechains.set(msg.sidechainId, existingSidechain)`. But then `convertReducerMessageToMessage` at line 1199 does `state.sidechains.get(reducerMsg.realID)`. For the FIRST time the tool-call message is created (Phase 2), `changed.add(mid)` fires. But if sidechain messages arrive in a LATER `reducer()` call, the tool-call message is NOT in `changed` (it was already processed), so `convertReducerMessageToMessage` is never called again for it.

**Wait** -- Phase 4 line 1083-1091 explicitly handles this:
```
for (const [internalId, message] of state.messages) {
    if (message.realID === msg.sidechainId && message.tool) {
        changed.add(internalId);
        break;
    }
}
```

This searches ALL messages for one whose `realID === msg.sidechainId`. This SHOULD work. But it's an O(n) scan and requires `message.realID` to match `msg.sidechainId`.

**THE ACTUAL BUG**: For session protocol messages, the reducer creates the tool-call message in Phase 2 with `realID: msg.id` where `msg.id` is the NormalizedMessage's id (the envelope id). But `msg.sidechainId` from the tracer is ALSO the envelope id of the parent. So `message.realID === msg.sidechainId` should be true.

After careful analysis, the most likely failure scenario is:

**When the tool-call message was created from a PERMISSION (Phase 0), not from the tool-call-start message (Phase 2)**. In Phase 0, the tool-call message is created with `realID: null` (line 449). Then in Phase 2, when the tool-call-start arrives, it matches via `state.toolIdToMessageId.get(c.id)` and updates `message.realID = msg.id` (line 733). BUT -- `c.id` for a hidden Task tool is the CUID2 sessionSubagent (from the mapper line 573: `call: sessionSubagentForCall`). The `toolIdToMessageId` was registered with the permission id (which is the original `tool_use_id` from Claude), NOT the CUID2.

**So for Task tools**: permission id = original `tool_use_id` (e.g. `toolu_01XYZ...`), but the tool-call-start has `call: <CUID2>`. Phase 2 looks up `state.toolIdToMessageId.get(<CUID2>)` which returns NOTHING because the permission was stored under `toolu_01XYZ...`. A NEW message is created with `realID: msg.id = <envelope_id>`. Then Phase 4 sidechain messages look for `message.realID === msg.sidechainId` which is `<envelope_id>`, and this DOES match the new message. But now there are TWO messages for the same tool: one from Phase 0 (permission) with `realID: null`, and one from Phase 2 with `realID: <envelope_id>`.

This is not the primary issue though. The primary issue for missing sidebar messages is simpler: **some message types produced by the normalizer for session protocol envelopes do not have `isSidechain: true`**. Specifically:

- `turn-start`, `turn-end`, `start`, `stop` envelopes return `null` from the normalizer (lines 556-574), so they never reach the reducer at all -- this is correct.
- `service` events return with `isSidechain: false` (line 598) even when the envelope has a `subagent` field -- this means service events in subagents are NOT treated as sidechain messages.

But the main missing messages are text and tool calls from the subagent, which DO get `isSidechain: true` from the normalizer. So the data flow analysis suggests the pipeline is MOSTLY correct for session protocol messages.

**The actual observed symptom needs browser console inspection** to confirm which specific messages are missing from children[].

## Requirements (MoSCoW)

### Must Have
- Problem 1: AskUserQuestion answers must persist through page refresh
- Problem 2: All subagent text and tool-call messages must appear in sidebar children[]

### Should Have
- Answers should flow through the proper message pipeline (JSONL -> server -> app)
- Fix should work for both live and restored sessions

### Could Have
- Answers could be stored in agentState completedRequests for immediate availability

### Won't Have (Non-Goals)
- No changes to Claude SDK behavior
- No changes to server-side message storage format

## Edge Cases & Risks

- Race condition: answers RPC arrives before/after tool completion
- Session resume: answers must survive CLI restart and session restore
- Multiple AskUserQuestion tools in same session
- Orphan message ordering during session restore for subagent messages

## Acceptance Criteria

### AC1: AskUserQuestion answers survive page refresh
- GIVEN user answered an AskUserQuestion and refreshed the page
- WHEN the session reloads and the AskUserQuestion tool renders
- THEN the selected answers are displayed (not dashes)

### AC2: Subagent sidebar shows all messages
- GIVEN a completed Agent/Task tool call with subagent activity
- WHEN user opens the sidebar for that tool
- THEN all subagent text, thinking, and tool-call messages appear in the sidebar
