# BA Specification: Fix codex session registration gap so codex sessions survive dev-daemon restart

**Request ID**: 20260428-215017
**Created**: 2026-04-28T22:00:00Z

## Goal

Close the registration gap where codex-flavor sessions are not enrolled into the daemon's `/list` snapshot, so a future dev-daemon restart can recover them via `--resume <codexThreadId>` through the same recovery pipeline that already works for claude sessions.

## Context

The dev daemon (`happy-daemon-dev`) currently parents 10 sessions (5 claude + 5 codex). All 5 claude sessions appear in the recovery snapshot manifest the recovery script writes; all 5 codex sessions are absent. On a daemon restart, the recovery pipeline can re-spawn the 5 claude sessions via `--resume <UUID>` but cannot resurrect the 5 codex sessions because they were never enrolled. Production daemons (`happy-daemon`, `happy-daemon-jade`) parent only claude sessions and are unaffected.

The defect originated when codex `--resume` infrastructure was added (commit `64d96741`, "Add Codex thread resume support", 2026-03-08): metadata-side `codexThreadId` was wired through, but the parallel daemon-HTTP `notifyDaemonSessionStarted` re-notification that claude performs at `claude/session.ts:112-124` was not ported to the codex spawn paths.

## Edge Cases & Risks

- **Codex thread that never has a first user turn**: the lazy `if (!client.hasActiveThread())` branch never fires, so no notify happens. The codex app server has no thread state to recover anyway — this is consistent with the current "no recovery for empty session" behavior and is not a regression. (Architect issue arch-3, severity minor, accepted.)
- **`session.updateMetadata` vs `notifyDaemonSessionStarted` ordering**: `updateMetadata` runs the handler synchronously to compute the new metadata, then queues the network write inside an internal lock. `notifyDaemonSessionStarted` is an independent HTTP POST. The two write to different sinks; no race. Dev MUST compose the metadata blob ONCE and pass the SAME blob to both — never reuse the stale `metadata` local variable.
- **Fire-and-forget semantics**: claude's call at `session.ts:120` uses `.catch()` and never awaits the result. Mirror this for codex: a daemon HTTP failure must NOT block the codex turn loop. Use `.catch(err => logger.debug(...))` per the claude pattern.
- **Mid-resume failure**: if `client.resumeThread()` rejects, control exits via the existing `try/catch` in `resumeExistingThread.ts:46-49` BEFORE the new notify call would execute. No partial state.
- **Mid-thread-start failure**: same — the new notify call lives inside the existing `try { ... } catch` at `runCodex.ts:692/729+`. Failure short-circuits before notify.
- **Stale `metadata` local in `runCodex.ts:710-713`**: the local `metadata` variable composed at line 180 (via `createSessionMetadata`) does NOT have `codexThreadId`. The dev fix MUST pass `{...currentMetadata, codexThreadId: startedThread.threadId}` (where `currentMetadata` is the closure parameter from the `updateMetadata` handler) — NOT the outer-scope stale `metadata`.
- **`controlServer.ts:82` fallback regressing claude path**: the `??` coalesce only fires when `claudeSessionId` is empty. Since flavor is set once per session at `createSessionMetadata({flavor: 'codex' | 'claude'})` and never transitions, no claude session can carry a stray `codexThreadId`. Safe.
- **Sandbox-daemon vs live-daemon verification**: QA verification MUST use sandbox-daemon mode per `/root/.claude/projects/-dev-shm-dev-workspace-happy-dev/CLAUDE.md` Cycle C — restarting `happy-daemon-dev.service` for verification would kill the 5 live codex sessions BEFORE the fix is deployed. Acceptance criterion AC4 enforces this.

## Acceptance Criteria

### AC1: Codex thread-start notifies daemon with thread id
- GIVEN a codex session has just spawned and `client.startThread()` has returned a `startedThread.threadId` for the first user turn
- WHEN the lazy thread-start branch in `runCodex.ts:710-713` runs
- THEN `notifyDaemonSessionStarted` is invoked exactly ONCE with `(session.sessionId, metadataBlob)` where `metadataBlob` contains `codexThreadId === startedThread.threadId`
- AND the call is fire-and-forget (no `await`, with `.catch(err => logger.debug(...))`)
- AND the metadata passed to `notifyDaemonSessionStarted` is the SAME blob written by `session.updateMetadata` (composed once, used twice)

### AC2: Codex resume notifies daemon with resumed thread id
- GIVEN a codex session is resuming via `--resume <threadId>` and `client.resumeThread()` has returned a `resumedThread.threadId`
- WHEN the resume branch in `resumeExistingThread.ts:35-38` runs
- THEN `notifyDaemonSessionStarted` is invoked exactly ONCE with `(<happy session id>, metadataBlob)` where `metadataBlob` contains `codexThreadId === resumedThread.threadId`
- AND the function signature has been widened to expose the happy session id to the call site (either via `session.sessionId` if `ResumeThreadSession` is widened, or via a new explicit parameter)
- AND the call is fire-and-forget with `.catch(err => logger.debug(...))`

### AC3: Daemon /list response surfaces codex thread id under claudeSessionId field
- GIVEN the daemon has a `TrackedSession` whose `happySessionMetadataFromLocalWebhook` has `claudeSessionId === undefined` (or empty) AND `codexThreadId === "019d-..."` (some codex thread id)
- WHEN a client POSTs to `/list`

- AND the field name in the JSON response is still literally `claudeSessionId` (so the user-only recovery script's existing parser works without modification)

### AC4: Existing claude registration path unchanged

- AND no claude session is observed to lose its `claudeSessionId` after the controlServer.ts:82 change
