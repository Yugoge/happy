## 4. QA verification of each codex finding (against running source)

QA must not rubber-stamp codex; QA must reproduce. Each finding tested via direct vitest fixture against the actual built parser:

### Finding 1 — Compact `<details>` not parsed

**Test (vitest reproducer)**:
```typescript
const blocks = parseMarkdown('<details><summary>X</summary>Y</details>');
// expected: blocks[0].type === 'details'
// actual:   blocks[0].type === 'text', content '<details><summary>X</summary>Y</details>' rendered literal
```

**Source root cause** (`parseMarkdownBlock.ts:330`):
```typescript
function tryDetailsBlock(ctx: ParseCtx, line: string, lineStartIndex: number): boolean {
    const openMatch = line.match(DETAILS_OPEN_RE);
    if (!openMatch) return false;
    const endIndex = findDetailsClose(ctx.lines, lineStartIndex + 1);  // <-- starts AFTER current line
    if (endIndex === -1) return false;
```

`findDetailsClose` starts at `lineStartIndex + 1`, so it never checks the current line. When `<details>` and `</details>` appear on the SAME line, the closing tag is missed and the block falls through to literal text rendering.

**User-need impact**: HTML5 spec allows `<details><summary>X</summary>Y</details>` on a single line. This is a common authoring pattern. BA spec §4 line 88 prose explicitly cites this form. The AC test fixture happens to use multiline only, so QA's PASS verdict missed it.

**Severity**: Major — direct user-need violation, in-scope per Section 5.4 rule 3 (user-need axis).

**Verdict**: REAL BUG, NEW in this diff (tryDetailsBlock is new in Cycle 8).

### Finding 2 — sub/sup styles identical (no baseline shift)

**Source** (`MarkdownView.tsx:524-525`):
```typescript
sub: { fontSize: 12, lineHeight: 16 },
sup: { fontSize: 12, lineHeight: 16 },
```

These are byte-identical. There is no `transform: [{ translateY: N }]`, no `verticalAlign`, no `lineHeight` differential. Visually H₂O and E=mc² will render with `2` simply at smaller font, with no vertical shift to distinguish subscript from superscript.

**BA spec contradiction**: §11 lines 364-365 explicitly specifies:
```
sub: { fontSize: 12, lineHeight: 16, transform: [{ translateY: 4 }] },
sup: { fontSize: 12, lineHeight: 16, transform: [{ translateY: -4 }] },
```

Dev shipped without the `transform` part of the spec. The desktop screenshot does show `H₂` with `2` as smaller text and `mc²` similarly — visually they look correct because of font fallback baseline behavior in the browser, but the React Native style declarations are wrong, which means native rendering will fail to distinguish them.

**User-need impact**: BA AC-9-HTML-SUB and AC-9-HTML-SUP exist precisely to make subscript appear below baseline and superscript above. Identical styles cannot semantically render that.

**Severity**: Major — direct user-need violation, in-scope per Section 5.4 rule 3.

**Verdict**: REAL INCOMPLETE IMPLEMENTATION, NEW in this diff.

### Finding 3 — Code block contents stripped by extractDefinitions

**Test (vitest reproducer)**:
```typescript
const md = '```\n[ref]: https://example.com\nsome code\n```';
const blocks = parseMarkdown(md);
// expected: code block content contains '[ref]: https://example.com\nsome code'
// actual:   code block content === 'some code' (the [ref]: line is GONE)

const md2 = '```\n[^1]: footnote-like line in code\n```';
const blocks2 = parseMarkdown(md2);
// expected: code block content === '[^1]: footnote-like line in code'
// actual:   code block content === '' (entire content stripped)
```

**Source root cause** (`parseMarkdownBlock.ts:364-386`):
```typescript
function extractDefinitions(rawLines: string[]): { bodyLines: string[], defs: BlockDefs } {
    // ... iterates ALL rawLines, no awareness of code-fence state ...
    for (const line of rawLines) {
        const lm = line.match(LINK_DEF_RE);
        if (lm && !lm[1].startsWith('^')) {
            linkDefs.set(...);
            continue;  // <-- line removed from bodyLines
        }
        const fm = line.match(FOOTNOTE_DEF_RE);
        if (fm) { footnoteRawDefs.set(...); continue; }  // <-- ditto
        bodyLines.push(line);
    }
```

`extractDefinitions` runs as a single global pre-pass over the raw line stream BEFORE `parseSingleLine` ever sees a fenced-code-block opener. There is no fence state tracking, so any line matching `LINK_DEF_RE` or `FOOTNOTE_DEF_RE` inside a `\`\`\`...\`\`\`` block is silently swallowed.

**User-need impact**: The happy-app rendering audit (saga purpose) is itself a content type where users frequently document markdown syntax in fenced code blocks for explanation. Tutorials, bug reports, code samples, and AI agent output that quote markdown reference-link or footnote syntax are corrupted. The user's own request "spec不留一点没有做完的空间" refers to clean parser support — landing one feature while regressing another is not "finished".

**Severity**: Critical — silent data loss, regression introduced by THIS diff (extractDefinitions is new in Cycle 8).

**Verdict**: REAL REGRESSION, NEW in this diff. Section 5.4 rule 3 cleanliness-of-THIS-diff axis applies.

Modal.alert(`Footnote ${props.span.footnoteLabel}`, text, [{ text: t('common.ok'), style: 'cancel' }]);
