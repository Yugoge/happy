## What's documented as residual / out-of-scope

### W3 (verbatim from BA spec): pre-existing symlinks at cp-state paths

`spec-check.py` uses `path.read_text()` / `path.write_text()` without `O_NOFOLLOW` / `lstat`. If a malicious symlink pre-exists at a cp-state path (introduced by a different attack vector OR a pre-compromised state), the script follows it. The new write-guard prevents subagent CREATION of such a symlink (`ln` is in VC3); fixing the read-side is a separate cycle.

### 21 obscure adversarial Bash forms (codex round-2 in dev-QA)

QA's codex consultation enumerated 21 additional bypass forms (`gawk -i inplace`, `perl -pi -e`, `tar -xC`, `unzip -d`, `node -e fs.writeFileSync`, `pushd`/`popd`, `cd -`, `>|` clobber, `tee --append`, `sudo touch`, `if/then` wrap, `printf | tee`, `patch -o`, `python -m json.tool`, `python os.replace`, `wget -P`, `curl --output=` flag variants, `ln -s -t` flag variant). These are NOT covered by the 22-form deny.

**Why out-of-scope**:
- Threat model is **cooperative-but-buggy subagent**, not adversarial.
- Cooperative LLMs reach for Edit / Write / `cat >` / `python -c open()` first — all covered by the 22 forms.
- Modern LLMs do NOT reach for `gawk -i inplace` / `perl -pi -e` / `tar -xC` to update a JSON checkpoint file. These are sysadmin idioms outside the LLM-coding training distribution.
- The deny message itself teaches the right path: when a subagent hits the deny, the stderr explicitly names `spec-check.py` as the proper tool.
- True adversarial defense requires a different architecture (filesystem-level enforcement, setuid wrappers, default-deny Bash whitelist) — separate cycle if needed.

The 21 forms are recorded in BA spec W3 + this completion report for downstream cycle visibility.
