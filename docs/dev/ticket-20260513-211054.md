## Goal

Bring codex sessions to first-class biological-child status alongside claude-code sessions in happy-cli, so the daemon `/list`, the codex tid-bind notification, the durable per-daemon mapping file, and the recovery/restart/save/watcher scripts all treat codex parity-equivalent to claude. User accepted `养子也可以` (adopted-child = 99% parity), so the goal is functional symmetry, not pedantic identity.

## Context

happy-cli already tracks claude sessions as first-class citizens through three pillars: (1) claude UUID present in the cmdline (`--resume <uuid>`), (2) daemon `/list` exposes `claudeSessionId`, (3) recovery script scans claude rollouts via `~/.claude/projects/...`. Codex sessions are second-class on FIVE axes:

1. **Cmdline visibility**: codex Rust binary holds the tid internally; no cmdline marker.
2. **/list endpoint**: returns claude-shaped rows only; codex sessions invisible by tid.
3. **Spawn-time ID ownership**: codex generates tid inside `thread/start` (async, post-spawn) — happy-cli CANNOT preassign.
4. **State file location**: codex rollouts live in shared `/root/.codex/sessions/` — no per-daemon scoping. (This shared-dir reality is also why AC1/AC2 must verify primarily via mocked codex clients — see Iteration Note below.)
5. **Identifier format**: codex uses UUIDv7 (timestamp-prefixed) — caused regex rot at recovery-script line 767 fixed in commit 043e3fec.

Today's band-aid is `scan_codex_via_fd` in `/root/bin/happy-session-recovery.sh:798-818`, which walks `/proc/<pid>/fd` to find codex processes holding rollout files open. It works but is fragile (depends on /proc visibility), indirect (no causal link to daemon ownership), and incomplete (post-daemon-restart blind spot until codex re-opens fds).

The claude reference path (`packages/happy-cli/src/claude/session.ts:112-124`) shows the pattern that should be mirrored: after the session ID is discovered downstream, `notifyDaemonSessionStarted` is called AGAIN with the enriched metadata — same hook, idempotent re-call (verified at `daemon/run.ts:181-188`). Codex re-notify is missing today.

- **M2 — Atomic write utility (codex-mapping ONLY)** *(revised per F3)*: Create `packages/happy-cli/src/utils/atomicWriteJson.ts` exporting a single function that: (a) writes to a `.tmp.<pid>` sibling file, (b) `fsync`s the tmp file, (c) `rename`s to the target path (POSIX-atomic on same filesystem), (d) `fsync`s the parent directory. Used by M3 mapping file ONLY in this cycle. **Locking is moot** *(revised per F6)*: M3 makes the daemon the SINGLE writer of codex-mapping.json — codex wrappers send tid via /session-started, the daemon owns the mapping file write. - **M3 — Per-daemon codex mapping file (daemon-as-SSoT writer)** *(revised per F6)*: New file at `$happyHomeDir/codex-mapping.json` written EXCLUSIVELY by the daemon (NOT by codex wrappers) via the M2 utility. Codex wrappers send tid via the existing idempotent `/session-started` endpoint (M1 helper); the daemon's webhook handler (`run.ts:179-205`) writes the mapping row. Schema: `{schemaVersion: 1, entries: [{happySessionId, codexThreadId, pid, cwd, flavor: 'codex', state: 'pending' | 'bound' | 'stale', firstSeenAt, lastUpdatedAt}]}`. Writer (daemon-side): on (a) initial /session-started without tid → state=pending row, (b) /session-started with tid → state=bound row, (c) session end → remove row. Readers: recovery script + daemon startup sweep (state=stale GC). Readers do NOT need locks — POSIX rename is atomic AND daemon is the sole writer (naturally serialized via single Node process event loop).

- **M4 — /list schema v2 with flavor discriminator (ADDITIVE)** *(revised per F4)*: Extend `controlServer.ts:60-86` Zod response to include `schemaVersion: 2` at response root + per-row OPTIONAL fields:

Once tid binds (M1 fires), pending → bound, `tidPending` flag clears.

## Edge Cases & Risks

- **R-1**: tid-bind never arrives (codex process crashes before thread/start completes). Mitigation: M5 + S1 — pending rows older than 30s are GCed.
- **R-2**: thread/resume returns a DIFFERENT tid than requested (codexAppServerClient.ts:856 rotates). Mitigation: M7 — helper is called with RESULT tid, not requested.
- **R-3**: Two codex spawns within one daemon at the same millisecond. Mitigation: daemon-as-single-writer (M3 per F6) — there is exactly one daemon process writing the mapping file; serialization is natural via Node single event loop. Codex wrappers never write the file directly.
- **R-4**: Daemon crashes mid-write of mapping file. Mitigation: atomic-rename in M2 — readers see old or new, never partial. Tests assert sequence (tmp write → fsync → rename → parent fsync) per AC3.
- **R-5**: Recovery script's existing jq filters silently break when new fields appear. Mitigation: M4 audit of ALL named consumers (including hidden integration tests at `packages/happy-agent/...` and `packages/happy-cli/src/openclaw/...`) BEFORE /list schema bump ships; consumers must tolerate optional fields.
- **R-6**: process.title truncation on Linux (16 chars). Mitigation: short tid prefix (8 chars) per S3 note.
- **R-7**: happy-restart.sh pre-save logic must NOT lose claude UUIDs when adding codex tid handling. Mitigation: M8 Branch A (v1 fallback) preserves existing claude-only capture path unchanged.
- **R-8 (NEW per F5)**: Restart-script ships before production daemon binary upgrade — v1 /list response from default+jade daemons could cause new script to drop claude UUIDs. Mitigation: AC6-mandated schema-version guard with legacy-path fallback (M8 Branch A). Tested explicitly in AC6 against a v1-/list mock. This is the critical risk surfaced by QA F5.

  - **Fault model A — kill-before-rename**: simulate the writer exiting BEFORE the rename call (test: write to .tmp, do NOT call rename, verify target file remains old contents OR is absent if no prior file existed).
