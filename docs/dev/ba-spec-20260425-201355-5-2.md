# BA Specification: §5.2 Context% Display Broken — Architecture Bug (Cycle 6 Re-attempt)

**Request ID**: dev-20260425-201355-5-2
**Created**: 2026-04-25T20:13:55+00:00
**Spec item**: §5.2 of `docs/dev/specs/spec-20260424-084848.md`

## Goal

Make the AgentInput status-bar context-usage indicator (`N% left`) display correctly for both `default` and `sonnet 4.6` Claude model selections in happy-dev. The Cycle 1 attempt patched the L3 denominator lookup table but did NOT address the deeper L4 issue: the picker key `'default'` carries no model identity, the CLI never populates `metadata.currentModelCode` for Claude sessions, and the per-model lookup heuristic therefore always falls back to `200_000` even when the actual underlying Claude model is 1M-context. Additionally, the `usageData?.contextSize` falsy-guard at the call site silently hides the indicator entirely whenever `latestUsage` has not yet been observed (offline session, fresh session, post-restore).

Cycle 1 (BA spec `ba-spec-20260424-143000-6.md`, dev report `dev-report-20260424-143000-6.json`, commit `0ba2ddfc`) introduced `getModelContextWindow(modelKey)` in `modelModeOptions.ts` and replaced the hardcoded `MAX_CONTEXT_SIZE=190000` constant in `AgentInput.tsx` with a per-session resolved value. ## Requirements (MoSCoW)

### Must Have

- **R1 (L4 happy-app — picker-default → 1M)**: When `props.modelMode?.key === 'default'` (or null) on a Claude flavor session, treat the resolved context window as `1_000_000`. This encodes the user's product assertion that "default 模型本身就是 1M". Do NOT depend on `metadata.currentModelCode` being populated, because the Claude CLI path does not populate it.
- **R2 (L4 happy-app — non-default picker → existing logic)**: When `props.modelMode?.key` is `'opus'`, `'sonnet'`, or `'haiku'`, retain the current `getModelContextWindow` lookup (returns `200_000`). User has not asserted these are 1M; they remain at the documented Anthropic 200k window.
- **R3 (L4 happy-app — falsy-guard fix)**: Replace the truthy guard at AgentInput.tsx:365 from `props.usageData?.contextSize ? ... : null` with a presence check (`props.usageData ? ... : null`) so that an unhydrated `contextSize=0` does NOT hide the indicator when `alwaysShowContextSize=true`. The `getContextWarning` function itself already returns `null` for `alwaysShow=false && remaining > 10`, so removing the outer truthy gate does not regress non-show cases.
- **R4 (acceptance — sonnet 4.6 still works)**: With picker='sonnet' and `alwaysShowContextSize=true`, status bar must show `N% left` for an active session with non-zero `contextSize`.
- **R5 (acceptance — default → 1M)**: With picker='default' and `alwaysShowContextSize=true`, status bar must show `N% left` against a `1_000_000` denominator. Concretely: at `contextSize=200_000`, display ≈ `80% left`; at `contextSize=500_000`, display ≈ `50% left`; at `contextSize=900_000`, display ≈ `10% left`.

## Edge Cases & Risks

- **Picker = `'default'` on non-Claude flavor**: Codex and Gemini also expose a `'default'` picker key. The current `resolvedModelKey` logic falls through to `metadata.currentModelCode` for those, which IS populated by the ACP path. The fix MUST scope the new `'default' → 1_000_000` rule to Claude flavor only (use `props.metadata?.flavor === 'claude'` or default-to-claude when flavor is undefined per `getDefaultModelKey` behaviour).
- **`usageData` entirely undefined**: If `usage` is `undefined` from `resolveUsageData` (no `latestUsage` yet AND no `session.latestUsage`), the indicator should render NOTHING (no false data). The new presence check `props.usageData ? ... : null` correctly handles this — only when `usageData` exists but its `contextSize` is `0` does the new behaviour differ.
- **`alwaysShowContextSize=false` + low usage**: existing behaviour is preserved — `getContextWarning` returns `null` when `remaining > 10` and `alwaysShow=false`. R3 only removes the OUTER truthy guard; the function's internal early-return is unchanged.
- **User later adds `[1M]` Claude variant to picker**: R1's "claude default → 1M" rule still works; explicit `'opus-4-7-1m'`-style keys would continue to match the existing `/1m$/i` heuristic in `getModelContextWindow`, which already returns 1_000_000.
- **Cycle 1 fix coexistence**: This cycle does NOT remove the `getModelContextWindow` helper or its 1M heuristics. Instead it adds a flavor-aware default rule layered on top. This minimises blast radius.
- **No revert / no history rewrite**: This is a pure forward fix on top of commit `0ba2ddfc`. The destructive-action escalation rule does not apply.

### Concrete patch sketch (illustrative — dev should adapt)

```ts
// modelModeOptions.ts — add below getModelContextWindow
export function getDefaultModelContextWindow(flavor: AgentFlavor): number {
    // Source: user assertion in spec-20260424-084848.md line 2801 + Anthropic public model docs.
    // The 'default' picker on Claude sessions in happy-dev runs against a 1M-context Claude model.
    // Codex default is gpt-5 series (~200k effective). Gemini default is 2.5 series (1M+).
    if (flavor === 'codex') return 200_000;
    if (flavor === 'gemini') return 1_000_000;
    // claude (default) and unknown flavors → claude semantics
    return 1_000_000;
}

// AgentInput.tsx ~line 360 — replace existing resolvedModelKey/maxContextSize block
const pickerKey = props.modelMode?.key;
const maxContextSize = (!pickerKey || pickerKey === 'default')
    ? getDefaultModelContextWindow(modelFlavor)
    : getModelContextWindow(pickerKey);
const contextWarning = props.usageData
    ? getContextWarning(
        props.usageData.contextSize,
        props.alwaysShowContextSize ?? false,
        theme,
        maxContextSize,
      )
    : null;
```

Note: `modelFlavor` already exists at line 327 (`const modelFlavor = props.metadata?.flavor ?? props.agentType;`), so no new prop threading is required.
