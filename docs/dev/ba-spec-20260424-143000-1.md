# BA Specification: Inline LaTeX $...$ not rendered (§5.16)

**Request ID**: dev-20260424-143000-1
**Created**: 2026-04-24T14:30:00+00:00

## Goal

Add inline `$...$` LaTeX recognition to the markdown span parser and wire a `displayMode: false` render path through `MarkdownView`, so that inline math expressions appear typeset inline with surrounding text. Display math `$$...$$` already works and must not be regressed.

## Context

Commit `f8b208fa` (2026-03-23) introduced `LatexRenderer.tsx`, added `$$...$$` block-level detection in `parseMarkdownBlock.ts`, and routed those blocks into `LatexRenderer` via `MarkdownView.tsx`. However, the inline counterpart (`$...$`) was never implemented: `parseMarkdownSpans.ts` was not touched in that commit, and the `MarkdownSpan` type has no `latex` variant. As a result, any inline math expression like `$a^2 + b^2 = c^2$` passes through the span parser as raw plain text and is rendered verbatim.

- **Measured**: `parseMarkdownSpans.ts` line 4 — the regex pattern handles `**bold**`, `*italic*`, `[link](url)`, and `` `code` `` only. No `$...$` case exists. `MarkdownSpan.styles` (parseMarkdown.ts:42) accepts `'italic' | 'bold' | 'semibold' | 'code'` — no `'latex'` variant. The only LaTeX path in `parseMarkdownBlock.ts` starts at line 73: `if (trimmed.startsWith('$$'))`, which handles block display math exclusively.

- **Gap**: The span regex in `parseMarkdownSpans.ts` has zero cases matching `$...$`. No `latex-inline` span type exists anywhere in the type system. `LatexRenderer.tsx` always passes `displayMode: true`, making it unsuitable for inline use without a new prop.

## Edge Cases & Risks

- **`$` in non-math context**: Price strings like `$100` or shell variables `$HOME` must not be incorrectly parsed as LaTeX. Fix: require the closing `$` to appear before the next whitespace and to not be immediately preceded by a digit or alphanumeric character at the start. A safe heuristic: `$[^ $]([^$]*?)[^ $]$` (content must not start or end with whitespace; must have at least one character; single-char content is allowed if not a digit directly following `$`). Dev should use a conservative regex and document the limitation.
- **Escaped dollar sign**: `\$` should not open a LaTeX span. Dev must check the character before `$`.
- **`displayMode: true` in `LatexRenderer`**: Current callers always use block mode. Adding `inline` prop must default to `false` so existing usage is unchanged.
- **React Native Text nesting**: Inline KaTeX HTML cannot be embedded directly inside React Native `<Text>`. On native, inline LaTeX will likely need a small `<WebView>` or `dangerouslySetInnerHTML` `<span>` (web only). Dev should verify whether a `dangerouslySetInnerHTML` `<span>` inside a `<Text>` works on web, and fall back to a `<View>` with `flexDirection: 'row'` wrapping for cross-platform if needed.

## Technical Hints

- **Affected files** (in order of change):
  1. `packages/happy-app/sources/components/markdown/parseMarkdown.ts` — add `latex-inline` span discriminant to `MarkdownSpan` type (or add a new `type: 'latex'` field alongside `styles`)
  2. `packages/happy-app/sources/components/markdown/parseMarkdownSpans.ts` — add `$...$` to the regex pattern and produce the new span
  3. `packages/happy-app/sources/components/markdown/LatexRenderer.tsx` — add `inline?: boolean` prop; pass `displayMode: !inline` to KaTeX
  4. `packages/happy-app/sources/components/markdown/MarkdownView.tsx` — in `RenderSpanItem`, detect `latex` span type and render `<LatexRenderer inline content={...} />`
- **Pattern to follow**: inline `code` span (backtick pattern in `parseMarkdownSpans.ts:74-76`) is the closest parallel; adapt for `$...$` with appropriate ambiguity guards
- **Span model choice**: The cleanest approach is to add a discriminant field `latexContent?: string` to `MarkdownSpan` alongside the existing `styles/text/url` fields, rather than adding 'latex' to the styles enum (which is semantically a style, not a content type). Alternatively, add a new union arm to `MarkdownSpan`. Dev should pick the approach that minimises cast/type-guard noise in `RenderSpanItem`.
- **KaTeX inline size**: add `fontSize: 'inherit'` to the KaTeX container CSS to avoid font-size jumps relative to surrounding text.
- Run `yarn typecheck` in `packages/happy-app` after all changes.
