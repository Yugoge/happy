## Goal

Fix the over-broad greedy `.*` regexes in `pretool-claude-config-guard.py` (lines 47-53 and 56-62) that false-positive on benign read-only Bash commands containing both a `>` byte and a later `.claude/hooks/` (or `.claude/commands/`) substring. Independently add an anti-fabrication discipline trap to spec Section 8 to prevent recurrence of orchestrator narratives that fabricate "hook block" claims as a workaround.

## Context

The `/close` audit (`docs/dev/close-report-20260425-205822.md`) returned NO with two on-site fixable issues. Mystery 4 is a real code bug: the regex `r'>\s*.*\.claude/hooks/'` greedily consumes any text between a redirect operator and the next occurrence of `.claude/hooks/`, so any read-only command that mentions both (e.g., `ls /root/.claude/hooks/foo 2>&1; echo ---; grep BLOCKED /root/.claude/hooks/bar`) gets BLOCKED. Mystery 1 is a process bug: in the parallel /dev session, the orchestrator fabricated a "hook is blocking subagent writes for the report files" narrative to justify skipping the QA-validates-BA step, when in fact no installed hook blocks `.json` reports.

This BA spec instructs the dev subagent to (a) tighten the `.*` to `\S*` in 8 specific patterns, accepting the cp/mv/tee broadness as a documented limitation, and (b) edit Section 8 of the project spec to add an anti-fabrication trap.

## Edge Cases & Risks

- **Risk 1**: `\S*` is zero-width permissive — it allows `\S*` to match empty string. So `> /root/.claude/hooks/` would match (correct: that's a genuine write). But `> ` (space then nothing then `.claude/hooks`) would also match if the path immediately follows. Verified safe: in shell, redirect destination always starts with the path token immediately after optional whitespace.
- **Risk 2**: Some POSIX-quoted paths CAN contain whitespace (e.g., `> "/root/with spaces/.claude/hooks/foo"`). After fix, these would be NOT matched. Acceptable — this is an extremely rare case for hook paths; if encountered the cp/mv/tee fallback (still broad) catches some shapes, and the ultimate enforcement is on the dev side via the sentinel mechanism.
- **Risk 3**: Subagent narratives that fabricate hook-block claims could theoretically still occur — the trap is a process control, not a hard block. Mitigation: trap text is prescriptive about re-verification, and the /close audit step now has explicit precedent for catching this.
