# BA Specification: Permanently Fix Title Change (Bug #62)

**Request ID**: dev-20260404-080000
**Created**: 2026-04-04T08:00:00Z

## Goal

Permanently fix the session title change mechanism so that (1) the MCP tool call succeeds without "endpoint connection error", (2) the tool call renders as a tool block in the UI, and (3) the sidebar updates in real-time to show the new title.

## Context

When Claude calls `mcp__happy__change_title`, the title IS persisted via an internal handler in `startHappyServer.ts` (Path B), but the MCP tool call itself fails (Path A) because the STDIO bridge cannot connect to the HTTP MCP server. The sidebar does not refresh because the app already has the correct sync infrastructure (WebSocket `update-session` broadcast with metadata) -- the problem is upstream: the metadata update is fired from `sendClaudeSessionMessage` which receives a `summary` type message, but this only happens via Path B's `persistTitle()`. When Path A (MCP) fails, Claude reports an error to the user even though the title was changed.

## Requirements (MoSCoW)

### Must Have
- MCP tool call `mcp__happy__change_title` must succeed without "endpoint connection error"
- Sidebar must update in real-time when title changes (metadata summary update must reach the app)
- Title change tool call must render as a visible tool block in the chat UI (not hidden)

### Should Have
- Remove the dual-path architecture: title should flow through ONE reliable path
- Error handling: if title persistence fails, the error should be clear and actionable

### Could Have
- Automatic title suggestion on first message (currently Claude decides when to call it)

### Won't Have (Non-Goals)
- Changing the title change UX (e.g., adding a title edit button in the sidebar)
- Changing how titles are stored in metadata
- Supporting title changes from the mobile app directly

## Edge Cases & Risks

- The STDIO bridge spawns as a child process of Claude SDK; if the bridge process crashes or fails to start, the tool is unavailable for the entire session
- Race condition: if metadata update fails due to version mismatch, the title persists via retry (backoff in `updateMetadata`), but the user may see a transient error
- The `recipientFilter: 'all-interested-in-session'` means the sidebar update only reaches clients that have the session's WebSocket room joined -- if the sidebar lists sessions via a different data path (e.g., REST fetch), it won't see the update until next fetch

## Acceptance Criteria

### AC1: MCP tool call succeeds
- GIVEN a running Claude session with the Happy MCP server
- WHEN Claude calls `mcp__happy__change_title` with a new title
- THEN the tool call returns success (not "endpoint connection error")

### AC2: Sidebar updates in real-time
- GIVEN the app is open with a session visible in the sidebar
- WHEN the title is changed via `mcp__happy__change_title`
- THEN the sidebar shows the new title within 2 seconds without manual refresh

### AC3: Tool call renders in chat
- GIVEN `mcp__happy__change_title` is called
- WHEN the message stream is rendered in the chat UI
- THEN the tool call appears as a tool block (icon + label card), not hidden

## Technical Hints

- Affected files:
  - `packages/happy-cli/src/codex/happyMcpStdioBridge.ts` -- STDIO-to-HTTP bridge that fails to connect
  - `packages/happy-cli/src/claude/utils/startHappyServer.ts` -- HTTP MCP server + internal handler
  - `packages/happy-cli/src/claude/runClaude.ts` -- Where MCP server is started and bridge is configured
  - `packages/happy-app/sources/components/tools/knownTools.tsx` -- Tool rendering config (already partially fixed)
  - `packages/happy-app/sources/sync/reducer/messageToEvent.ts` -- Currently converts title tool-call to event (may need adjustment)
  - `packages/happy-app/sources/sync/sync.ts:1900-1935` -- `update-session` handler that applies metadata changes
  - `packages/happy-app/sources/utils/sessionUtils.ts:80-82` -- `getSessionName()` reads `metadata.summary.text`
- Root cause of MCP failure: The STDIO bridge (`happyMcpStdioBridge.ts`) uses `StreamableHTTPClientTransport` to connect to the HTTP MCP server, but the connection fails. The bridge is spawned as a stdio child process by Claude SDK, and the HTTP server is on `127.0.0.1:<random-port>`. The bridge receives the URL via `--url` flag. The issue is likely that the bridge process fails to establish the HTTP connection (firewall, timing, or SDK incompatibility with the StreamableHTTP transport).
- Sidebar sync IS working: The server broadcasts `update-session` with metadata, the app's `sync.ts` decrypts and calls `applySessions()`, and `getSessionName()` reads `metadata.summary.text`. The problem is that when MCP fails, the title is still set via the internal handler but the sidebar update depends on the `update-metadata` WebSocket roundtrip which DOES work.
- The real question: Why does the STDIO bridge fail to connect to the HTTP MCP server? This needs investigation of the `StreamableHTTPClientTransport` + `StreamableHTTPServerTransport` interaction.
