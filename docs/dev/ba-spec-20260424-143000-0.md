# BA Specification: Markdown Primitives — Missing Block and Span Rendering (§5.17)

**Request ID**: dev-20260424-143000-0
**Created**: 2026-04-24T14:30:00Z

## Goal

Add rendering support for the seven markdown primitives that are currently absent from the custom parser-renderer pipeline (`parseMarkdownBlock.ts` / `parseMarkdownSpans.ts` / `MarkdownView.tsx`): strikethrough, task lists, nested lists (with depth), blockquotes (including nested), `<kbd>` HTML elements, and HTML entity decoding. Existing inline rendering (bold, italic, code, links) and all existing block types (headings, ordered lists, code blocks, tables, LaTeX, Mermaid) must not regress.

## Context

The happy-app uses a fully custom Markdown pipeline with no third-party parser (no `marked`, no `remark`). The pipeline was established in commit `7f178466` (Jan 2026) and has received incremental additions (LaTeX/Mermaid in `f8b208fa`, image blocks in `2cd19102`). None of the seven missing primitives were ever added to either the type system, the parser, or the renderer — they are new feature additions, not regressions.

The §5.16 BA is handling inline LaTeX (`$...$`), which shares the same `parseMarkdownSpans.ts` module. Both specs touch adjacent code but do not overlap: §5.17 adds new block types and span styles; §5.16 adds a new span type. Shared code path: `MarkdownView.tsx` (renderer), `parseMarkdownBlock.ts` (block parser), `parseMarkdownSpans.ts` (inline span parser). Coordinate merge order so the two specs do not conflict on `MarkdownSpan.styles` type.

## Edge Cases & Risks

- **`~~` inside code span**: The strikethrough regex must not fire inside backtick code spans. `parseMarkdownSpans` already processes code spans first via the `\`` capture group — ensure `~~` is processed after or uses a negative lookahead.
- **Task list vs plain list**: `- [x]` must be detected BEFORE the plain `- ` list branch. The parser currently checks `trimmed.startsWith('- ')` and collects all lines — task list detection must happen either inside the list collector or as a separate parser branch higher in the cascade.
- **Nested list depth tracking**: Requires passing the raw (untrimmed) line to measure leading whitespace before trimming. Current code trims first (`let trimmed = line.trim()`), losing depth information. The nested list branch must read indentation from `line` (not `trimmed`).
- **Blockquote continuation lines**: Multiple consecutive `> ` lines should be merged into one blockquote block (not one block per line). The parser must consume a run of `>` prefixed lines.
- **`&nbsp;` handling**: Non-breaking space entity may affect layout in React Native text — use a regular space or ` ` as the decoded value depending on platform behavior.
- **§5.16 shared code**: `MarkdownSpan.styles` type union is shared. Adding `strikethrough` here and `latex-inline` in §5.16 must not conflict. Coordinate: the type change is additive in both cases.
- **Production codebase parity**: Production `parseMarkdownSpans.ts` at `/root/happy` has identical span pattern — no blockquote/strikethrough there either. No production reference to port; this is entirely new feature development.

- GIVEN a markdown message with `- item A\n  - nested\n- item B`

### AC4: Blockquote renders with left border

### AC5: Nested blockquote renders with double indent

### Implementation guidance

**Strikethrough (parseMarkdownSpans.ts)**:
- Add `(~~(.*?)(?:~~|$))` to the regex pattern.
- In the match handler, push with `styles: ['strikethrough']`.
- In `MarkdownView.tsx` `style` sheet, add `strikethrough: { textDecorationLine: 'line-through' }`.

**Blockquote (parseMarkdownBlock.ts)**:
- Before the horizontal-rule check, add: if `trimmed.startsWith('> ')`, consume a run of `> ` prefixed lines; strip `> ` prefix from each; determine max depth from `>>` count; push `{ type: 'blockquote', depth: number, content: MarkdownBlock[] }` (recursive parse) OR `{ type: 'blockquote', depth: number, lines: MarkdownSpan[][] }` (flat, simpler).
- In `MarkdownView.tsx`, `RenderBlockquoteBlock`: `View` with `borderLeftWidth: 3`, `borderLeftColor: theme.colors.divider`, `paddingLeft: 12`, `backgroundColor: theme.colors.surfaceHigh`, `marginVertical: 4`.

**Task list (parseMarkdownBlock.ts)**:
- In the list collector, after extracting item content, check if content matches `/^\[([xX ])\]\s/`. If yes, push a `task-list` block instead of (or as a variant of) a `list` block.
- Simplest approach: add `type: 'task-list'` with `items: { checked: boolean, spans: MarkdownSpan[] }[]`.
- In `MarkdownView.tsx`, `RenderTaskListBlock`: render a row per item with a checkbox icon (`Ionicons checkmark-circle` vs `circle-outline`, or a simple `■`/`□` character) + spans.

**Nested lists (parseMarkdownBlock.ts)**:
- Measure indentation from the raw `line` (not `trimmed`) using `/^(\s*)[-*+]\s/`.
- Store depth (indentation / 2 or /4, clamped to int) per item.
- Update `MarkdownBlock` `list` type: `items: { depth: number, spans: MarkdownSpan[] }[]`.
- In `MarkdownView.tsx`, add `paddingLeft: item.depth * 16` per item row.

**HTML entities (parseMarkdownBlock.ts fallback OR parseMarkdownSpans.ts)**:
- After extracting plain text for the fallback `text` block (and in `pushTextWithAutoLinks`), apply a simple entity decode: `text.replace(/&lt;/g, '<').replace(/&gt;/g, '>').replace(/&amp;/g, '&').replace(/&quot;/g, '"').replace(/&#(\d+);/g, (_, n) => String.fromCharCode(Number(n)))`.
- This decode should run on ALL plain text (in `pushTextWithAutoLinks`), not only in the fallback branch.

**`<kbd>` (MarkdownView.tsx or parseMarkdownSpans.ts)**:
- Add `/<kbd>(.*?)<\/kbd>/g` detection in `parseMarkdownSpans.ts` pattern (or as a pre-pass).
- Render `<kbd>` spans with `fontFamily: Typography.mono()`, `borderWidth: 1`, `borderColor: theme.colors.divider`, `borderRadius: 3`, `paddingHorizontal: 4`, `backgroundColor: theme.colors.surfaceHigh`.
