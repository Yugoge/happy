# BA Specification: Enter Key Does Not Send Message in Web Input

**Request ID**: dev-20260403-210447-3
**Created**: 2026-04-03T21:04:47Z

## Goal

Fix the Enter key behavior in the message input field on web so that pressing Enter sends the message (when the user setting is enabled) instead of inserting a newline, and Shift+Enter inserts a newline.

## Context

The `MultiTextInput.tsx` component uses React Native's `submitBehavior="newline"` prop (line 222), which tells the native textarea to insert a newline on Enter keypress. On web, this native behavior fires **before** React's `onKeyPress` handler can call `preventDefault()`. The result: Enter always inserts a newline, and the `onKeyPress` handler's `e.preventDefault()` call on line 132 arrives too late -- the newline is already in the textarea.

Both `AgentInput.tsx` (session input) and `new/index.tsx` (new session composer) have Enter-to-send logic that reads the `agentInputEnterToSend` setting and calls `onSend()` when Enter is pressed without Shift. This logic works correctly in its callback, but the underlying `submitBehavior="newline"` defeats it by inserting the newline before the handler fires.

A prior PR (#854, commit `b94fbae2`) added a touch-device check to skip Enter interception on mobile web, which is correct. The current bug affects desktop web only.

## Requirements (MoSCoW)

### Must Have
- Enter key sends the message on desktop web when `agentInputEnterToSend` is `true`
- Shift+Enter inserts a newline on desktop web regardless of the setting
- When `agentInputEnterToSend` is `false`, Enter inserts a newline (current behavior preserved)
- Mobile web touch devices continue to use Enter for newline (PR #854 behavior preserved)
- Fix applies to both `AgentInput.tsx` (session view) and `new/index.tsx` (new session composer)

### Should Have
- No behavior change on native iOS/Android platforms
- The fix should use `onKeyDown` (DOM-level) instead of React Native's `onKeyPress` to intercept before the textarea processes the key

### Could Have
- Strip any trailing newline that was inserted by the native textarea before the handler fires (defensive cleanup)

### Won't Have (Non-Goals)
- Changes to the settings UI or settings.ts defaults
- Changes to mobile native keyboard behavior
- New keyboard shortcuts beyond Enter/Shift+Enter

## Edge Cases & Risks

- **Race condition**: On web, the browser's default textarea behavior (insert newline) may fire before any JS handler. The fix must use a DOM-level `keydown` event listener (not React Native's `onKeyPress`) to call `preventDefault()` before the newline is inserted.
- **IME composition**: Enter during IME composition (CJK input) should NOT send the message. Check `event.isComposing` or `event.keyCode === 229`.
- **Empty input**: Enter on empty input should not send (already handled in AgentInput.tsx line 525).
- **Platform detection**: `Platform.OS === 'web'` guard must remain. The fix is web-only.
- **submitBehavior prop**: Changing from `"newline"` to `"blurAndSubmit"` or removing it entirely may affect native platforms. The safest approach is to keep `submitBehavior="newline"` for native and add a web-specific `onKeyDown` handler via a `ref` on the underlying DOM element.

## Acceptance Criteria

### AC1: Enter sends message on desktop web
- GIVEN the user is on desktop web with `agentInputEnterToSend` enabled
- WHEN the user presses Enter in the message input with non-empty text
- THEN the message is sent and no newline is inserted

### AC2: Shift+Enter inserts newline on desktop web
- GIVEN the user is on desktop web with `agentInputEnterToSend` enabled
- WHEN the user presses Shift+Enter in the message input
- THEN a newline is inserted and no message is sent

### AC3: Setting disabled preserves newline behavior
- GIVEN the user is on desktop web with `agentInputEnterToSend` disabled
- WHEN the user presses Enter in the message input
- THEN a newline is inserted and no message is sent

### AC4: Mobile web touch devices unaffected
- GIVEN the user is on mobile web (touch device)
- WHEN the user presses Enter in the message input
- THEN a newline is inserted (send via button only)

### AC5: Native platforms unaffected
- GIVEN the user is on iOS or Android native
- WHEN the user presses Enter/Return on the keyboard
- THEN behavior is unchanged from current (newline inserted)

### AC6: IME composition respected
- GIVEN the user is composing CJK text via IME on desktop web
- WHEN the user presses Enter to confirm the IME composition
- THEN the composition is confirmed (not sent as a message)

### AC7: New session composer works identically
- GIVEN the user is on the new session screen on desktop web
- WHEN the user presses Enter with non-empty text and an online machine selected
- THEN the session is created and message sent

## Technical Hints

- Primary affected file: `packages/happy-app/sources/components/MultiTextInput.tsx:222` (submitBehavior prop)
- Key handling consumers: `packages/happy-app/sources/components/AgentInput.tsx:520-533`, `packages/happy-app/sources/app/(app)/new/index.tsx:871-879`
- Setting definition: `packages/happy-app/sources/sync/settings.ts:89`
- Recommended approach: In `MultiTextInput.tsx`, add a `useEffect` that attaches a DOM `keydown` listener to the underlying textarea element (via ref) on web platform. This listener fires before React's synthetic events and before the textarea's default behavior, allowing `preventDefault()` to block the newline insertion. Pass the key event up through the existing `onKeyPress` callback.
- Alternative approach: Change `submitBehavior` to `"blurAndSubmit"` on web only, using `Platform.select()`, and handle the submit event. However, this changes blur behavior which may have side effects.
- Related PR: #854 (commit `b94fbae2`) added `isTouchDevice` guard -- must be preserved.
