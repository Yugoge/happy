## Evidence (Contract A)

### Finding 1 (F1) — Split-target daemon kill (corrected from prior iteration)

- **Observed**: "stopDaemon() reads daemon.state.json and stops whatever PID is listed there, with no generation guard."
- **Measured**: `stopDaemon()` at `controlClient.ts:196-228` calls `readDaemonState()` at line 198 to capture `state.pid`. It then calls `stopDaemonHttp()` at line 208, which calls `daemonPost()` at line 88, which INDEPENDENTLY calls `readDaemonState()` at line 15 to get the HTTP port. The PID captured at line 198 and the port read by `daemonPost` at line 15 can belong to different daemon generations if `daemon.state.json` changes between those two reads.
- **Verified call order** (corrected — prior iteration had this wrong): `run.ts:119` calls `stopDaemon()` FIRST in the new daemon's startup sequence. `run.ts:664` calls `writeDaemonState()` LATER (after the control server starts and the new daemon writes its own state). Therefore at line 119, `daemon.state.json` still holds the OLD daemon's PID — self-kill via SIGKILL cannot occur at that point because the new daemon has not yet written its PID. The self-kill guard (`state.pid === process.pid`) remains valid as secondary defense for any future race where state.json is updated before `stopDaemon` reaches SIGKILL.
- **Expected**: `stopDaemon()` must read `daemon.state.json` ONCE into a `targetState` snapshot and use that snapshot for BOTH the HTTP stop (using `targetState.httpPort` directly, not via a helper that re-reads state) and the SIGKILL fallback (using `targetState.pid`).
- **Gap**: Two independent reads of `daemon.state.json` — `stopDaemon():198` and `daemonPost():15` — create a window where HTTP stop targets a different generation's port than SIGKILL targets.

### Finding 2 (F2) — Lock double-unlink race (corrected scope — both sites)

- **Observed**: "cleanupDaemonState() is called before releaseDaemonLock(). But cleanupDaemonState() internally deletes the lock file path."
- **Measured** (both sites verified):
  - `run.ts:763-766` (heartbeat upgrade handoff): `cleanupDaemonState()` at line 765, `releaseDaemonLock(daemonLockHandle)` at line 766 — WRONG ORDER (missed in prior BA iteration)
  - `run.ts:831-835` (cleanupAndShutdown): `cleanupDaemonState()` at line 833, `releaseDaemonLock(daemonLockHandle)` at line 835 — WRONG ORDER (identified in prior iteration)
  - `persistence.ts:321-333`: `clearDaemonState()` deletes BOTH `daemonStateFile` (line 323) AND `daemonLockFile` (lines 326-332)
  - `persistence.ts:386-396`: `releaseDaemonLock()` also calls `unlinkSync(daemonLockFile)` — two functions both attempt to delete the same file
- **Expected**: Lock lifecycle owned exclusively by `acquireDaemonLock/releaseDaemonLock`. `clearDaemonState()` must delete ONLY `daemonStateFile`. Both owned-shutdown sites must call `releaseDaemonLock()` BEFORE `cleanupDaemonState()`.
- **Gap**: `clearDaemonState()` deletes the lock file it does not own (`persistence.ts:326-332`), creating a TOCTOU race at both shutdown sites.

### Finding 3 (F3) — Zero-daemon on spawn failure (corrected AC)

- **Observed**: "if spawnHappyCLI() throws during the upgrade handoff, the catch block only logs and then process.exit(0) still executes."
- **Measured**: `run.ts:757`: `clearInterval(restartOnStaleVersionAndHeartbeat)` called BEFORE the try block. `run.ts:763-767`: full teardown runs BEFORE `spawnHappyCLI` — `apiMachine.shutdown()`, `stopControlServer()`, `cleanupDaemonState()`, `releaseDaemonLock()`, `stopCaffeinate()`. `run.ts:769-779`: `spawnHappyCLI` inside try block, catch at 774-776 only logs, `process.exit(0)` at line 778 is OUTSIDE the try block.
- **Post-spawn-failure daemon state**: no WebSocket connection, no control server, no state file, no lock file, no heartbeat interval. A daemon that does not exit has NO control path — it is a zombie process. `process.exit(1)` (failure exit code) is the correct behavior so that process supervisors (e.g., systemd `Restart=on-failure`) can respawn.
- **Expected**: `process.exit(0)` moved INSIDE the try block after successful spawn. Catch block calls `process.exit(1)` with a FATAL log. Daemon does NOT continue in degraded state.
- **Gap**: `process.exit(0)` at line 778 is unconditional; spawn failure exits with code 0 (success), suppressing supervisor respawn signal.

## Edge Cases & Risks

1. **F1 call order**: `run.ts:119` calls `stopDaemon()` BEFORE `run.ts:664` writes the new daemon's PID. Self-kill via SIGKILL at startup cannot occur. The self-kill guard (`targetState.pid === process.pid`) is a secondary defense for any future scenario where state.json is updated before `stopDaemon` reaches SIGKILL.
2. **F1 HTTP stop inlining**: `stopDaemonHttp()` calls `daemonPost('/stop')` which re-reads state. Inlining the `fetch` call in `stopDaemon()` with `targetState.httpPort` eliminates the re-read. Dev should prefer the smallest change — inlining the fetch call is the simplest approach.
3. **F1 old daemon already dead**: If old daemon already exited, `readDaemonState()` returns null — `stopDaemon` returns early. Already handled at line 199.
4. **F2 clearDaemonState stale lock cleanup**: The comment at `persistence.ts:325` says "for stale cleanup." This path is already covered by `acquireDaemonLock`'s retry loop (which removes stale locks at line 364). Removing the lock deletion from `clearDaemonState()` is safe.
5. **F2 releaseDaemonLock ENOENT**: `releaseDaemonLock()` already uses `catch {}` — ENOENT is silently swallowed. No change needed. Confirm behavior.
6. **F3 no continuation path**: After spawn failure, WebSocket, control server, state file, lock file, and heartbeat interval are ALL torn down. There is no safe continuation path. `process.exit(1)` is the only correct action. The FATAL log before exit provides operator visibility.
7. **F3 systemd dependency**: `process.exit(1)` triggers respawn only when the supervisor has `Restart=on-failure` (or equivalent). The AC requires exit code 1 only — it does not mandate supervisor configuration.

## Acceptance Criteria

### AC1: F1 — Single snapshot; self-kill guard
- GIVEN `daemon.state.json` contains the current process's own PID at the time `stopDaemon()` reads it
- WHEN `stopDaemon()` processes the captured targetState
- THEN it logs a warning and returns without sending HTTP stop or SIGKILL to self

### AC2: F1 — Single snapshot used for both stop operations
- GIVEN `daemon.state.json` contains a valid daemon entry with a different PID from current process
- WHEN `stopDaemon()` is called
- THEN `daemon.state.json` is read exactly once; the resulting `targetState.httpPort` is used for the HTTP stop request; `targetState.pid` is used for SIGKILL fallback; no intermediate helper re-reads `daemon.state.json`

### AC3: F2 — clearDaemonState does not touch lock file
- GIVEN `clearDaemonState()` is called
- WHEN it executes
- THEN only `daemonStateFile` is deleted; `daemonLockFile` is NOT touched by this function

### AC4: F2 — Lock released before state cleanup in heartbeat handoff
- GIVEN the daemon is executing the heartbeat upgrade handoff block (run.ts approx lines 763-766)
- WHEN the cleanup sequence executes
- THEN `releaseDaemonLock(daemonLockHandle)` is called BEFORE `cleanupDaemonState()`

### AC5: F2 — Lock released before state cleanup in cleanupAndShutdown
- GIVEN the daemon is shutting down via `cleanupAndShutdown()` (run.ts approx lines 831-835)
- WHEN the cleanup sequence executes
- THEN `releaseDaemonLock(daemonLockHandle)` is called BEFORE `cleanupDaemonState()`

### AC6: F3 — process.exit(1) on spawn failure
- GIVEN `spawnHappyCLI()` throws during the upgrade handoff
- WHEN the catch block executes
- THEN `process.exit(1)` is called (not 0, not omitted); a FATAL log message is emitted before exit; `process.exit(0)` is NOT present in the catch block

### AC7: F3 — successful spawn exits cleanly with code 0
- GIVEN `spawnHappyCLI()` succeeds during the upgrade handoff
- WHEN execution continues after the spawn call
- THEN `process.exit(0)` is called (daemon exits cleanly to let new daemon take over)

### AC8: Sentinel file — PAUSE-PENDING-USER
- GIVEN `.claude/.hook-refactor-allow` exists at project root
- WHEN dev subagent reaches this task
- THEN dev subagent stops and outputs a REQUEST asking the user to manually delete the sentinel file; dev subagent does NOT attempt deletion itself via rm, python3, node, or any other interpreter

### AC9: deploy.sh URL (MANUAL USER ACTION — not implementable by subagent)
- GIVEN `/root/happy/scripts/deploy.sh` web-dev case uses `https://api.life-ai.app`
- WHEN user edits `/root/happy/scripts/deploy.sh`
- THEN `HAPPY_SERVER_URL=https://api-dev.life-ai.app` in the web-dev case
