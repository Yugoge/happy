### Critical Finding: Codex App-Server Event Surface (OBJ-1 correction — inferred wrong, now observed correct)

Investigation of `codexAppServerClient.ts` lines 280–364 (observed: Read of actual source) reveals the
Codex app-server client translates `item/started` + `item/completed` JSON-RPC notifications into EventMsg
types for **only 3 item.type values**:

| Codex item.type | EventMsg emitted |
|-----------------|-----------------|
| `commandExecution` (item/started) | `exec_command_begin` |
| `commandExecution` (item/completed) | `exec_command_end` |
| `fileChange` (item/started) | `patch_apply_begin` |
| `fileChange` (item/completed) | `patch_apply_end` |
| `agentMessage` (item/completed) | `agent_message` |
| **any other item.type** | silently consumed — `return method.startsWith('item/')` at line 364; **zero EventMsg** |

The previous BA spec's hypothesis that tools `write_stdin`, `update_plan`, `request_user_input` etc. arrive
as `write_stdin_begin` / `update_plan_begin` events was **factually wrong** — those event names never appear
in the event stream. `codexAppServerClient.test.ts` confirms only `commandExecution`, `fileChange`,
`agentMessage` appear in test fixtures. Adding mapper branches for non-existent events would be dead code.

### CodexPatch extractDescription Reference

```typescript
// Suggested extractDescription for CodexPatch knownTools entry
extractDescription: (opts) => {
    const changes = (opts.args as any)?.changes;
    if (!changes || typeof changes !== 'object') {
        return t('tools.names.applyPatch');
    }
    const files = Object.keys(changes);
    const n = files.length;
    if (n === 0) return t('tools.names.applyPatch');
    const names = files.slice(0, 3).map((f: string) => f.split('/').pop() ?? f).join(', ');
    return n <= 3 ? `Edit ${n} file${n > 1 ? 's' : ''}: ${names}` : `Edit ${n} files: ${names}, ...`;
},
```
