# Ticket — Happy recovery debt cleanup and targeted OOM protection

## Goal
Fix the previously introduced recovery debts so manually restored Happy sessions are not misleadingly treated as durable daemon state, user-stopped/archived sessions are not resurrected, restore-in-progress does not trigger false recovery, and OOM protection targets runaway session process groups instead of taking down the server.

## Requirements
1. Recovery must not claim a session is restored unless the live daemon can track it or the action is explicitly reported as an external/non-daemon restore.
2. Live watcher must not restore stable low-count states as if they were failures.
3. Runtime watcher must not use peak snapshot as a permanent desired count.
4. Restore-in-progress must suppress fast-detect loss handling.
5. Manual stop/archive intent must be represented by a durable skip mechanism that recovery respects.
6. OOM protection must prefer targeted session/process-group termination and audit logging.
7. Do not add or rely on a coarse MemoryMax limit for the whole happy daemon.
8. Do not remove Codex.

## Evidence
- `docs/dev/evidence-20260523-235421-happy-recovery-debt.txt` shows most recovered session processes have parent PID 1 while only three are daemon children.
- `/root/happy/packages/happy-cli/dist/index-WGnVoqay.mjs` writes daemon snapshots from `pidToTrackedSession` only.
- `/root/bin/happy-session-recovery.sh` currently spawns recovery sessions externally and contains stable-loss recovery logic.
- Recovery logs show fast-detect firing during active restore.

## Acceptance Criteria
1. Stable low-count live watcher states abort rather than auto-restore.
2. Runtime watcher never uses peak snapshot merely because current saved count is below peak; peak snapshots are only for cold boot/disaster mode.
3. A restore-in-progress marker prevents watcher fast-detect from triggering during recovery.
4. Recovery respects a durable tombstone/skip list for manually stopped or archived sessions.
5. Recovery report distinguishes daemon-tracked restore from external/non-daemon restore and does not overclaim.
6. Emergency memory guard has an explicit targeted-session action path and is protected enough to act under memory pressure.
7. No change imposes a coarse memory limit on the whole happy daemon.
8. QA can verify behavior with static/script checks without rebooting or killing live sessions.

## Out of Scope
- Rebooting the server.
- Killing or restarting live happy daemons/sessions during this cycle.
- Removing Codex.
- Whole-daemon MemoryMax caps.
