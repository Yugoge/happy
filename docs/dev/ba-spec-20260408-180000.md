# BA Specification: Session Archive Cascade Root Cause Analysis (2026-04-08 Morning Incident)

**Request ID**: dev-20260408-180000
**Created**: 2026-04-08T18:00:00Z

## Goal

Determine who killed session processes on 2026-04-08 at ~09:05 UTC when the user archived a session, and why the same action at ~17:50 UTC did NOT kill processes.

## Context

At 09:04:32 UTC, the user archived session `1140deaf` (PID 289607, running in `/dev/shm/dev-workspace/applio`). This triggered a cascade that killed and respawned ALL sessions across all daemons (default, jade, dev). At ~17:50 UTC, the user archived another session and no cascade occurred -- 39 processes before, 39 after.

## Root Cause Analysis: Complete Timeline

### 09:04:32.874 -- The App Sent `killSession` RPC

The app's "Archive Session" action (`ActiveSessionsGroup.tsx:347-352` and `info.tsx:155`) calls `sessionKill(session.id)` which sends a `killSession` RPC through the server WebSocket to the CLI session process.

**Evidence** (from `/root/.happy/logs/2026-04-08-07-40-36-pid-289607.log`):
```
[09:04:32.874] [RPC] Calling handler {"method":"cmnpqnr9e124rt615ig4jwdw1:killSession"}
[09:04:32.875] Kill session request received
[09:04:32.875] [START] Received termination signal, cleaning up...
[09:04:32.882] [START] Cleanup complete, exiting
```

The `killSession` handler (`registerKillSessionHandler.ts:18`) calls `killThisHappy()` which cleanly shuts down the happy-cli process. **This is the intended behavior -- archive = kill process.**

### 09:05:26.388 -- Daemon Detected the Dead Process

The daemon's health check loop found PID 289607 no longer running:
```
[09:05:26.388] [DAEMON RUN] Removing stale session with PID 289607 (process no longer exists)
```

The daemon removed the session from its tracking, which caused `session_dirs.txt` to shrink by 1 entry.

### 09:05:26 -- Session Watcher Detected the Change and Triggered Cascade

The session watcher (OLD code, before today's fix) saw one session disappear:
```
[09:05:26] Change detected: 14 sessions (+0 -1)
[09:05:26] Sessions disappeared (1 removed), triggering auto-restore...
```

The OLD watcher behavior on ANY session disappearance was:
1. Read `session_dirs.txt` to get the list of sessions that SHOULD exist
2. Kill ALL existing processes as "orphans" (blanket kill)
3. Re-spawn ALL sessions from scratch

**Evidence of the blanket kill**:
```
[09:05:40] Killed orphaned process for 09b4ed09-... (home=/root/.happy)
[09:05:40] Killed orphaned process for 76f187c1-... (home=/root/.happy)
[09:05:41] Killed orphaned process for 817e8407-... (home=/root/.happy)
[09:05:41] Killed orphaned process for 8e46a63b-... (home=/root/.happy)
[09:05:42] Killed orphaned process for d47a0726-... (home=/root/.happy)
[09:05:42] Killed orphaned process for ed24aacd-... (home=/root/.happy)
```

Then it respawned 10 sessions for `/root/.happy`, 3 for `/root/.happy-jade`, 1 for `/root/.happy-dev`.

### 09:06:44 -- Secondary Cascade

While the first restore was still running, the jade daemon's sessions were being killed. The watcher detected MORE disappearances:
```
[09:06:44] Change detected: 12 sessions (+0 -2)
[09:06:44] Sessions disappeared (2 removed), triggering auto-restore...
[09:06:44] Restore already running (pid 4895), skipping
```

Fortunately the lock prevented a second concurrent restore.

### 09:09:11 -- THIRD Cascade

Another session died during the respawn chaos:
```
[09:09:11] Change detected: 13 sessions (+0 -1)
[09:09:11] Sessions disappeared (1 removed), triggering auto-restore...
```

This triggered ANOTHER full kill-and-respawn cycle.

## Why 17:50 Archive Did NOT Cascade

The session watcher code was fixed earlier today (Bug #61 fix). The new watcher no longer treats a single session disappearance as a reason to kill all sessions and do a full restore. It recognizes that a single session dying (e.g., from user archive) is normal and does not trigger the blanket orphan-kill + mass-respawn behavior.
