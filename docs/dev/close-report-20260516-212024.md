### Style Inspector Critical Violation — AC-2.6 Evaluation

**Finding**: `python3 -` invocation at `docs/dev/patches/write_json_snapshot-20260516-212024.sh:98` without `source venv/bin/activate`.

**Evaluation against AC-2.6**:
- The `use-source-venv` standard was designed for project scripts that invoke project-level Python tools with pip dependencies.
- The patch script is a one-shot delivery artifact in `docs/dev/patches/` (not `scripts/`), not a persistent utility.
- No project venv exists at `/root/bin/` or `docs/dev/patches/` — there is no venv to activate.
- The `python3` invocation uses only stdlib (`sys`, `os`) — no pip dependencies.
- Both `/root/bin` and `/dev/shm/dev-workspace/happy-dev` lack a venv applicable to this script.
- The style inspector's own `recommendation` acknowledges: "This patch script is a one-shot utility with no project venv; if the standard is to be observed literally, add a note... or restructure to avoid inline Python."
- This is a misapplication of the `use-source-venv` rule to an artifact type (patch delivery script using stdlib-only Python) that the rule was not designed to cover.

**Disposition**: The `use-source-venv` critical violation does NOT force `CLOSE: NO`. The violation is inapplicable to this artifact type. The style inspector's severity designation of "critical" for a stdlib-only script with no applicable venv is a false alarm under AC-2.6 analysis.

### Codex Feedback

**FINDING 1** (PROPOSED_FIX provided — in scope):
- **Issue**: The Python apply script creates the temp file with default mode (typically 644) and uses `os.rename` to atomically replace the target. Target `/root/bin/happy-session-recovery.sh` has permissions `755`. After apply, the file would lose its executable bit (becomes 644).
- **Evidence**: `stat -c '%a %U:%G %n' /root/bin/happy-session-recovery.sh` returns `755 root:root`. Python `open(tmpfile, 'w')` creates file at default umask (e.g., 644), and `os.rename` replaces the target with the new file, losing original permissions.
- **Impact**: `/root/bin/happy-session-recovery.sh` would no longer be directly executable after patch application. Users invoking `bash /root/bin/happy-session-recovery.sh` would still work (bash doesn't require x-bit on target for `bash <file>` invocation), but direct invocation `./happy-session-recovery.sh` or systemd-triggered invocations that use the path without explicit `bash` prefix would fail.
- **PROPOSED_FIX**: Preserve target metadata in the Python apply section:
  ```python
  st = os.stat(target)
  tmpfile = target + ".patch-tmp"
  with open(tmpfile, "w") as f:
      f.write(new_content)
  os.chmod(tmpfile, st.st_mode & 0o7777)
  os.chown(tmpfile, st.st_uid, st.st_gid)
  os.replace(tmpfile, target)
  ```

**FINDING 2** (PROPOSED_FIX provided — minor):
- **Issue**: Line 8 of the patch script comment says `python3 docs/dev/patches/write_json_snapshot-20260516-212024.sh --apply`, but the file is a bash script. Running `python3` on it would fail.
- **Impact**: Documentation error in usage comment; does not affect functionality (the correct `bash $0 --apply` invocation is properly handled in the main section at line 204).
- **PROPOSED_FIX**: Change line 8 to `bash docs/dev/patches/write_json_snapshot-20260516-212024.sh --apply`.

**FINDING 3** (PROPOSED_FIX provided — minor):
- **Issue**: The comment at lines 39-91 says "EXACT replacement text" but uses Unicode arrows `→`, while the Python `AFTER` string uses ASCII `->`.
- **Impact**: Documentation-only discrepancy; the Python `AFTER` string is what the apply script actually uses, so automated application is unaffected. Manual application from the comment could produce slightly different text.
- **PROPOSED_FIX**: Remove "EXACT" from the comment heading and replace with "illustrative", or update comment to use ASCII `->`.

## Round 1b': Findings Classification and Disposition

### Finding 1 (Permission Stripping) — Assessment

**Classification**: `in_scope_defect` — real bug in the patch delivery artifact.

**Severity evaluation**:
- The permission bug affects the delivery mechanism, not the feature logic (AC1-AC5).
- After user applies the patch (even with wrong permissions), the bash logic inside is correct; AC1-AC5 would all pass.
- `/root/bin/happy-session-recovery.sh` is invoked in the systemd service file and by `bash /root/bin/...` — if the invocation always uses explicit `bash` prefix, the x-bit loss is survivable.
- However, losing the 755 bit on a critical operational script is a meaningful regression. The systemd ExecStart may use direct invocation.

**Critical question**: Does the permission stripping prevent AC1-AC5 from being achieved?
- AC1-AC5 test the bash logic correctness of `write_json_snapshot` AFTER code, not the apply mechanism.
- Even with 644 permissions, `bash docs/dev/patches/write_json_snapshot-20260516-212024.sh --apply` still works (bash doesn't need x-bit on the called script).
- The applied logic would produce correct output for AC1-AC5.

**However**: The permission bug is a real operational defect that the user must be aware of and address (either via the PROPOSED_FIX or a manual `chmod 755` after apply). The close report must document this.

**Disposition**: Finding 1 does not block CLOSE for AC1-AC5, but it is a known defect in the patch delivery artifact that requires user action after applying. Documented below.
