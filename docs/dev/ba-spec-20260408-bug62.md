## Detailed Fix Plan

### ISSUE #1: Partial crash permanently loses sessions

**Root Cause**: Line 409 changed peak merge trigger from `count < prev_count` to `count == 0`. This means if OOM kills 3 of 10 sessions (count 10 -> 7), peak merge does NOT trigger. The 7-session scan overwrites `session_dirs.txt`, and the 3 dead sessions are permanently lost.

**Affected Code**: `update_snapshot_with_peak_protection()` (lines 402-437)

**The old behavior** (`count < prev_count`) resurrected archived sessions because any drop triggered merge with the peak, which contained sessions the user had intentionally removed.

**Fix Design -- Tombstone-based approach**:

The fundamental problem is distinguishing "session disappeared because it crashed" from "session disappeared because user archived it / it exited naturally". The solution is to track intentional removals via a tombstone file.

1. Add a tombstone mechanism: when the watcher detects a session disappearing AND the daemon's `/list` endpoint confirms it was intentionally ended (not in the daemon's child list AND daemon is running), record the UUID in a tombstone file (`~/.happy*/session_tombstones.txt`).
2. On peak merge, filter out tombstoned UUIDs before merging.
3. Tombstones expire after `PEAK_PROTECT_SECONDS` (8 hours) -- same window as peak snapshots.

**Alternative simpler fix** (recommended): Change peak merge to trigger on ANY count drop (restore the `count < prev_count` check), but filter the peak sessions through the tombstone list. This way:
- Crash (OOM kills 3 of 10): count drops 10->7, peak merge fires, restores the 3 crashed sessions (not tombstoned)
- Archive (user removes 1 of 10): count drops 10->9, peak merge fires, BUT the archived session is in tombstones, so it gets filtered out
- Natural exit: same as archive -- daemon notifies session end, tombstone is written

**Tombstone lifecycle**:
- Written by: `compute_and_record_diff()` when a "remove" event is detected AND the session is NOT in any daemon's `/list` (meaning it was intentionally ended, not crashed)
- Actually, simpler: write tombstones for ALL remove events. On crash, the sessions won't have a remove event before the next scan because they just died -- the watcher will detect them missing. The key insight: if a session disappeared AND we recorded a "remove" event for it in a previous poll cycle, it was intentional. If it disappeared between two consecutive polls without a prior "remove" event... that's still detected as a remove.

**Even simpler approach (recommended)**: Track "removed UUIDs" in a rolling window. The `compute_and_record_diff()` function already records remove events in the JSONL history. On peak merge:
1. Read recent remove events from JSONL (last `PEAK_PROTECT_SECONDS`)
2. Check if each removed session's process is truly dead (not in `/proc`)
3. If process is dead AND there's no remove event with a daemon confirmation... this doesn't work cleanly.

**RECOMMENDED FIX**: Use the daemon `/list` endpoint at merge time to distinguish crash from intentional exit:
1. Restore `count < prev_count` trigger (merge on any drop)
2. When merging, for each peak session NOT in the current scan:
   - Check if ANY daemon is running for its home
   - If daemon is running and session is NOT in daemon's `/list`: it was intentionally ended -> skip (don't resurrect)
   - If daemon is NOT running (crash/restart scenario): include in merge (preserve for restore)
   - If no daemon can be reached: include in merge (safe default -- preserve)
3. This is the authoritative check: the daemon knows which sessions it manages.

**Edge Cases**:
- All daemons crash simultaneously: all sessions included in merge (correct: preserve everything)
- Single daemon restarts: its sessions preserved, other daemons' sessions filtered correctly
- User archives session then daemon crashes before next poll: session is in daemon's memory as ended, but daemon is now dead. Daemon `/list` is unreachable, so session gets included in merge. This is acceptable -- the session will be spawned, discover it's archived, and exit gracefully.

### ISSUE #3: `find_peak_snapshot()` only checks first home

**Root Cause**: Line 390 has `break  # only check first home`. With per-home snapshots (introduced in the Bug #62 initial fix), each home has its OWN snapshots directory with only its sessions. The function must search the correct home.

**Affected Code**: `find_peak_snapshot()` (lines 369-396)

**Fix**:
1. Accept an optional `$1` parameter for target home (defaults to searching all homes)
2. When `SCOPE_HOME` is set, only search `$SCOPE_HOME/$SNAPSHOT_DIR`

4. When searching all homes, find peak across all homes (for global watcher mode)

**Note**: Since snapshots are now per-home filtered, searching the correct home's directory naturally returns only that home's sessions. The `break` was a leftover from when all snapshots were global.

### ISSUE #4: `read_snapshot_count()` reads wrong home

### ISSUE #5: Qijie sessions have `home_dir=""` -- misassigned to default

**Root Cause**: In `scan_running_sessions()`, lines 58-62 set `home_dir_val=""` for the default daemon (`/root/.happy`). But when a qijie session's PID is not tracked by any daemon's `/list` endpoint (e.g., daemon just restarted), the fallback env var check (line 97) returns the HAPPY_HOME_DIR from the process environment. However, the qijie daemon uses `HAPPY_HOME_DIR=/root/.happy-qijie`, so this should work... unless the process doesn't have that env var set.

**Deeper analysis**: The real problem is in `filter_sessions_for_home()` (line 189): `local effective_home="${home_dir:-/root/.happy}"`. If `home_dir` is empty string `""`, this evaluates to `/root/.happy` (bash `${var:-default}` triggers on empty string). But for qijie processes, `home_dir` should be `/root/.happy-qijie`. The issue is:
1. Daemon `/list` for qijie sets `home_dir_val="/root/.happy-qijie"` (correct)
2. But if qijie daemon is down or slow, the PID won't be in `pid_to_home`
3. The env var fallback reads `HAPPY_HOME_DIR=/root/.happy-qijie` from `/proc/$pid/environ` (should work)
4. BUT if qijie daemon IS up and the PID IS in its `/list`, then `pid_to_home[$pid]="/root/.happy-qijie"` (correct)

The actual bug path: qijie daemon is running but its `/list` endpoint doesn't include a particular session PID (e.g., session was spawned by recovery script via `systemd-run`, and the daemon doesn't track it via `/list`). Then `pid_to_home` has entries (from other daemons), so the orphan filter on line 99-101 kicks in and SKIPS the session entirely. This means qijie sessions spawned by recovery are invisible to the scanner.

**Alternative bug path**: In `write_json_snapshot()` per-home filtering (line 316-319), the jq filter uses `(.home_dir == "" or .home_dir == null)` for default. If a qijie session somehow gets `home_dir=""`, it would be assigned to default's snapshot. Then restore reads default's snapshot and tries to spawn it on default daemon -- wrong home.

**Fix**: Multiple layers:
1. In `daemon_spawn_session()`, ensure spawned processes have `HAPPY_HOME_DIR` set explicitly in their environment (already done via `spawn_env="HAPPY_HOME_DIR=$home"` on line 708 -- verify this propagates through `systemd-run`)
2. In `systemd-run` spawn (line 730-738), verify `-E HAPPY_HOME_DIR="$home"` is present (it is on line 733)
3. In `filter_sessions_for_home()`, use `${home_dir:-}` (no default) and explicitly check: if `home_dir` is empty AND `target_home` is `/root/.happy`, match. Otherwise, only match if `home_dir == target_home`. This is what it already does... but the `:-` syntax with a default of `/root/.happy` means empty strings always map to default.
4. **The real fix**: Change the default daemon convention. Instead of using empty string for default, use the explicit path `/root/.happy`. This eliminates all ambiguity.

**Recommended fix**:
- In `scan_running_sessions()` line 59: change `home_dir_val=""` to `home_dir_val="/root/.happy"`
- In `filter_sessions_for_home()` line 189: change `local effective_home="${home_dir:-/root/.happy}"` to `local effective_home="$home_dir"` (no default needed since we always set explicit path)
- In `write_json_snapshot()` jq filter: remove the `or .home_dir == "" or .home_dir == null` special case for default
- In all places that check `home_dir` against `/root/.happy`: remove the empty-string-means-default convention
- **Backward compatibility**: When reading old snapshots/session_dirs.txt that have `home_dir=""`, treat as `/root/.happy` during migration

### ISSUE #6: Race between watcher restore and ExecStartPost --kill-orphans

**Root Cause**: Timeline:
1. Daemon restarts (ExecStop kills daemon + sessions)
2. Watcher poll (every 60s) detects sessions disappeared, triggers `restore_online_sessions` (no --kill-orphans)
3. Watcher's restore spawns sessions
4. ExecStartPost fires ~10s after ExecStart, runs `restore --home $HOME --kill-orphans`
5. ExecStartPost kills the sessions watcher just spawned (they're "orphans" from its perspective -- not in new daemon's /list yet)
6. ExecStartPost re-spawns them

**Fix**: Use the existing `RESTORE_LOCK_DIR` mutex more effectively:
1. ExecStartPost writes a "restore pending" marker file BEFORE sleeping 8s: `/tmp/happy-restore-pending-$HOME_HASH`
2. Watcher checks for this marker before triggering auto-restore for a specific home
3. If marker exists and is < 30s old, watcher skips restore for that home (ExecStartPost will handle it)
4. ExecStartPost removes marker after restore completes

**Alternative simpler fix** (recommended): ExecStartPost already sleeps 8 seconds. The watcher polls every 60 seconds. The race window is when the watcher's poll happens to land in those 8 seconds. Fix:
1. ExecStartPost creates `/tmp/happy-restore-active-$HOME` immediately (before sleep)
2. Watcher's auto-restore checks for this file; if present and < 60s old, skip
3. ExecStartPost removes the file after restore completes

## Edge Cases & Risks

- **OOM kills subset of sessions**: Must preserve killed sessions in snapshot. ISSUE #1 fix handles this via daemon `/list` check.
- **Multiple daemons restart simultaneously**: Each daemon's ExecStartPost scopes to its own home. Lock prevents concurrent restores.
- **Watcher restarts**: Watcher is stateless on startup -- reads session_dirs.txt and rescans. No data loss.
- **Stale tombstone/marker files**: All marker files are timestamped and expire within minutes. `RESTORE_LOCK_DIR` has stale-lock detection.
- **Backward compatibility with old snapshots**: Old snapshots have `home_dir=""` for default. Must handle during read.

## Acceptance Criteria

### AC1: Partial crash preserves sessions
- GIVEN 10 sessions running on default daemon
- WHEN OOM kills 3 sessions (count drops 10 -> 7)
- THEN next watcher poll detects 7 running, peak merges the 3 missing ones back, session_dirs.txt has 10 entries, auto-restore spawns the 3 missing sessions

### AC2: Archive does not resurrect
- GIVEN 10 sessions running, user archives 1 (daemon removes it from /list)
- WHEN next watcher poll detects 9 running
- THEN peak merge checks daemon /list, finds the archived session is not a crash victim, does NOT resurrect it. session_dirs.txt has 9 entries.

### AC3: No bash syntax errors
- GIVEN the script is invoked with `restore --home /root/.happy --kill-orphans`
- WHEN bash parses the case block
- THEN no errors about `local` outside function

### AC4: Per-home peak works for non-default daemons
- GIVEN jade daemon has 5 sessions, snapshots in `/root/.happy-jade/session_backup_history/`
- WHEN jade daemon restarts and count drops to 0
- THEN `find_peak_snapshot()` finds jade's peak snapshot (not default's), restore uses jade's sessions

### AC5: Qijie sessions assigned correctly
- GIVEN qijie daemon is running with 2 sessions
- WHEN watcher scans running sessions
- THEN qijie sessions have `home_dir="/root/.happy-qijie"` (not empty string), appear in qijie's snapshot, NOT in default's snapshot

### AC6: No double-restore race
- GIVEN daemon is restarting, watcher is running
- WHEN ExecStartPost creates restore-active marker
- THEN watcher skips auto-restore for that home until marker expires, only ExecStartPost's restore runs
