# BA Specification: find_peak_snapshot break-after-first-home is a no-op bug

**Request ID**: dev-20260408-161500
**Created**: 2026-04-08T16:15:00+00:00

## Goal

Investigate why jade and dev daemons work fine despite `find_peak_snapshot()` breaking after checking only the first home directory. Document the root cause and determine whether the `break` is a latent bug or intentional.

## Context

`find_peak_snapshot()` in `/root/bin/happy-session-recovery.sh` (line 372) has a `break` statement that exits the `for home in HAPPY_HOMES` loop after processing the first home (`/root/.happy`). This means it never checks snapshot directories under `/root/.happy-jade`, `/root/.happy-dev`, or `/root/.happy-qijie`.

Despite this, jade and dev daemons have been running without issue.

## Root Cause Analysis

### Why jade/dev work fine: snapshots are GLOBAL, not per-home

The answer is in `write_json_snapshot()` (lines 309-314):

```bash
for home in "${HAPPY_HOMES[@]}"; do
    [ -d "$home" ] || continue
    local dir="$home/$SNAPSHOT_DIR"
    mkdir -p "$dir"
    echo "$json" | jq '.' > "$dir/$ts.json" 2>/dev/null || echo "$json" > "$dir/$ts.json"
done
```

**Every snapshot is written identically to ALL home directories.** The JSON includes sessions from ALL daemons (with `home_dir` field distinguishing them). This means:

- `/root/.happy/session_backup_history/2026-04-08-16-11.json` contains 18 sessions (default + jade + dev + qijie)
- `/root/.happy-jade/session_backup_history/2026-04-08-16-11.json` contains the **exact same** 18 sessions

Verified: `diff` of the latest snapshots between default and jade produces zero differences.

Since `find_peak_snapshot()` finds the peak by `session_count` (which is global across all homes), and the snapshot content is identical in every home directory, checking only `/root/.happy/` returns the same result as checking all homes. The `break` is a performance shortcut that happens to be correct -- but only by accident.

### The break IS still a latent bug

The `break` is still problematic because:

1. **Fragile assumption**: If `write_json_snapshot` is ever changed to write per-home snapshots, `find_peak_snapshot` silently breaks for non-default homes.
2. **Stale/missing snapshots**: If `/root/.happy/session_backup_history/` is manually cleaned or corrupted, the function returns nothing even though valid snapshots exist in jade/dev/qijie homes.
3. **Comment says "only check first home"**: This was clearly intentional as an optimization, but it encodes a hidden coupling to the global-write behavior.

## Requirements (MoSCoW)

### Must Have
- Remove the `break` on line 372 so `find_peak_snapshot()` checks all homes
- This is a one-line deletion with zero risk

### Should Have
- Add a comment explaining that snapshots are global (written to all homes identically) so future readers understand why checking one home currently suffices

### Won't Have (Non-Goals)
- Changing `write_json_snapshot` to per-home snapshots (separate investigation)
- Refactoring the snapshot system

## Edge Cases & Risks

- **Zero risk**: Removing the `break` makes the function iterate all homes, finding the same peak. At worst it checks 3 extra directories (microseconds of overhead).
- **Edge case**: If one home has a newer/larger snapshot than another (e.g., due to disk error during write), removing `break` ensures the true peak is found.

## Acceptance Criteria

### AC1: break removed
- GIVEN `find_peak_snapshot()` in `happy-session-recovery.sh`
- WHEN the function is called during peak protection
- THEN it iterates all `HAPPY_HOMES` entries, not just the first

### AC2: no functional regression
- GIVEN the session watcher is running
- WHEN a daemon restarts and triggers peak protection
- THEN peak merge works identically to before (since snapshots are already global)
