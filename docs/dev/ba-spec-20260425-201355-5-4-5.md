# BA Specification: Top-bar 800px hardcoded cap + inverted-toggle symptom (§5.4 + §5.5 bundle)

**Request ID**: dev-20260425-201355-5-4-5
**Created**: 2026-04-25T20:13:55Z

## Goal

Remove the hardcoded `WEB_TABLET_MAX_WIDTH_CAP = 800` constant in `useHeaderMaxWidth` so the
top-bar content row actually responds to viewport width on web/tablet. The Cycle 1 fix
(introducing the hook) made the calculation reactive but preserved the 800 cap, so on a
1920px viewport the avatar still sits at right=1526 (394px short of the right edge). With
the cap dominating the formula, opening or closing the right sidebar produces an apparent
clustering rather than expansion (§5.5 "inverted toggle" symptom is a downstream effect of
§5.4's same root cause).

## Context

Cycle 1 introduced `packages/happy-app/sources/hooks/useHeaderMaxWidth.ts` which replaced
the old static `layout.headerMaxWidth = 800` constant with a hook that computes
`windowWidth - leftDrawer - rightSidebar`. Both `Header.tsx:68` and `ChatHeaderView.tsx:120`
consume the hook's value. The hook ships, but its return value is `Math.min(available, 800)`
on every non-Mac platform (line 42), which means at any viewport ≥ 800 + drawers, the cap
dominates and the header still measures 800px regardless of viewport size or sidebar state.

Cycle 5 QA confirmed: at 1920 viewport, `avatar.right = 1526` (delta to viewport right
edge = 394px). At 1280 viewport, `avatar.right = 1206` (delta = 74px). This is exactly what
the user reports: "顶部栏的happy logo和头像元素没有自适应窗口内容元素的伸缩".

The §5.5 user complaint ("响应方向反了：sidebar 折叠时元素聚拢而非展开") shares this root
cause: when both sidebar-open and sidebar-closed states clamp `available` to 800, the
toggle visually changes only the *position* of the centered 800px container, not its width.
The user perceives this as "elements clustering together" instead of "container expanding
into freed space".

## Edge Cases & Risks

- Ultra-wide monitor (e.g., 3840×2160): header content row will stretch the full width minus drawers/sidebar. Could feel "too spacious" if the user has very few items in the header. Mitigation: Could-Have C1 if user later objects; not part of this fix per Cycle 5 directive.
- Right sidebar opens at exactly 901px viewport boundary: `available` becomes `901 - 0 - 450 = 451px`. Header content row will be 451px on web/tablet. Today this case already produces 451 (because cap=800 doesn't bite at 451). No regression.
- Mac path was using `available` (no cap) already. Web/tablet path becomes identical to Mac path. Acceptable per Cycle 5 directive (the Mac path was always the "correct" path; we are aligning all platforms to it).
- React Native `useWindowDimensions` triggers re-render on resize; no additional listener needed. Already verified by Cycle 1's `useHeaderMaxWidth` hook.
- TypeScript: removing the `WEB_TABLET_MAX_WIDTH_CAP` constant requires also removing or commenting any reference in the file (currently only used in lines 15 and 42; no consumers outside the file). `isRunningOnMac` import becomes unused after collapsing the branch — must also remove the import to keep the file clean and avoid unused-import warnings under TS strict mode.

- After the fix, the hook body should look like (illustrative — not authoritative; dev decides exact form):
  ```
  function computeHeaderMaxWidth(inputs: HeaderMaxWidthInputs): number {
      const { windowWidth, isAuthenticated, isTablet, sidebarCollapsed, rightSidebarOpen } = inputs;
      const showPermanentDrawer = isAuthenticated && isTablet;
      const drawerVisible = showPermanentDrawer && !sidebarCollapsed;
      const leftDrawerWidth = drawerVisible
          ? Math.min(Math.max(Math.floor(windowWidth * 0.3), 250), 360)
          : 0;
      const isRightSidebarDesktop = windowWidth >= RIGHT_SIDEBAR_DESKTOP_MIN_WIDTH;
      const rightSidebarWidth = rightSidebarOpen && isRightSidebarDesktop
          ? RIGHT_SIDEBAR_WIDTH
          : 0;
      // Cycle 6: removed WEB_TABLET_MAX_WIDTH_CAP (was 800 — Cycle 1 carried it
      // over from the legacy static layout.headerMaxWidth. User feedback in
      // spec-20260424-084848.md §7 directs to remove the cap entirely so the
      // header fills the available main area on all platforms.)
      return Math.max(0, windowWidth - leftDrawerWidth - rightSidebarWidth);
  }
  ```
