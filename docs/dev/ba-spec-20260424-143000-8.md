# BA Specification: Detail Panel — Long File Path Overflows Header

**Request ID**: dev-20260424-143000-8
**Created**: 2026-04-24T14:30:00Z
**Spec §**: 5.11

## Goal

The right-side detail panel renders a long `file_path` as an unconstrained `Text` element in `SidebarFileView.tsx`. On web, this text escapes the 450 px panel boundary horizontally, producing visible overflow. The fix must constrain the path text so the panel never overflows at any viewport width while keeping the full path accessible.

## Context

`RightSidebar.tsx` is a fixed-width 450 px panel (desktop) or a modal (mobile). `SidebarFileView.tsx` renders the resolved `file_path` from the tool input at the very top of the panel content area, before the diff/file tabs. The current `styles.filePath` has only cosmetic properties (fontSize, fontWeight, color, marginBottom) and no width or overflow constraint. On web React Native, a `Text` with no `numberOfLines` or `flexShrink` inside a vertical `ScrollView` can expand its intrinsic width beyond the scroll container's bounds, causing the visible horizontal bleed shown in the reference screenshot.

The `filePath.replace(/\//g, '/​')` insertion of zero-width spaces at line 49 provides soft-wrap opportunities but does NOT prevent horizontal overflow — it only allows wrapping when there IS a width constraint in place.

## Evidence (Contract A)

- **Observed**: "详情面板文件名超宽导致溢出" — detail panel file name overflows the bounds
- **Measured**: `SidebarFileView.tsx:49` renders `<Text style={styles.filePath}>{filePath.replace(...)}</Text>` where `styles.filePath` (lines 213–218) has no `numberOfLines`, no `flexShrink`, no `maxWidth`, no `overflow: 'hidden'`. The enclosing `ScrollView` at line 47 has `flex: 1` (vertical scroll only). On web, the Text intrinsic width is unbounded, exceeding the 450 px `SIDEBAR_WIDTH` set in `RightSidebar.tsx:11`.
- **Expected**: The path text must remain within the 450 px panel at all times. Acceptable: single-line truncation with middle ellipsis (keeps start+end of path visible), multi-line wrap, or horizontal scroll inside a bounded sub-container.
- **Gap**: No horizontal constraint on the `filePath` Text → unconstrained render width → horizontal bleed beyond panel on web.

## Reference Source (Contract C)

- **Tier**: tier_2_verified
- **Source**: React Native `Text` component documentation — `numberOfLines={1}` clips text to a single line with ellipsis on web and native; `ellipsizeMode="middle"` produces middle truncation. For the container: `flexShrink: 1` ensures the `Text` can shrink within a flex parent. No external URL required — both are documented React Native primitives.
- **Location**: React Native `Text` API (built-in, no external reference needed)
- **Copy allowed**: yes
- **Dev constraint**: Use `numberOfLines={1}` + `ellipsizeMode="middle"` on the `Text` node, AND add `flexShrink: 1` to `styles.filePath` so it yields to the parent flex container width. Do NOT add a separate horizontal `ScrollView` wrapper (that would make the path hidden by default with no affordance to reveal the start of it). Optionally add `Pressable` + clipboard copy so the full path remains accessible.

## Requirements (MoSCoW)

### Must Have

- R1: The `filePath` text in `SidebarFileView.tsx` must not overflow the panel horizontally at any viewport width.
- R2: Full path must remain accessible — via tooltip, long-press copy, or tap-to-expand (any one acceptable).
- R3: The fix must also cover `CodexPatchView.tsx` per-file path labels, which have the same unguarded rendering.

### Should Have

- R4: Use middle ellipsis (`ellipsizeMode="middle"`) so both the root prefix (e.g. `/dev/shm/...`) and the leaf filename remain visible in the truncated form.
- R5: Tapping the truncated path copies the full path to the clipboard with a brief confirmation.

### Could Have

### Won't Have (Non-Goals)

- Changing the detail panel width (`SIDEBAR_WIDTH`).
- Implementing a horizontal scroll for the path header (the path text is header metadata, not content to be scrolled).
- Fixing overflow in the `Input Parameters` JSON block — that is handled by `CodeView` and is a separate issue.

## Edge Cases & Risks

- React Native `ellipsizeMode="middle"` works on native but relies on the host element having a bounded width on web. Without `flexShrink: 1` on the Text style AND the parent View having no `width: undefined`, the ellipsis may not trigger. Dev must verify in the actual browser at 450 px and 320 px panel widths.
- Zero-width space insertion (`​`) must be preserved only if the path is also allowed to wrap (multi-line). If the preferred fix is single-line middle ellipsis, the `​` replacement is redundant and can be removed, simplifying the code.
- `CodexPatchView.tsx` uses a `FlatList` / `View` structure, not a `ScrollView` — the fix must be structurally compatible with that component's layout.

## Acceptance Criteria

### AC1: No horizontal overflow in SidebarFileView

- GIVEN the detail panel is open for any Edit / Write / MultiEdit tool call
- WHEN the tool input `file_path` is longer than the panel width (e.g. 80+ chars)
- THEN the path text is fully contained within the panel bounds — no text bleeds outside the 450 px panel on desktop or the full-width modal on mobile

### AC2: Full path accessible

- GIVEN the path is truncated by the fix
- WHEN the user taps/long-presses the truncated path OR uses a copy affordance
- THEN the full, untruncated path is accessible (copied to clipboard or shown in a tooltip/modal)

### AC3: Middle ellipsis preserves context

- GIVEN a path like `/dev/shm/dev-workspace/applio/.claude/worktrees/overnight-20260423-c593e035/docs/dev/overnight/c593e035-9739-48c7-b87f-9c1700252083/user-feedback-2026-04-23T20-50.md`
- WHEN rendered in the panel header
- THEN the visible text shows the leading root (e.g. `/dev/shm/...`) and the trailing filename (`user-feedback-...md`) with `...` in the middle

### AC4: No overflow in CodexPatchView

- GIVEN a CodexPatch tool call with per-file path labels that are long
- WHEN the detail panel renders the CodexPatchView
- THEN each per-file path label is horizontally constrained with the same treatment as SidebarFileView
