### Phase 9.1 — CR-1 (extractDefinitions fence-aware) — LAND FIRST

**File**: `parseMarkdownBlock.ts:364-386`

**Change shape** (iter-2 amended for renderer-consistent opener detection per REJ-2):

```typescript
function extractDefinitions(rawLines: string[]): { bodyLines: string[], defs: BlockDefs } {
    const linkDefs = new Map<string, LinkDef>();
    const footnoteRawDefs = new Map<string, string>();
    const bodyLines: string[] = [];
    let fenceMarker: '`' | '~' | null = null;  // null = not in fence
    let fenceLen = 0;
    for (const line of rawLines) {
        const trimmed = line.trim();  // SAME predicate as tryCodeBlock at parseMarkdownBlock.ts:207
        if (fenceMarker === null) {
            // opener detection: renderer-consistent — any leading whitespace OK (matches tryCodeBlock)
            if (trimmed.startsWith('```') || trimmed.startsWith('~~~')) {
                const marker = trimmed[0] as '`' | '~';
                // count opener run length (consecutive same-marker chars)
                let len = 0;
                while (len < trimmed.length && trimmed[len] === marker) len++;
                fenceMarker = marker;
                fenceLen = len;
                bodyLines.push(line);
                continue;
            }
            // outside any fence: existing def-stripping logic
            const lm = line.match(LINK_DEF_RE);
            if (lm && !lm[1].startsWith('^')) {
                linkDefs.set(normalizeLinkLabel(lm[1]), { url: lm[2], title: lm[3] });
                continue;
            }
            const fm = line.match(FOOTNOTE_DEF_RE);
            if (fm) { footnoteRawDefs.set(fm[1], fm[2]); continue; }
            bodyLines.push(line);
        } else {
            // inside fence — preserve verbatim, check for matching close
            // close: same marker, run length >= opener length, ONLY trailing whitespace after the run
            const closeRunMatch = trimmed.match(/^([`~])\1*/);
            if (closeRunMatch
                && closeRunMatch[1] === fenceMarker
                && closeRunMatch[0].length >= fenceLen
                && trimmed.slice(closeRunMatch[0].length).trim() === '') {
                fenceMarker = null;
                fenceLen = 0;
            }
            bodyLines.push(line);
        }
    }
    // Unclosed fence: fenceMarker remains non-null at EOF; the loop already pushed all lines to
    // bodyLines and skipped def-extraction for them. M4 / AC-CR1-UNCLOSED-FENCE satisfied automatically.
    // ... unchanged: 2-pass footnote def parsing on bodyLines ...
}
```

(Dev may inline-style differently; the above is shape-only. Two-pass footnote resolution after the fence-aware extraction is unchanged.)

**Iter-2 key change vs iter-1**: the opener regex `^ {0,3}(`{3,}|~{3,})` was CommonMark-strict (max 3 leading spaces). It is replaced with `line.trim().startsWith('``` ` / `~~~')` to match the existing renderer-side `tryCodeBlock` predicate at parseMarkdownBlock.ts:207. This closes the tab-indented-fence regression vector (REJ-2). The closer detection operates on `trimmed` so leading whitespace cannot fool it either.

### Phase 9.2 — CR-2 (`<details>` inline form) — LAND SECOND

**File**: `parseMarkdownBlock.ts:297-340`

**Three coordinated changes**:

1. **`findDetailsClose`** (line 297-303): change `from = lineStartIndex` (inclusive). Caller still passes `lineStartIndex + 1`? — NO, change the callsite at line 330 to pass `lineStartIndex` (inclusive). The function body is unchanged.

2. **`collectDetailsBody`** (line 305-312): when `openIndex === endIndex` (same-line close), the OLD logic appends `inlineRest` AND `closerHead` for the SAME line. Strip `</details>` from `inlineRest` for the same-line case, AND skip the `closerHead` push. Pseudo-shape:

   ```typescript
   function collectDetailsBody(lines: string[], openIndex: number, endIndex: number, inlineRest: string): string[] {
       const bodyLines: string[] = [];
       if (openIndex === endIndex) {
           // same-line close: inlineRest contains '...</details>' suffix; strip it.
           const stripped = inlineRest.replace(/<\/details>\s*$/, '');
           if (stripped.trim().length > 0) bodyLines.push(stripped);
           return bodyLines;
       }
       // multi-line case (existing logic):
       if (inlineRest.trim().length > 0) bodyLines.push(inlineRest);
       for (let i = openIndex + 1; i < endIndex; i++) bodyLines.push(lines[i]);
       const closerHead = lines[endIndex].replace(/<\/details>\s*$/, '');
       if (closerHead.trim().length > 0) bodyLines.push(closerHead);
       return bodyLines;
   }
   ```

3. **`extractDetailsSummary`** (line 314-325) OR `SUMMARY_LINE_RE` (line 295): relax to accept inline body after `</summary>`. Two options:

   - Option A (preferred — minimal): change `SUMMARY_LINE_RE` from `/^\s*<summary>(.*?)<\/summary>\s*$/` to `/^\s*<summary>(.*?)<\/summary>\s*(.*)$/`. Group 2 captures the inline body remainder; `extractDetailsSummary` returns it as a synthesized first body line:

     ```typescript
     function extractDetailsSummary(bodyLines: string[], defs: BlockDefs): { summary: MarkdownSpan[], bodyStart: number, prefix?: string } {
         for (let i = 0; i < bodyLines.length; i++) {
             const raw = bodyLines[i];
             if (raw.trim().length === 0) continue;
             const sm = raw.match(SUMMARY_LINE_RE);
             if (sm) {
                 const inlineBody = sm[2] ?? '';
                 // If there's inline body remainder, prepend it as bodyStart's first line:
                 if (inlineBody.trim().length > 0) {
                     bodyLines[i] = inlineBody;  // mutate (caller treats this as the new bodyStart line)
                     return { summary: parseMarkdownSpans(sm[1], false, defs.linkDefs, defs.footnoteDefs), bodyStart: i };
                 }
                 return { summary: parseMarkdownSpans(sm[1], false, defs.linkDefs, defs.footnoteDefs), bodyStart: i + 1 };
             }
             return { summary: [], bodyStart: 0 };
         }
         return { summary: [], bodyStart: 0 };
     }
     ```

   - Option B (slightly more invasive): pre-split the inline-form body in `collectDetailsBody` BEFORE calling `extractDetailsSummary`. Splits `<summary>X</summary>Y` into two pseudo-lines `<summary>X</summary>` and `Y`.

   Dev SHOULD choose Option A unless Option B is materially cleaner.

**Risk**: `SUMMARY_LINE_RE` change with the new group 2 is backward compatible — when there's no inline body, group 2 captures empty string, and the function takes the existing `bodyStart: i + 1` branch. All existing fixtures (multi-line `<details>` with summary on its own line) remain green.
