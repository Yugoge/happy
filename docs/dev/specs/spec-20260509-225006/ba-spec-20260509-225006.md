## 4. Evidence (Contract A)

### Item #10 reference-style links

- **Observed**: User catalog row says "Literal output, ref definitions also literal" — `[text][ref]` and `[ref]: url "title"` render as plain text.
- **Measured**: `parseMarkdownSpans.ts:117-124` (`consumeLink`) ONLY accepts `[text](url)` syntax (inline link). No code path consumes `[text][ref]`, `[ref][]`, `[ref]`, or `[ref]: url`. `parseMarkdownBlock.ts` has no link-definition collector. Confirmed by static read.
- **Expected**: Per CommonMark §6.3 Reference Links + §4.7 Link Reference Definitions:
  - `[ref]: <url> "optional title"` definition lines are extracted at block level (must be at start of line, optionally indented up to 3 spaces, label is case-insensitive, normalized by collapsing whitespace).
  - `[text][ref]` (full reference) → link with text=`text`, url=defs[ref.toLowerCase().trim()].
  - `[ref][]` (collapsed reference) → link with text=`ref`, url=defs[ref.toLowerCase().trim()].
  - `[ref]` (shortcut reference) → only when next char is not `[` and `ref` matches a definition.
  - Unmatched references render literally (CommonMark behavior: "If there is no matching link reference definition, the link reference is parsed as literal text").
- **Gap**: 0 reference-style link forms supported → must support 3 (full + collapsed + shortcut) plus literal fallback for unmatched.

### Item #11 footnotes

- **Observed**: User catalog row says `[^1]` not parsed — renders as literal `[^1]`.
- **Measured**: `consumeLink` (`parseMarkdownSpans.ts:117-124`) requires `[` followed by text, then `]`, then `(`. `[^1]` matches the leading `[` but the `^1]` content is not an inline-link match (no `(` follows the `]`), so the scanner falls through and emits literal text. No footnote definition collector in `parseMarkdownBlock.ts`. Confirmed by static read.
- **Expected**: Per GFM §6.7 Footnotes (https://github.github.com/gfm/) — but GFM's spec is silent on footnotes; the de-facto standard from Pandoc / commonmark-extension-footnote is:
  - `[^label]` reference → renders as superscript chip with content (typically the index 1, 2, 3...) linking to definition.
  - `[^label]: footnote content` definition line → captured at block level; not rendered inline at the definition site.
  - Definitions render at end-of-message OR inline-on-tap (chosen behavior per §5.2 design decision below).
  - Unmatched `[^x]` (no matching definition) renders literally (consistent with reference-link CommonMark behavior).

**§5.2 design decision (BA call)**: Render footnote chip as **inline tap-to-popover** (modal or inline expansion), NOT end-of-document accumulation. Rationale: (a) MarkdownView is rendered per-message inside scrollable conversation, not as a self-contained document; (b) end-of-message accumulation requires cross-block state plumbing (counter assignment between paragraphs), which significantly broadens scope; (c) tap-to-popover matches mobile-first UX and is consistent with the existing tooltip pattern for `<abbr>`.

- **Gap**: 0 footnote forms supported → must support 1 reference + 1 definition with bidirectional linkage, with unmatched fallback to literal.

### Item #9 HTML inline elements

- **Observed**: User catalog row + 5.3 §"渲染失败的降级策略不一致" — `<mark>`, `<sub>`, `<sup>`, `<abbr>`, `<details>` all render as literal angle-bracket text. Only `<kbd>` works.
- **Measured**: `parseMarkdownSpans.ts:109-115` has `consumeKbdSpan` for `<kbd>` only. No other HTML tag handlers. `parseMarkdownBlock.ts` has block-level handlers for `<options>` (line 209) but no `<details>` handler. Confirmed by static read.
- **Expected**: Per HTML5 spec for each tag:
  - `<mark>text</mark>` → highlighted text (yellow background by convention; theme-aware in our case).
  - `<sub>text</sub>` → subscript (smaller font, lower baseline).
  - `<sup>text</sup>` → superscript (smaller font, raised baseline).
  - `<abbr title="explanation">text</abbr>` → text with dotted underline; tap shows `title` attribute as tooltip/popover.
  - `<details><summary>label</summary>body</details>` → collapsible disclosure; closed by default unless `open` attribute set; clicking summary toggles body visibility.
- **Gap**: 5 HTML elements must be added. 4 are inline (`<mark>`, `<sub>`, `<sup>`, `<abbr>`), 1 is block-level (`<details>`).

**§5.3 design decision (BA call)**: `<details>` must be parsed at the block level (in `parseMarkdownBlock.ts`), not the span level, because it can contain other blocks (paragraphs, lists, code). The other 4 are pure inline spans.

## 9. Phasing (single cycle, 3 sub-phases — sequenced for codex iter-1 risk envelope)

Codex iter-1 forbade 4 parser items concurrent. This cycle is N=3 and sequences them so each lands cleanly before the next:

### Phase 8.1 — Item #10 reference-style links (LAND FIRST)

Rationale: pure inline-span tokenizer that ALSO needs a block-level def collector. Most isolated of the three (no new render styles, no collapsible UI, no popover plumbing). Validates the 2-pass block parser pattern (def collection pass → span resolution pass).

Implementation map:
- `parseMarkdown.ts`: add type field `linkDefs?: Map<string, { url: string, title?: string }>` to top-level parse result OR pass as second arg to `parseMarkdownSpans`. Recommended: keep `parseMarkdownSpans` purely span-local; have `parseMarkdownBlock` do a pre-pass to extract def lines, then pass the resolved map to each span call.
- `parseMarkdownBlock.ts`: add `extractLinkDefinitions(lines: string[]): { lines: string[], defs: Map<string, LinkDef> }` that strips `^\s{0,3}\[label\]:\s+url(\s+"title")?$` lines and returns a label-keyed map (label normalized via lowercase + whitespace collapse).
- `parseMarkdownSpans.ts`: extend `consumeLink` (or add `consumeReferenceLink`) to handle `[text][ref]`, `[ref][]`, `[ref]` forms. Requires the def map as a second parameter on the inline parser entry point.
- `MarkdownView.tsx`: NO change (link rendering already exists; just gets `url` populated for ref-style links).
- `parseMarkdown.test.ts`: 5 new fixtures (full ref + collapsed + shortcut + unmatched literal + def-line-stripped-from-output).

Risk: changing the public signature of `parseMarkdownSpans(markdown, header)` to `(markdown, header, linkDefs?)` is a wide change — every call site (table cells, list items, headers, blockquotes) needs the def passed. Mitigation: make `linkDefs` optional with default `undefined`, and only populate from the top-level `parseMarkdownBlock` entry. Inner recursive calls (blockquote inner-block, table cells) inherit empty map → ref-style links inside table cells with defs at block-message level resolve only if the def-extraction pass collects across the whole message before per-block parsing starts. Decision: **collect defs once at message level**, pass through `parseMarkdownBlock` recursive calls. Document this in code.

### Phase 8.2 — Item #11 footnotes (LAND SECOND)

Rationale: reuses the def-collection pattern from Phase 8.1. The popover/expansion UI is new but isolated to one new span style + one optional render component.

Implementation map:
- `parseMarkdown.ts`: extend `MarkdownSpan` styles union with `'footnote-ref'`. Add new optional field `footnoteLabel?: string` on span shape (or reuse `url` as a sentinel like `#footnote:label`).
- `parseMarkdownBlock.ts`: extend `extractLinkDefinitions` with `extractFootnoteDefinitions` (or merge into one pass). Returns separate map.
- `parseMarkdownSpans.ts`: add `consumeFootnoteRef` that matches `\[\^([^\]\s]+)\]` (label = no whitespace, no `]`). Emit span with style `footnote-ref` + `footnoteLabel`. Unmatched (label not in map) → fall through to literal.
- `MarkdownView.tsx`: add `style.footnoteRef` (smaller font + raised baseline + theme-accent color), wire up tap handler that toggles a per-span expanded state revealing the definition text. Keep state local to the message component to avoid cross-message contamination.
- `parseMarkdown.test.ts`: 4 new fixtures (single ref+def, multiple refs+defs, unmatched literal, ref inside table cell).

Risk: cross-block state (definitions defined in paragraph 5 but referenced in paragraph 1). Mitigation: same def-collection pre-pass as Phase 8.1 — defs are message-global. Render-time state (which footnote is currently expanded) is component-local React state.

### Phase 8.3 — Item #9 HTML inline + `<details>` block (LAND THIRD)

Rationale: 5 distinct HTML tags. Inline 4 (`<mark>` `<sub>` `<sup>` `<abbr>`) reuse the `consumeKbdSpan` pattern. `<details>` is block-level and is the most invasive (new block type). Land last so Phase 8.1 + 8.2 are stable before any block-shape addition.

Implementation map:
- `parseMarkdown.ts`: extend `MarkdownSpan` styles union with `'mark'`, `'sub'`, `'sup'`, `'abbr'`. Add optional field `tooltip?: string` for `<abbr title="...">`. Add new `MarkdownBlock` variant `{ type: 'details', open: boolean, summary: MarkdownSpan[], content: MarkdownBlock[] }`.
- `parseMarkdownSpans.ts`: add `consumeMarkSpan`, `consumeSubSpan`, `consumeSupSpan`, `consumeAbbrSpan` mirroring `consumeKbdSpan` shape. `consumeAbbrSpan` parses `title="..."` attribute via simple regex (`<abbr\s+title="([^"]*)"\s*>`); falls back to literal if attribute parsing fails.
- `parseMarkdownBlock.ts`: add `tryDetailsBlock` similar to `tryOptionsBlock`. Must consume opening `<details>` (with optional `open` attribute), optional `<summary>...</summary>` line, body lines, closing `</details>`. Body lines are recursively parsed via `parseMarkdownBlock`.
- `MarkdownView.tsx`: add `style.mark`, `style.sub`, `style.sup`, `style.abbr` entries. Add `RenderDetailsBlock` component with a `Pressable` summary (acts as toggle) and conditional render of inner blocks. Tooltip for abbr: tap reveals tooltip via inline expansion (same primitive as footnote popover for consistency).
- `parseMarkdown.test.ts`: 5 new fixtures (one per HTML element). Plus 1 negative fixture: `<unknown>tag</unknown>` → renders literally (consistent with current behavior).

Risk: `<details>` body recursive parse may hit edge cases (e.g., nested `<details>`). Mitigation: recursive `parseMarkdownBlock` already handles nested constructs via blockquote precedent. Add a fixture for nested `<details>`. `<abbr>` attribute regex must be loose enough to accept single-quote `title='...'` AND double-quote `title="..."`. Add fixture for both.

## 14. Risks (regression vectors and AC defenses)

| Risk | Vector | Defense |
|---|---|---|
| **R1**: changing `parseMarkdownSpans` signature breaks every internal call site | Table cells, list items, headers, blockquotes all call `parseMarkdownSpans(text, header)` directly | Optional `linkDefs` + `footnoteDefs` params; default to empty maps. AC-NONREG-PARSER + AC-INTERACTION-TABLE-REFLINK + AC-INTERACTION-NESTED-OL-REFLINK exercise every call site. |
| **R2**: link reference label normalization regression breaks existing `[text](url)` inline links | Label normalization touches the `[` token shared with inline links | Inline link `[text](url)` recognized FIRST in `consumeToken` (when `(` follows `]`); reference-link path only entered when `[` doesn't match an inline link. AC `keeps emphasis bounded before strikethrough, links, code, and escapes` from baseline guards this. |
| **R3**: footnote tokenizer collides with shortcut reference link `[ref]` | `[^1]` is also `[` followed by text closing in `]`, no following `(` or `[` | Footnote ref tokenizer ONLY fires when the char immediately after `[` is `^`. Shortcut ref tokenizer ONLY fires when first char is NOT `^`. AC-11-FOOTNOTE-INLINE + AC-10-REFLINK-SHORTCUT live in the same fixture mix to guard. |
| **R4**: `<details>` block parser swallows content past the closing tag | Greedy `</details>` matcher, malformed close | Match exactly `</details>` on its own line OR at line end; if no close found before end-of-input, fall through to literal text. Add fixture: `<details>` without close → renders literally. |
| **R5**: `<abbr title='...'>` single-quote case slips through | Regex tuned to double-quote only | Regex accepts both single and double quotes: `title=(['"])([^\1]*?)\1`. Fixture for both. |
| **R6**: footnote popover state leaks between messages | If footnote expanded state lifted too high in component tree | Keep React state local to `MarkdownView` component instance. Per-message keys ensure isolation. |
| **R7**: link def extraction drops a real text line that LOOKS like a def | `[ref]: this is a real sentence` mistakenly stripped | Strict regex: `^\s{0,3}\[([^\]]+)\]:\s+(\S+)(?:\s+"([^"]*)")?\s*$` — must be a single line, must have URL-shaped second field. False-positive risk acceptable; CommonMark accepts the same. |
| **R8**: `<details>` body recursive parse hits infinite loop on `<details>` without summary | Edge case | Recursive `parseMarkdownBlock` handles arbitrary block content; summary is optional (CommonMark). Fixture: `<details>` with only body, no `<summary>`. |
| **R9**: `MarkdownView.tsx` exceeds 800-line budget | New components for details + tooltip + footnote popover | Budget audit at end of Phase 8.3. If over, factor out subcomponents to companion file `MarkdownInlineDecorations.tsx`. AC-MARKDOWN-VIEW-LINES enforces. |
| **R10**: codex was not invoked this cycle, so adversarial review is BA+QA-only | No external second opinion | Self-review during BA: §9 phasing + §10 AC table + §14 risk table demonstrate adversarial discipline. QA during dev cycle and `/close` will challenge any miss. |
