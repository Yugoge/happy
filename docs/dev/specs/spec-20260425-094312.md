### 5.1 P0：peak-merge 算法重做

**1️⃣ 窗口太宽**
- **现状**：`PEAK_PROTECT_SECONDS=28800`（8h）
- **改成**：`14400`（4h）
- **位置**：`/root/bin/happy-session-recovery.sh` 顶部常量，以及 `/dev/shm/dev-workspace/happy-dev/CLAUDE.md` 文档
- **Success criteria**：grep 脚本 + CLAUDE.md 都是 14400 / 4h

**2️⃣ 整体覆盖错误（核心 bug）**
- **现状**：`find_peak_snapshot` 选 8h 内 session_count 最大的 snapshot，**整体替换** `session_dirs.txt`。结果：13:11 UTC 的 10 sessions 把 20:48 UTC 实时的 6 sessions 完全覆盖。
- **设计**：增量 merge —— `merged = current ∪ peak_within_window`，再过滤"磁盘 .jsonl 还在 + .jsonl mtime 在合理时间窗口内"。**默认阈值：`MERGE_FRESHNESS_SECONDS=7200`（2 小时）**，写在脚本顶部常量块（与 `PEAK_PROTECT_SECONDS` 相邻）。用户可覆盖：`MERGE_FRESHNESS_SECONDS=<n> bash /root/bin/safe-daemon-restart.sh ...`。
- **不能让 peak 覆盖当前** —— peak 只是补充 watcher 漏抓的兜底
- **Success criteria**：
  - 给定 case A：current=6, peak=10（4 个交集，6 个 peak 独有），merged 应≥6（保留 current 全部）+ 视过滤策略包含 peak 独有但 .jsonl 仍 fresh 的部分
  - 给定 case B：current=0（restart 瞬间）+ peak=10：merged 不再"整体覆盖"，而是 abort 写文件（见 5.1.3）
  - 单元测试或 dry-run 模式可以观察"current set / peak set / merged set / 被丢弃的 set"

**3️⃣ ExecStartPre save 在 daemon 被 kill 时仍写 0**
- **现状**：daemon 重启瞬间 ExecStartPre 跑 `save`，pid-based 检测拿到 0 sessions，**仍然把 0 写进 session_dirs.txt**（虽然有 peak-protect，但触发了下游的 peak-merge）
- **设计**：`save_session_state` 看到 `running_count == 0` 时**不写文件**（保留上次内容），并在 log 标记 `Skipping save: 0 sessions detected (likely transition)`
- **Success criteria**：
  - 模拟 daemon-down 状态下跑 `save`：session_dirs.txt mtime 不变、内容不变
  - log 出现 "Skipping save: 0 sessions detected"

#### 5.2-B：disambiguate `run.ts:111-122` 的误导性日志（次要，但必须修）

- **现状**（`packages/happy-cli/src/daemon/run.ts:111-122`）：
  ```ts
  const matches = await isDaemonRunningCurrentlyInstalledHappyVersion();
  if (!matches) {
    logger.debug('[DAEMON RUN] Daemon version mismatch detected, restarting daemon with current CLI version');
    await stopDaemon();
  } else { ... }
  ```
  `isDaemonRunningCurrentlyInstalledHappyVersion()` 在 "no daemon running" / "no state file" / "stale pid" / "real version mismatch" 四种情况下都返回 `false`，但调用方一律打"version mismatch"。
- **修法**：分别 log 四种情况：
  ```ts
  const state = await readDaemonState();
  if (!state) {
    logger.debug('[DAEMON RUN] No prior daemon state, starting fresh');
  } else if (state.startedWithCliVersion !== packageJson.version) {
    logger.debug(`[DAEMON RUN] Version mismatch (${state.startedWithCliVersion} -> ${packageJson.version}), restarting`);
    await stopDaemon();
  } else if (!processStillRunning(state.pid)) {
    logger.debug('[DAEMON RUN] Stale state file, prior daemon dead, starting fresh');
  } else {
    console.log('Daemon already running with matching version');
    process.exit(0);
  }
  ```
- **Success criteria**：
  - 模拟"无 state 文件"启动：log 出现 "No prior daemon state, starting fresh"，**不**出现 "version mismatch"
  - 模拟"真版本不一致"：log 出现 "Version mismatch (X -> Y)"

#### 5.2-C：`/stop` HTTP endpoint 需要保护（中期）

- **现状**：daemon HTTP control server 暴露 `/stop` 无任何 auth / token check，任何能连到 `127.0.0.1:<port>` 的进程都能杀掉 daemon
- **风险**：worktree 内任意 cycle / agent / hook 都可能误调或恶意调
- **修法（择一）**：
  - (i) `/stop` 加 token，token 写在 `daemon.state.json` 里只对 owner 进程可读（chmod 0600）
  - (ii) `/stop` 仅在 cmdline 显式传 `--allow-stop` 启动的 daemon 接受
  - (iii) `/stop` 检查调用方 PID 是否在白名单（systemd unit pid + same uid）
- **Success criteria**：
  - 不带 token 的 `curl POST /stop` → 401/403
  - 持 token 的 `happy daemon stop` 正常工作

##### 5.2-D-2：修复 hook 的 arg-parsing bug

**bug 定位**：`/root/.claude/hooks/pretool-bash-safety.sh` L66-90 `check_systemctl_targets_all_dev`（**此文件是 settings.json 注册的 live hook**；`/root/.claude.bak/hooks/pretool-bash-safety.sh` 是同内容的 backup，必须同步修改；`/root/happy/.claude/hooks/pretool-bash-safety.sh` 是独立 stub，不在本次修改范围）：
```bash
args=$(echo "$subcmd" | sed -E 's/.*systemctl\s+(stop|restart)\s+//')
for arg in $args; do ...
```
对 `systemctl restart happy-daemon-dev 2>&1 | head -5`，`$args` = `happy-daemon-dev 2>&1 | head -5`，`for` 循环把 `2>&1` / `|` / `head` / `-5` 都当 service 名 → 第二个就不命中 → return 1 → BLOCKED（即使第一个 service 名 happy-daemon-dev 是 dev 白名单成员）。

**修法**：
```bash
# 提取到第一个非 service-name token（redirect / pipe / & / ;）就停止
args=$(echo "$subcmd" | sed -E 's/.*systemctl\s+(stop|restart)\s+//' | awk '
  { for (i=1;i<=NF;i++) {
      if ($i ~ /^[<>|&;]/ || $i ~ /^[0-9]+>/) exit
      if ($i ~ /^-/) continue
      print $i
    } }
')
```

**Success criteria（仅验证解析正确性，政策约束见 5.2-E）**：
- `systemctl restart happy-daemon-dev` → hook `check_systemctl_targets_all_dev` 正确解析 service 名为 `happy-daemon-dev`，匹配白名单，函数返回 0（**注意：hook 不拦不代表 subagent 可以调；subagent 调用仍受 5.2-E 约束**）
- `systemctl restart happy-daemon-dev 2>&1 | head -5` → redirect 后 token 被忽略，service 名仍正确解析为 `happy-daemon-dev`，函数返回 0
- `systemctl restart happy-server` → 解析为非白名单 service，函数返回 1，命令被拦截
- `systemctl restart happy-daemon-dev happy-server` → 存在非白名单 service，函数返回 1，命令被拦截
- `systemctl restart happy-daemon-dev && systemctl restart happy-server` → split 后第二个子命令含非白名单 service，被拦截

**5.2-D-2 vs 5.2-E 关系**（必须显式写进 spec）：
- 5.2-D-2 修的是"解析正确性"——hook 不再因为 redirect/pipe 把合法的白名单命令误判为非白名单
- 5.2-E 修的是"谁有权调"——subagent 即使命令能通过 hook，仍不允许直接调 `systemctl restart happy-daemon-*`
- 两条规则不冲突：hook 允许通过 + subagent 政策禁止 = subagent 不调，user TTY 调 = 通过

#### 5.2-E：happy-dev / happy-prod 开发新功能时的安全重启 SOP

**目标**：当 user / dev workflow 真的需要重启 daemon（部署新代码、调试），用一套**统一、可审计、零数据丢失**的流程，而不是直接 `systemctl restart`。

##### 5.2-E-1：新工具 `/root/bin/safe-daemon-restart.sh <dev|default|jade> [--reason <text>] [--no-confirm]`

**职责**（一个动作走完整流程）：

1. **Pre-flight**：
   - `bash /root/bin/happy-session-recovery.sh save --home /root/.happy-<X>`
   - 列出当前 dev/prod home 下所有 active session（count + UUID + last_active + work_dir）
   - 检查有没有 dev-overnight cycle 正在跑（看 `.claude/workflow-*.json` mtime < 5 min）—— 有则 ABORT
   - 检查有没有 ExecStartPre / 其他 systemctl 在跑 —— 有则等
   - 备份 dev DB：`pg_dump dev>/root/backup/happydb_dev-<ts>.sql`（prod 同理但目标 happydb）
2. **Confirmation gate**：
   - 默认必须 TTY 交互（`[ -t 0 ]`），打印影响信息再 prompt "type RESTART to continue"
   - `--no-confirm` 必须配合 `--reason "<>"` 文本（≥ 20 字符），写到 audit log `/var/log/happy-restart-audit.log`
   - prod 严格：必须再带 `--prod-acknowledged` flag（明示确认会影响所有用户）
3. **Graceful stop（两阶段实现）**：
   - **v0（5.2-C 上线前）**：直接 `systemctl stop happy-daemon-<X>.service`（无 token，但此调用由脚本发起，不是 subagent 直接调 systemctl，因此不违反 5.2-E-2 的 subagent 禁令）
   - **v1（5.2-C 上线后）**：先 HTTP `POST /stop` with token（token 从 `daemon.state.json` 读），失败则 fallback `systemctl stop happy-daemon-<X>.service`
   - 脚本内用 `SAFE_RESTART_USE_TOKEN=${SAFE_RESTART_USE_TOKEN:-0}` env var 控制阶段切换
   - 等 `daemon.state.json` 删除 + main pid 退出（最多 30s）
   - 30s 仍在 → ABORT + 打印 user 该如何手动处理（**不**自动 SIGKILL）
4. **Start**：
   - `systemctl start happy-daemon-<X>.service`
   - 等 `daemon.state.json` 出现 + httpPort 可达（最多 30s）
   - 30s 仍未 ready → ABORT + 输出 systemd journal 最后 30 行
5. **Post-flight verify**：
   - 调 `/list` 拿新 session 列表
   - 对比 pre-flight：丢了哪些 UUID
   - 对每个丢失 UUID 调 `bash /root/bin/happy-session-recovery.sh recover <uuid> --home /root/.happy-<X>`
   - 等 1 分钟，再 `/list` 验证
   - 写一份 report 到 `/var/log/happy-restart-audit.log`：pre/post counts + recovered UUIDs + duration

##### 5.2-E-3：dev vs prod 差别策略

| 维度 | dev (`/root/.happy-dev`) | prod (`/root/.happy` + `/root/.happy-jade`) |
|---|---|---|
| 自动 cycle 调用 | 严禁 | 严禁 |
| user manual 调用 | 允许，需 TTY 确认 | 允许，需 TTY + `--prod-acknowledged` |
| 一次重启范围 | 仅 dev | 一次只能一个 prod home（default 或 jade，不能两个一起）|
| restart 间隔 | 无限制 | 重启完一个 prod home 后**至少等 5 min** 再重启另一个（让用户有迁移窗口）|
| 失败回滚 | 自动从 snapshot recover | 自动 recover + 必须 alert user 不再继续 |
| Audit log | 必写 | 必写 + 通知 user（webhook / email，可选）|

##### 5.2-E-4：daemon 自身的"开发新代码部署"流程

当 user 改了 `packages/happy-cli/src/...` 想让新代码生效时：

```bash
# Step 1: build（不会触发 daemon 自杀，因为 version 没变）
cd /dev/shm/dev-workspace/happy-dev/packages/happy-cli && yarn build

# Step 2: bump version（让 daemon auto-upgrade 心跳能正确触发）
#   只在确实想让 daemon 自动重启时才做
node -e 'const p=require("./package.json"); p.version=p.version.replace(/(\d+)$/,n=>+n+1); require("fs").writeFileSync("./package.json",JSON.stringify(p,null,2))'

# Step 3: rebuild dist（version 变化要让 dist 里的 currentCliVersion 同步）
yarn build

# Step 4: 触发 graceful restart
/root/bin/safe-daemon-restart.sh dev --reason "deploying new daemon code <changeset>"
```

**或者**直接调用 step 4，不 bump version —— `safe-daemon-restart.sh` 会保证零数据丢失，不依赖 auto-upgrade 心跳。

##### 5.2-E-5：Success criteria

1. `/root/bin/safe-daemon-restart.sh` 文件存在，executable，包含 5.2-E-1 所有步骤
2. dev-overnight skill / dev skill / 任何 subagent skill 中**没有**直接 `systemctl restart happy-daemon` 调用
3. 真实跑一次 `safe-daemon-restart.sh dev --reason "test"`：pre/post session count 一致（如果有丢失自动 recover），audit log 有完整记录
4. prod 同名命令必须额外要 `--prod-acknowledged`，否则 ABORT
5. 在 daemon 已经 down 的状态下跑：脚本检测到并 ABORT，**不**尝试 stop（已经 stop）

##### 5.2-E-6：不该做的（明确写进 SOP）

- ❌ `kill <pid>` —— 会跳过 graceful drain，session 数据丢失
- ❌ `systemctl restart` 直接调 —— 跳过 pre/post-flight 和 audit
- ❌ `docker restart happy-server` —— 不在本 SOP 范围（happy-server 不在 systemd 下，本 SOP 不管 docker）
- ❌ 在 dev-overnight cycle 里调 SOP —— SOP 检测到 cycle 在跑会 ABORT
- ❌ 跨 home 同时重启（一次只能 dev 或 default 或 jade，不能并行）
- ❌ 没有 `--reason` 的非 TTY 调用

### 5.4 P1：archive 状态 client-only

- **现状**：`Session.metadata.lifecycleState='archived'` 只在加密 metadata blob 里。server `grep -r 'lifecycleState' packages/happy-server/sources/` 0 处。
- **后果**：任何重新 `POST /v1/sessions` 覆盖 metadata 都丢失 archive flag，且不可逆（要 masterSecret 解密旧 blob）
- **修法**：
  - server schema：`Session.archived BOOLEAN DEFAULT false`，加 prisma migration
  - 改 `/v1/sessions/:id/archive` endpoint 写 server 列（不依赖 metadata）
  - 改 `/v1/sessions` list endpoint 默认按 `archived=false` 过滤；加 `?includeArchived=1` query 参数
  - app `SessionView.tsx` archive 过滤改用 server 列（`session.archived === true`），保留对老 metadata 的兼容读
- **Success criteria**：
  - 新 archive 一个 session，DB `Session.archived = true`，UI 列表立即不显示
  - daemon 重启 + recovery 重 spawn 同一 UUID，**archive 状态不丢**
  - 老数据 metadata 里有 `lifecycleState='archived'` 的 session 仍被 UI 隐藏（向后兼容期）

**5.4 Rollback Plan**：
- prisma migration 落地前，user 必须运行 `pg_dump happydb_dev > /root/backup/happydb_dev-pre-archive-migration-$(date +%Y%m%d-%H%M%S).sql`（注意 5 节 8 注 5：prisma migrate **不能直接对 dev DB 跑**，必须 user 批准 + 备份）
- 若 migration 失败、UI 加载报错、或 archive 列读写不一致：
  1. `prisma migrate resolve --rolled-back <migration-name>`（在 happy-server 容器内）
  2. 从 backup 恢复：`docker exec -i happy-postgres-dev psql -U yuge -d happydb_dev < /root/backup/happydb_dev-pre-archive-migration-<ts>.sql`
  3. revert `sessionRoutes.ts` 改动（git checkout 单文件）
  4. revert UI archive filter 改动，让 `SessionView.tsx` 仍走 metadata 路径
- **不**清理已 archive 但 metadata 未来得及写的 session（恢复 metadata 路径后老逻辑会再次识别）

### 5.5 P2：`restore` 子命令仍是 claude-only

- **现状（两层 bug）**：
  1. **上游过滤（更严重）**：`restore_online_sessions` L962-968 在 spawn 前做 `.jsonl` 存在性检查：
     ```bash
     local session_file="$CLAUDE_PROJECTS_DIR/$project_encoded/$uuid.jsonl"
     if [ ! -f "$session_file" ]; then
         log "Skip $uuid: .jsonl not found"
         continue
     fi
     ```
     Codex thread-id 的 session 可能无对应 `.jsonl`（或路径不同），导致被丢弃。**此上游过滤在 flavor 检测之前运行**，加 flavor-autodetect 无效。
  2. **下游 spawn 路径**：即使通过了上游过滤，`daemon_spawn_session` 当前不传 flavor 参数。

- **修法（必须按顺序）**：
  1. **先修上游过滤**：在 `.jsonl` 检查之前调 `is_codex_thread_id "$uuid"`。若为 codex flavor，跳过该 `.jsonl` 检查（codex 用 `CODEX_HOME` 路径，不是 `CLAUDE_PROJECTS_DIR`），直接进入 rollout 检查分支：
     ```bash
     # codex sessions do not have claude .jsonl files — skip the check
     if ! is_codex_thread_id "$uuid"; then
         local project_encoded
         project_encoded=$(echo "$work_dir" | sed 's|/|-|g')
         local session_file="$CLAUDE_PROJECTS_DIR/$project_encoded/$uuid.jsonl"
         if [ ! -f "$session_file" ]; then
             log "Skip $uuid: .jsonl not found (claude session)"
             total_skipped=$((total_skipped + 1))
             continue
         fi
     fi
     ```
  2. **再修下游 spawn**：`daemon_spawn_session` 调用加 flavor 参数（已有 `is_codex_thread_id` helper）：
     ```bash
     local flavor="claude"
     is_codex_thread_id "$uuid" && flavor="codex"
     if daemon_spawn_session "$home" "$work_dir" "$uuid" "$flavor"; then
     ```

- **Success criteria**：
  - session_dirs.txt 同时含 claude UUID 和 codex `019d…` thread-id
  - codex UUID 不因 `.jsonl not found` 被跳过（log 不出现 `Skip <codex-uuid>: .jsonl not found`）
  - restore 后 log 中每条 spawn 显示 `flavor=claude` 或 `flavor=codex`
  - 现有 claude session restore 行为不变（仍做 .jsonl 检查）

### 5.6 P2：cli_path symlink 脆弱 — DEFERRED

- **现状**：`/root/happy-dev → /dev/shm/dev-workspace/happy-dev`。`/dev/shm` 清空或重启后 → symlink dangling → spawn 全失败
- **原提案缺陷（已废弃）**：spec 原提案 "fallback `/root/happy-dev/...` → `/dev/shm/dev-workspace/happy-dev/...`" 解析到同一 inode，`/dev/shm` 清空后两条路径同时失效，fallback 无实际效果。
- **真正的修法**：把 happy-dev 源码克隆到 sda1 持久路径（如 `/root/happy-dev-stable`），更新 daemon systemd unit 的 `ExecStart` 路径，更新 `happy-session-recovery.sh` 的 `cli_path` 映射。此为架构变更，需独立 spec。
- **本次处置**：降级为 P3-DEFERRED，不在本 spec 修复范围。
- **临时缓解**：dev daemon 重启后，user 手动运行 `ls /dev/shm/dev-workspace/happy-dev/packages/happy-cli/dist/index.mjs` 确认路径存在，或在 daemon 启动脚本加 pre-check + 明确报错日志（不做 silent fallback）。
- **Success criteria（本 spec 仅验证文档）**：
  - 5.11 影响文件清单里 `cli_path` 那行标注 DEFERRED
  - 不存在任何代码 PR 实现原来那段 `[ -f "$cli_path" ] || cli_path=...` 双路径 fallback（因为无效）

### 5.7 P2：daemon_spawn_session 两条 spawn 路径 env 不一致

- **现状**：systemd-run 主路径硬编码 `-E HAPPY_HOME_DIR=... -E HAPPY_SERVER_URL=...`，**忽略** `$spawn_env`。fallback 用 `env $spawn_env`。上次只在 fallback 加了 codex 的 CODEX_HOME 剔除，主路径没改。

  - 跑一次 codex spawn，systemd-run 主路径下子进程的 environ 不含 `CODEX_HOME=`

### 5.10 Edge cases（spec 必须明确处理）

1. **peak window 4h 但全 4h 内都是 0 session**：
   - 不写 file（保留上次内容）
   - log warn "no peak snapshot in 4h window"
   - 下游 restore 仍按 session_dirs.txt 现有内容跑

2. **kill orphan 时 SIGTERM 失败**：
   - SIGTERM 后等 10s
   - 仍存活则 SIGKILL（针对 launcher 进程，不直接对 main —— main 是 PPID=1，被杀后 systemd 自动清理）
   - 子进程链：claude.exe / codex / playwright-mcp 也要清

3. **daemon auto-upgrade 心跳卡住**：
   - 心跳函数加 timeout（建议 30s）
   - 卡住超时 → log error，不主动重启
   - systemd Watchdog 兜底

4. **peak-merge 拿到的 snapshot 文件损坏（jq 解析失败）**：
   - skip 该 snapshot，继续找次新的
   - log warn

5. **codex thread-id 自动检测 false positive**（极小概率正常 UUIDv4 以 `019d` 开头）：
   - 显式 `--flavor` 优先级最高，能 override
   - 已有

6. **dev-overnight 多个 worktree 并发 build**：
   - 当前只有一个 dev daemon，多个并发 build 会触发多次 hash 变化
   - P0-NEW 的 grace window 设计要够长（5 min）覆盖 cycle 间隔

## Section 8: Attention Notes

**操作约束（非常重要）**：

1. `/root/bin/happy-session-recovery.sh` 是 systemd `happy-session-watcher.service` 在用的 live 脚本。改动后**不能直接重启服务**，要由 user 手动确认。
2. 整个 hook 体系封死了对 `happy-session-recovery.sh` 文件名的所有 bash 命令（含 cp / mv / diff），subagent 备份得用别名（如 `recovery-bak-XXXX`）。
3. **不准 npm install -g**、**不准 /usr/bin/happy**、**不准 systemctl restart**（除 user 明确批准），违者破坏 production daemon。
4. 改 `packages/happy-cli/src/daemon/run.ts` 后 yarn build dist **本身不会**触发 daemon 自杀（version 没变 daemon 不会主动重启） —— 但**禁止**手动调用 `happy daemon stop` / `happy daemon restart` （这才是这次故障的真正触发源；5.2-A 的根因）。如果确实要让新代码生效，停 dev daemon 必须由 user 显式批准。
5. archive 列加上 schema 后，prisma migrate **不能直接对 dev DB 跑**（要先备份），更不能动 prod DB schema。
6. 任何对 session 状态的"修复"必须先 `pg_dump` dev DB 备份。
7. 这次修复是**多文件 cross-package 改动**（happy-cli + happy-server + happy-app + bash + 文档），任一处独立完成不算结束 —— 必须全部通过 success criteria 才算 done。
8. dev-overnight 在跑的时候**不要并行做这次修复**，会撞车（worktree 还在改 happy-cli 源码）。先停掉 dev-overnight。
9. **绝不直接 `systemctl restart happy-daemon-*`**：必须用 `/root/bin/safe-daemon-restart.sh <home> --reason "<text>"`（5.2-E）。subagent 唯一允许的"我需要重启"动作是输出一个 REQUEST 消息给 user，由 user 显式触发 SOP 工具。
10. **subagent 遇 hook 拦截**必须立即 PAUSE 并向 user 汇报具体命令和错误，**严禁**写 /tmp/*.sh 绕过、严禁 nohup / systemd-run / setsid 包裹、严禁读 hook 源码找漏洞、严禁修改 hook 文件（5.2-D-1 / 全局 CLAUDE.md 第 14 条）。
11. **`safe-daemon-restart.sh` 自身**在 dev-overnight cycle 跑期间调用必须 ABORT —— 检测 `.claude/workflow-*.json` mtime < 5 min 即视为 cycle 在跑（5.2-E-1 step 1）。

- 老 daemon log 路径 `/root/.happy-dev/logs/2026-04-09-21-29-49-pid-400414-daemon.log` 13MB，是历史包袱，跟本次修复无关但可清理（不在 spec 范围）
