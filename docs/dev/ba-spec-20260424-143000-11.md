# BA Specification: Top Bar — Header Max-Width and Right-Sidebar Reserved Width Not Responsive (§5.4 + §5.5)

**Request ID**: dev-20260424-143000-11
**Created**: 2026-04-24T14:30:00Z
**Spec file**: docs/dev/specs/spec-20260424-084848.md §5.4 + §5.5

---

## Goal

Make the top navigation bar's content column — and therefore the happy logo (leading) and user avatar (trailing) — reflow responsively when the available main-area width changes, across all supported layout states: varying viewport widths, left-drawer expand/collapse, and right-sidebar open/close.

---

## Context

The header's flex row (logo — center — avatar) is structurally correct: all three slots are in flex, not absolutely positioned. However, the `content` wrapper applies `maxWidth: layout.headerMaxWidth` which is a static value computed once at module load time (800 px on web/tablet, `Infinity` on Mac). It does not shrink to account for the RightSidebar's fixed 450 px reservation. When the right sidebar opens, the header's `content` wrapper still claims its full static maxWidth, so the right edge of the center column overflows or the avatar drifts outside the visible main area. The visual symptom the user describes — "logo and avatar positions are hardcoded, don't track content stretching" — is a downstream consequence of this mismatch.

The fix is Option B (confirmed by orchestrator): make `headerMaxWidth` (or the `content` wrapper's `maxWidth`) a dynamic function of `windowWidth − leftDrawerWidth − rightSidebarWidth(when open)` rather than a static module-load constant.

A second file, `ChatHeaderView.tsx`, applies the same static `layout.headerMaxWidth` clamp and must receive the same fix.

## Reference Source (Contract C)

- **Tier**: tier_2_verified
- **Source**: React Native / CSS Flexbox standard: a `maxWidth` on a flex child constrains it to that value; when the value exceeds the parent's available width the flex algorithm clamps to the parent, but when it is `Infinity` or larger than the parent the child may render wider than the visible viewport portion. The correct pattern is to derive `maxWidth` from `useWindowDimensions().width` minus known sibling widths.
- **Location**: `packages/happy-app/sources/components/SidebarNavigator.tsx:21-24` (same pattern — `drawerWidth` is already computed dynamically from `windowWidth * 0.3`; we must apply the same pattern to the header's constraint)
- **Copy allowed**: yes
- **Dev constraint**: Do NOT read the static `layout.headerMaxWidth` property at the header call sites. Instead compute the effective header width dynamically in a hook or inline using `useWindowDimensions` + `useRightSidebar(s => s.isOpen)` + drawer-width formula. The static export `layout.headerMaxWidth` may be retained for non-header use or deprecated but MUST NOT remain the sole control point for header layout.

## Requirements (MoSCoW)

### Must Have

- R1: `Header.tsx` `content` style `maxWidth` must be computed dynamically at render time, tracking `windowWidth`, left-drawer state, and right-sidebar open/close state.
- R2: `ChatHeaderView.tsx` `content` style `maxWidth` must receive the same dynamic computation (same fix, same fix layer).
- R3: On desktop (≥ 901 px) with right sidebar open (450 px), header content must not overlap or extend into the sidebar panel.
- R4: On desktop with right sidebar closed, header content must fill the available main area up to any capped maximum (e.g. 1400 px on Mac / 800 px on web-tablet if those caps are still desired — but the caps must be applied AFTER subtracting sidebar widths).

## Edge Cases & Risks

- `layout.headerMaxWidth` is `Number.POSITIVE_INFINITY` on Mac: the new dynamic computation must preserve the effective "no cap" behaviour on Mac while still subtracting sidebar widths. Concretely: `Math.min(Infinity − subtracted, availableContentWidth)` simplifies to `availableContentWidth`; the code must not produce `NaN` or `Infinity` as the rendered value.
- `layout.ts` is a module-level constant evaluated at import time (before `useWindowDimensions` is available). The fix must NOT re-use `layout.headerMaxWidth` directly; it must call `useWindowDimensions()` at render time.
- `SidebarNavigator.tsx` drawer width formula uses `windowWidth * 0.3` clamped to `[250, 360]` — this changes only on tablet when the drawer is permanent. On phone/non-tablet the drawer is hidden (width 0 or rendered as front-modal). The dynamic header formula must handle the collapsed/hidden case (subtracted drawer width = 0).
- Right sidebar uses `DESKTOP_MIN_WIDTH = 901` to decide desktop vs mobile mode. The same threshold must be consistent in the header formula — below 901 px, do not subtract `SIDEBAR_WIDTH`.
- Both `Header.tsx` and `ChatHeaderView.tsx` must be updated; missing one leaves a broken header on some screens.

## Acceptance Criteria

### AC1: Right-sidebar open — header width shrinks to match

- GIVEN the app is open in a desktop-width browser (≥ 901 px)
- WHEN the right sidebar is opened (450 px panel appears on the right edge of the session view)
- THEN the header `content` row's effective width shrinks by 450 px, so logo and avatar remain within the main-area column, with no visual overflow into the sidebar panel

### AC2: Right-sidebar close — header width restores

- GIVEN the right sidebar is open
- WHEN the user closes the right sidebar
- THEN the header `content` row immediately expands back to fill the main-area width (up to any configured maximum)

### AC3: Left-drawer collapse — header width expands

- GIVEN the left drawer is expanded (permanent drawer on tablet/desktop)
- WHEN the user collapses the left drawer
- THEN the header `content` row expands to fill the newly available width in the same render pass

### AC4: Mobile layout unaffected

- GIVEN the viewport is < 901 px
- WHEN the right sidebar opens (as a full-screen modal)
- THEN the header layout is unchanged (no width subtraction applied)

### AC5: §5.5 second case — ChatHeaderView matches

- GIVEN the session view with its `ChatHeaderView` header is rendered
- WHEN the right sidebar opens
- THEN `ChatHeaderView`'s content row behaves identically to `Header.tsx` — no overflow, immediate reflow

## Technical Hints

**Affected files:**

1. `packages/happy-app/sources/components/layout.ts` — `getMaxWidth()` is a static function; the `layout.headerMaxWidth` export may be retained for backward compat but headers should stop using it.
2. `packages/happy-app/sources/components/navigation/Header.tsx:215` — replace static `maxWidth: layout.headerMaxWidth` in stylesheet with a dynamic inline style or hook.
3. `packages/happy-app/sources/components/ChatHeaderView.tsx:221` — same replacement.
4. `packages/happy-app/sources/components/RightSidebar.tsx:11` — `SIDEBAR_WIDTH = 450` and `DESKTOP_MIN_WIDTH = 901` — read these constants (or export them) for use in the header formula.
5. `packages/happy-app/sources/components/SidebarNavigator.tsx:21-24` — drawer width formula; header needs to replicate or import this.
6. `packages/happy-app/sources/stores/rightSidebarStore.ts` — `useRightSidebar(s => s.isOpen)` is the runtime signal for right-sidebar state.

**Recommended hook pattern** (dev to implement):

```typescript
// useHeaderMaxWidth.ts (new)
function useHeaderMaxWidth(): number {
    const { width: windowWidth } = useWindowDimensions();
    const rightSidebarOpen = useRightSidebar(s => s.isOpen);
    const isDesktop = windowWidth >= 901;  // DESKTOP_MIN_WIDTH from RightSidebar
    const { isTablet } = useIsTablet();    // or use windowWidth threshold
    
    const leftDrawerWidth = React.useMemo(() => {
        if (!isDesktop) return 0;
        // mirror SidebarNavigator formula
        return Math.min(Math.max(Math.floor(windowWidth * 0.3), 250), 360);
    }, [isDesktop, windowWidth]);
    
    const rightSidebarWidth = isDesktop && rightSidebarOpen ? 450 : 0;
    const availableWidth = windowWidth - leftDrawerWidth - rightSidebarWidth;
    
    if (isRunningOnMac()) return availableWidth;  // no fixed cap on Mac
    return Math.min(availableWidth, 800);         // tablet/web cap preserved
}
```

This hook should be called inside the header component and the result applied as an inline style override on the `content` container, overriding the stylesheet's static `maxWidth`.

**Unistyles note**: `StyleSheet.create` in Unistyles runs once; dynamic values must come from component-level code (inline style, `useStyles` override, or compound style array). Overriding a single property via `[styles.content, { maxWidth: dynamicValue }]` is the correct pattern.
