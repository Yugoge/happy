# BA Specification: Per-session model persistence + model indicator in status bar (§5.1)

**Request ID**: dev-20260424-143000-5
**Created**: 2026-04-24T14:30:00+00:00

## Goal

Mirror the permission-mode MMKV persistence plumbing for model-mode so that each session's last-selected model survives navigation away and back. Additionally, display the currently active model as a chip in the status-bar footer, immediately to the LEFT of the existing yolo/permission-mode badge.

## Context

The permission-mode plumbing already persists per-session choices to MMKV and reloads them on re-entry (storage.ts lines 320-339 / 834-862, persistence.ts lines 191-206). The model-mode updater (`updateSessionModelMode`, storage.ts:864-882) is asymmetric: it writes to Zustand in-memory state only, so any model pick is lost when the session is left and re-entered. The status-bar footer (AgentInput.tsx lines 770-904) shows the permission badge on the right side but has no model chip. This spec closes both gaps with a mechanical mirror of the permission-mode pattern.

## Requirements (MoSCoW)

### Must Have

- R1. `loadSessionModelModes()` and `saveSessionModelModes()` functions in `persistence.ts`, mirroring the permission-mode equivalents. MMKV key: `'session-model-modes'`.
- R2. Store init (`storage.ts:253-260`): call `loadSessionModelModes()` and assign to a local variable, exactly as `loadSessionPermissionModes()` is called and assigned to `sessionPermissionModes`.
- R3. `applySession` loop (`storage.ts:310-339`): resolve `modelMode` from the same four-priority chain as `permissionMode` — (1) existing in-memory value if non-default, (2) MMKV-saved value if non-default, (3) server-side `session.modelMode` if non-default, (4) `getDefaultModelKey(flavor)`. Assign to `mergedSessions[session.id].modelMode`.
- R4. `updateSessionModelMode` (`storage.ts:864-882`): after updating Zustand state, collect all non-default model modes across sessions and call `saveSessionModelModes(allModes)`, mirroring lines 848-856 of `updateSessionPermissionMode`.
- R5. Status-bar footer (`AgentInput.tsx:877-902`): insert a model chip `View` immediately BEFORE the permission badge `View`. The chip must: (a) show `props.modelMode?.name` as text at `fontSize: 11`, (b) use a distinguishing icon (e.g., `Ionicons name="cube-outline"` or `"layers-outline"`), (c) be hidden when `props.modelMode` is null/undefined or when its key equals `getDefaultModelKey` for the session flavor (i.e., only show when a non-default model is selected), (d) share the same `gap: 4`, `flexDirection: 'row', alignItems: 'center'` style as the permission badge.

### Should Have

- R6. The status-bar row visibility condition (`AgentInput.tsx:771`) currently gates on `displayPermissionMode && permissionModeKey !== 'default'`. Extend this condition to also show the row when a non-default model is active, so the footer appears even when permission mode is default but model is non-default.
- R7. The outer footer `View` condition should also account for the model chip: `(props.connectionStatus || contextWarning || (displayPermissionMode && permissionModeKey !== 'default') || (props.modelMode && props.modelMode.key !== getDefaultModelKey(...)))`.

### Could Have

- R8. Show a short abbreviated model name in the chip (e.g., strip the `claude-` prefix or use a pre-existing abbreviation from `modelModeOptions.ts`) to keep the status bar compact.

### Won't Have (Non-Goals)

- Changing the model automatically on reconnect, reload, or machine restart.
- Server-side persistence of the model choice (the field `session.metadata.currentModelCode` is server-controlled; `session.modelMode` local field is what we're persisting).
- Any changes to how the model picker overlay itself works (AgentInput.tsx lines 694-752).
- Any changes to model options or `getDefaultModelKey`.

## Edge Cases & Risks

- **Default key consistency**: `getDefaultModelKey(flavor)` returns `'default'` for claude/codex. The save function MUST skip persisting entries with key `'default'` (same as permission-mode skips `'default'`) to avoid cluttering MMKV.
- **Null flavor**: `session.metadata` may be null on initial load. `getDefaultModelKey(undefined)` returns `'default'` — safe.
- **Model chip overflows footer**: keep the chip text short; truncate with `numberOfLines={1}` if needed. Do not let the right cluster overflow past the available width.
- **Condition gate**: the outer footer row condition must be updated together with the model chip addition — if the condition is not updated, the chip will be invisible when permission mode is default.
- **MMKV key collision**: use `'session-model-modes'` exactly (not `'session-model-mode'`), matching the plural pattern of `'session-permission-modes'`.

## Acceptance Criteria

### AC1: Model persists across session navigation

- GIVEN a session is open and user selects a non-default model (e.g., "claude-opus-4") in the model picker
- WHEN user navigates to the sessions list and then back to the same session
- THEN the model picker shows "claude-opus-4" selected (not reverted to default), and the status-bar model chip displays "claude-opus-4" (or its abbreviated name)

### AC2: Model chip appears in status bar

- GIVEN a session has a non-default model selected
- WHEN the status-bar footer renders
- THEN a chip with the model name is visible immediately to the LEFT of the permission-mode badge (yolo/acceptEdits/etc.); if permission mode is default, the chip is still visible (the row shows on account of the model chip)

### AC3: Default model produces no chip

- GIVEN a session's model is the default (e.g., key `'default'`)
- WHEN the status-bar footer renders and permission mode is also default
- THEN the model chip is NOT rendered and the footer row is hidden (same as today's behaviour when both are default)

### AC4: Manual-only change

- GIVEN a model is stored for session X
- WHEN the user reconnects, navigates away and back, or the app is reloaded
- THEN the stored model for session X is unchanged (still the user's last GUI pick)
