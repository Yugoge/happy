# BA Specification: §5.9 Stop-Hook Feedback Suppression

**Request ID**: dev-20260424-143000-10
**Created**: 2026-04-24T14:30:00Z

## Goal

Stop-hook feedback messages (e.g. `Stop hook feedback: [python3 "$HOME/.claude/hooks/stop-spec-coverage-enforce.py"] … ERROR: No .md view files found`) are currently rendered as visible user-bubble messages in the conversation view. They must be silently discarded — never sent to the app, never rendered.

## Context

The Claude Code CLI emits stop-hook output as a `user` JSONL message with `message.content` (string) starting with `"Stop hook feedback:\n"`. The happy-cli `sessionProtocolMapper.ts` already has a `getSystemInjectedServiceText()` function that silently swallows other internal-protocol strings (e.g. `<task-notification>`, `[Request interrupted`, `API Error:`). This function simply lacks a case for the `"Stop hook feedback:"` prefix, so these messages pass through unchanged and arrive in the app as real user-bubble text.

## Requirements (MoSCoW)

### Must Have

- R1: Any `user`-type JSONL message whose string content starts with `"Stop hook feedback:"` must be silently discarded — no envelope emitted, nothing sent to the app.
- R2: The suppression must cover ALL stop-hook variants regardless of the hook script name, severity marker (✅/❌/⚠️), or hook type (Python, shell, other). The common denominator is the `"Stop hook feedback:"` prefix emitted by the Claude Code CLI for ALL stop-hook output.
- R3: The fix must NOT suppress any message that does NOT start with `"Stop hook feedback:"`.

### Should Have

- The change should be confined to `getSystemInjectedServiceText()` in `sessionProtocolMapper.ts`, matching the existing pattern of prefix-based suppression already present in that function.

### Could Have

- A unit test in `sessionProtocolMapper.test.ts` verifying that a user message with `Stop hook feedback:` content produces zero envelopes.

### Won't Have (Non-Goals)

- Any logging or telemetry of stop-hook output (out of scope — pure suppression only).
- Changes to the app render layer (happy-app) — not needed if the CLI layer is fixed correctly, because the message will never reach the app.
- Capturing/forwarding stop-hook output to a dev log (separate concern).

## Edge Cases & Risks

- **False positive**: A legitimate user message starting with the exact string `"Stop hook feedback:"` would be swallowed. This is an acceptable trade-off — a real user would never type this as the literal start of a message (it is an internal CLI marker).
- **Array-content variant**: The existing code only checks `typeof message.message.content === 'string'`; the observed JSONL records confirm stop-hook output is always emitted as a plain string content, not array. No additional handling needed.
- **Future hook scripts**: The `"Stop hook feedback:"` prefix is emitted by the Claude Code CLI itself for all stop-hook output, not by individual scripts. If Anthropic changes this prefix, the filter would need updating — but this is not a current risk.

## Acceptance Criteria

### AC1: Stop-hook message produces zero envelopes

- GIVEN a JSONL user message with `message.content = "Stop hook feedback:\n[python3 \"$HOME/.claude/hooks/stop-spec-coverage-enforce.py\"]: \nSPEC COVERAGE ENFORCEMENT: spec-verify.py reports < 100% coverage."`
- WHEN `mapClaudeLogMessageToSessionEnvelopes()` processes it
- THEN the result contains exactly 0 envelopes (message is silently discarded)

### AC2: Regular user messages are unaffected

- GIVEN a JSONL user message with `message.content = "Hello, what can you do?"`
- WHEN `mapClaudeLogMessageToSessionEnvelopes()` processes it
- THEN the result contains exactly 1 envelope with `role: 'user'`, `ev.t: 'text'`

### AC3: Partial-prefix match does NOT suppress

- GIVEN a JSONL user message with `message.content = "About stop hook feedback: this is a comment"`
- WHEN `mapClaudeLogMessageToSessionEnvelopes()` processes it (note: does NOT start with the exact prefix)
- THEN the result is NOT suppressed (a user envelope is produced)
