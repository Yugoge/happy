# BA Specification: Session Watcher Ignores Intentional Archive

**Request ID**: dev-20260408-120000
**Created**: 2026-04-08T12:00:00+08:00

## Goal

Prevent the session watcher from auto-restoring sessions that the user intentionally archived from the app UI. Currently, archiving a session kills its CLI process, which the watcher detects as a "session disappeared" event and blindly restores -- undoing the user's action and spawning sessions under potentially the wrong daemon.

## Context

The session recovery system (`/root/bin/happy-session-recovery.sh`) was designed to recover sessions after daemon crashes or reboots. Its `watch` loop polls running processes every 60 seconds and triggers `restore_online_sessions` whenever the session count drops. This is correct for crash recovery but incorrect for intentional user actions (archive, delete, natural completion).

When the user archives session `1140deaf` from the app UI:
1. App sends `killSession` RPC to the CLI process (via `sessionKill` in `ops.ts`)
2. CLI kills itself (`registerKillSessionHandler.ts` calls `killThisHappy()`)
3. Daemon's `onChildExited` notifies server the session ended
4. 60s later, watcher's `scan_running_sessions` sees fewer processes
5. Watcher unconditionally triggers `restore_online_sessions` (line 642-644)
6. Peak protection merges the archived session back into the snapshot
7. Restore spawns the session again, potentially under the wrong daemon

## Requirements (MoSCoW)

### Must Have
- Watcher must distinguish intentional session removal (archive/delete/kill via UI) from unexpected disappearance (crash)
- Sessions archived/killed via app UI must NOT be auto-restored
- The fix must not break crash recovery (sessions that disappear due to process crash must still be restored)

### Should Have
- A lightweight signaling mechanism between the kill/archive action and the watcher (e.g., a "recently-archived" file the watcher checks before restoring)
- Logging that clearly indicates when a session was skipped due to intentional archive vs restored due to crash

### Could Have
- Server-side session state query: watcher checks server API for session lifecycle state before restoring (archived/deleted sessions are skipped)
- Grace period: wait one extra poll cycle before restoring, giving the archive signal time to propagate

### Won't Have (Non-Goals)
- Changes to the app UI archive/delete flow itself
- Changes to the daemon's `onChildExited` or server-side session lifecycle
- Migration to a daemon-integrated watcher (the bash script approach is retained)

## Edge Cases & Risks

- **Race condition**: Archive signal must be written BEFORE the process dies, or watcher may poll in between
- **Stale signals**: If the signal file is not cleaned up, future sessions with the same UUID could be incorrectly skipped
- **Multiple daemons**: The signal must be scoped correctly so it reaches the right watcher context
- **Peak protection interaction**: Even if watcher skips restore, peak protection still merges old snapshots -- the archived session must also be excluded from peak merge
- **killSession RPC failure**: If RPC fails (CLI already dead), app falls back to server-side archive -- watcher still sees process disappear

## Acceptance Criteria

### AC1: Intentional archive does not trigger restore
- GIVEN a session is running and tracked by the watcher
- WHEN the user archives it from the app UI (killSession RPC)
- THEN the watcher detects the session disappearance but does NOT trigger restore for that session

### AC2: Crash recovery still works
- GIVEN a session is running and tracked by the watcher
- WHEN the CLI process crashes unexpectedly (SIGKILL, OOM, etc.)
- THEN the watcher detects the disappearance and restores the session normally

### AC3: Peak protection excludes archived sessions
- GIVEN a session was recently archived
- WHEN peak protection merges snapshots
- THEN the archived session is excluded from the merged result

### AC4: Signal cleanup
- GIVEN a session archive signal exists
- WHEN the signal is older than 1 hour (or configurable TTL)
- THEN the signal is automatically cleaned up

## Technical Hints

- **Primary file to modify**: `/root/bin/happy-session-recovery.sh`
  - `watch_sessions()` (line 642): Add check before triggering restore
  - `update_snapshot_with_peak_protection()` (line 384): Exclude archived UUIDs from peak merge
  - `restore_online_sessions()` (line 761): Skip sessions in the recently-archived list
- **Signal mechanism option A (recommended)**: Write a file per archived UUID to a known directory (e.g., `$HOME/.happy/archived_sessions/`) when `killSession` RPC is received. Watcher checks this dir before restoring. CLI writes the signal in `registerKillSessionHandler.ts` BEFORE calling `killThisHappy()`.
- **Signal mechanism option B**: Daemon writes to a shared file when `onChildExited` is called for a session that was killed via RPC (vs crashed). Requires daemon code changes.
- **Signal mechanism option C**: Watcher queries server API `GET /v1/sessions/:id` to check `lifecycleState` before restoring. Most robust but adds network dependency.
- **Related patterns**: Bug #61 scoped recovery per-daemon (commit `79cf62b5`)
