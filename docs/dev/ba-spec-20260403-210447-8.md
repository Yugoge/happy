# BA Specification: Fix Session Navigation on Web

**Request ID**: dev-20260403-210447-8
**Created**: 2026-04-03T21:04:47Z

## Goal

Fix two navigation bugs on web: (1) direct URL navigation to a session redirects to the wrong page (Settings or another session), and (2) pressing the back button from the tool detail view (`/session/:id/message/:msgId`) navigates to the wrong page instead of returning to the parent session.

## Context

The app uses Expo Router v6 with a Drawer (sidebar) + Stack navigation architecture. Session navigation uses `router.navigate()` with `dangerouslySingular` to ensure only one session screen exists in the stack at a time. The tool detail view at `/session/[id]/message/[messageId]` uses `router.back()` to return. On web, the browser history and React Navigation stack can become desynchronized, causing both bugs.

**Key architectural details**:
- `SidebarNavigator.tsx` wraps a `Drawer` from `expo-router/drawer` which contains the Stack
- `(app)/_layout.tsx` defines a `Stack` with `initialRouteName='index'`
- `session/[id].tsx` reads `route.params.id` via `useRoute()` (React Navigation API, not Expo Router)
- `navigateToSession()` uses `router.navigate()` with `dangerouslySingular` returning `'session'`
- `ToolView.tsx` pushes to `/session/${sessionId}/message/${messageId}` via `router.push()`
- `[messageId].tsx` calls `router.back()` when message not found after load
- `SessionView.tsx` back button uses `router.back()`

**Root cause analysis**:
1. **Direct URL navigation failure**: When navigating directly to `/session/<id2>` on web (e.g., via address bar or deep link), the Stack navigator's `initialRouteName='index'` means the index route is the initial screen. However, on web with Expo Router, direct URL navigation should hydrate the correct route. The issue is likely that `dangerouslySingular` with `router.navigate()` replaces the existing session screen when navigating from sidebar, but direct URL navigation bypasses this mechanism. The `useRoute()` call in `session/[id].tsx` (React Navigation API) instead of `useLocalSearchParams` (Expo Router API) may cause params to not update correctly when the route is reused via `dangerouslySingular`.
2. **Back button from tool detail**: `router.back()` pops the browser history stack, which on web may not correspond to the React Navigation stack. If the user navigated to the session via sidebar (which uses `navigate` not `push`), there may be no proper back entry to the parent session.

## Requirements (MoSCoW)

### Must Have
- Direct URL navigation to `/session/<id>` must load and display that specific session on web
- Back button from `/session/:id/message/:msgId` must return to the parent session `/session/:id`
- Session switching via sidebar must continue to work correctly (using `dangerouslySingular`)

### Should Have
- Use `useLocalSearchParams` consistently instead of `useRoute()` for reading route params in Expo Router screens
- Back navigation from tool detail should use `router.navigate` to parent session as a fallback when `router.back()` would go to the wrong place

### Could Have
- Add a web-specific navigation history guard that detects and corrects mismatched back navigation

### Won't Have (Non-Goals)
- Changing the Drawer/Stack architecture
- Native mobile navigation fixes (issue is web-specific)
- Adding browser history manipulation beyond what Expo Router provides

## Edge Cases & Risks

- `dangerouslySingular` is an undocumented/internal Expo Router API -- behavior may change across versions
- `encodeURIComponent` on session IDs with special characters may cause URL mismatch on direct navigation
- The `useRoute()` vs `useLocalSearchParams` mismatch in `session/[id].tsx` means the component may not re-render when params change via `dangerouslySingular` navigate
- `router.back()` in `[messageId].tsx` (line 51) when message not found could cause unexpected navigation if the back stack is empty

## Acceptance Criteria

### AC1: Direct URL navigation loads correct session
- GIVEN the user is authenticated on web
- WHEN they navigate directly to `/session/<session2-id>` via the address bar
- THEN session 2 is displayed (not Settings, not session 1, not a redirect)

### AC2: Back from tool detail returns to parent session
- GIVEN the user is viewing a tool detail at `/session/<id>/message/<msgId>`
- WHEN they press the back button
- THEN they return to `/session/<id>` showing the correct session

### AC3: Sidebar session switching still works
- GIVEN the user is viewing session 1
- WHEN they click session 2 in the sidebar
- THEN session 2 is displayed and the URL updates to `/session/<session2-id>`

### AC4: Param reactivity on session change
- GIVEN the session screen is already mounted
- WHEN the route params change (via `dangerouslySingular` navigate)
- THEN the SessionView re-renders with the new session ID

## Technical Hints

- Affected files:
  - `packages/happy-app/sources/app/(app)/session/[id].tsx` -- uses `useRoute()` instead of `useLocalSearchParams`
  - `packages/happy-app/sources/hooks/useNavigateToSession.ts` -- `dangerouslySingular` navigation
  - `packages/happy-app/sources/app/(app)/session/[id]/message/[messageId].tsx` -- `router.back()` back navigation
  - `packages/happy-app/sources/components/tools/ToolView.tsx` -- `router.push()` to message detail
  - `packages/happy-app/sources/-session/SessionView.tsx` -- session view with `router.back()`
  - `packages/happy-app/sources/app/(app)/_layout.tsx` -- Stack screen definitions
- Primary fix: Change `session/[id].tsx` to use `useLocalSearchParams` instead of `useRoute()` for param reading
- Secondary fix: In `[messageId].tsx`, replace `router.back()` with `router.navigate(`/session/${sessionId}`)` to ensure correct back navigation regardless of browser history state
- Related patterns: Other screens like `files.tsx` already use `useLocalSearchParams` correctly
