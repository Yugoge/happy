### 5.3 — Bash popup overflow — 实测 FAIL（QA 报告 PASS）

**QA 当初的测量**
```
Desktop viewport: 1920px
Bash 卡片在主区域，弹窗右侧打开
测量发现：scroll 祖先 left=530, right=1290, width=760
         scroll 祖先 scrollWidth=1373，clientWidth=760
         overflow-x: auto
声称：命令文本被包裹在 overflow-x:auto 容器中，滚动条可见 ✓
```

**QA 的错误**
- QA 找到的那个 scroll 容器（l=530, r=1290）**在主区域消息卡中**，不是在右侧面板中！
- 用户打开右侧 Bash 详情面板后，是在**另一个地方**看命令文本
- 右侧面板本身的 Bash 卡 width=1065px（超出面板宽度 450px）

**我的重测结果**
```
右侧面板（Bash details）：
- 面板 width=450px（正常）
- 但右侧面板内的 Bash 卡 width=1065px（溢出！）
- Bash 卡 right=2564，超出视口 1920（超出 644px）
- 没有滚动条，命令文本被截断

主区域 Bash 卡：
- 有 scroll 祖先，scrollWidth=1373 > clientWidth=760 ✓
- 但这不是用户抱怨的"popup"——用户说的是右侧面板
```

**正确判定**
- **FAIL**
  - 右侧面板（用户实际看到的）**没有滚动条**，内容溢出
  - 主区域卡片中*有*滚动容器，但这不是用户抱怨的对象
  - QA 选错了被测容器，把主区域的"正常情况"当成了右侧面板的"成功"

**QA 看错的具体原因**
- 5.3 QA 报告中说"scroll_ancestor_right_px=1280, popup_right=1280"
- 这个 1280 实际上是主区域的某个容器右边界，**不是右侧面板的边界**
- 右侧面板应该在 viewport right=1920 附近，但被测的 scroll 容器只到 1290
- QA 混淆了两个不同物理位置的容器

### 5.5 — 顶栏第二个不响应案例 — 实测 FAIL（QA 报告 PASS）

**QA 当初的逻辑**
- 测试右侧 Bash panel toggle：开/关
- 测试 viewport resize：1280↔390
- 测试 viewport resize：768↔1280
- 声称所有这些 toggle 中，title 和 avatar 都有"位置变化"

**QA 的错误**
- **位置变化 ≠ 正确响应**
- 根本原因：top-bar 内部容器有 `max-width: 800` 居中的约束（见 5.4 报告）
- 虽然 title/avatar 确实在 resize，但它们在一个**固定 800px 宽的容器内**伸缩
- 结果：toggle 后元素**聚拢**而非**展开**，视觉上是"反向的"

**用户的观察**
- "toggle 后元素反而聚拢而不是适应"
- 这正是 max-width=800 centered 的表现

**与 5.4 的同根因**
- **是**。都是 top-bar content container max-width=800 hardcoded
- 5.4：avatar 在宽视口（1920）离开了右边界，留下 394px 空白
- 5.5：sidebar toggle 时，元素在 800px 容器内挤动，看起来反向

**QA 的具体错误**
- 5.5 QA 报告显示：right_sidebar_toggle 时，avatar 从 right=1041 → right=1206（移动 +165px）
- QA 声称："avatar shifts right 时，这说明元素响应了"
- **但忽视了**：整个外部容器本身是 max-width=800 centered，所以绝对位置变化只是容器内的重新分布
- 用户期望的是：当 bash panel 关闭时，content area 变大，avatar 应该跟着**流动到更右**
- 实际上：avatar 只是在 800px 容器内往右移了些，**不是跟着 content area 扩展**

**正确判定**
- **FAIL**
  - 虽然元素有响应，但响应方向"错了"（聚拢 vs 展开）
  - 根本原因同 5.4：top-bar max-width=800 constraint
  - 需要移除这个 constraint，让 top-bar 容器充满可用宽度

### 5.18 — CronList 卡片 — 实测 FAIL（QA 报告 PASS）

**QA 当初的结论**
```
inline 卡片：只显示 "CronList" （8-10 字符）
侧边栏打开后：显示 Description | Input Parameters {} | Output
声称：PASS（符合简化 + sidebar detail 的要求）
```

**用户的原始诉求**
- "学习 bash + subagent 的渲染模式**展示 input 就行**"
- 参考 Bash 卡的 inline 形式：`$ <command>`
- **关键点**：bash inline 包含了**命令本身（input）**，不只是工具名

**QA 的错误**
- 理解错了"展示 input 就行"
- 把"简化"理解成"删除 input 行"
- 实际上用户想要：`CronList: {}` 或 `CronList (${})`（类似 bash 的 `$ ls ...` 格式）
- 而不是只显示 "CronList" 三个字

**我的重测**
```
当前 inline CronList 卡：只有文字 "CronList" （8 字符）
Bash 卡的 inline（参考标准）：`$ ls /root/...` （包含 input）
```

**对比标准**
| 工具 | 当前 inline | 应该是 inline |
|------|----------|----------|
| Bash | `$ ls /root/...` | ✓ 包含 command input |
| CronList | `CronList` | ✗ 缺少 input (`{}`) |

**QA 的具体错误**
- 5.18 QA 报告说"inline_text_length_chars = 10, inline_contains_INPUT_label = false"
- QA 以为"只显示工具名"是"简化"的体现，符合用户要求
- **但用户的意思是**："保留 input，不显示完整 OUTPUT"
- 用户想要的是 **input 行**，而不是"简化到什么都没有"

**正确判定**
- **FAIL**
  - inline 应该包含 input（哪怕只是 `{}`），不能只有工具名
  - 应该改成：`CronList: {}` 或 `CronList ({})`，保持与 Bash 卡一致的模式
