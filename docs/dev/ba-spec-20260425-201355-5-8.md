# BA Specification: 5.8 — Message-card wrapper width mismatches actual content width on mobile

**Request ID**: dev-20260425-201355-5-8
**Created**: 2026-04-25T20:18:00Z
**Spec Item**: 5.8 (single, no multitask)

---

## Goal

Fix the message-card / message-content wrapper-width logic so that, at narrow
viewports (mobile 390×844), neither agent-message paragraphs, user-message
bubbles, nor inline tool-call cards (Bash, etc.) overflow the visible
horizontal bounds. The Cycle 5 PASS for the `<table>` element only addressed
one symptom; the wrapper-width logic itself is still wrong for both desktop
and mobile.

## Context

`docs/dev/specs/spec-20260424-084848.md` §5.8 (line 1567) ports the
production happy fix for "wide markdown tables overflow". Cycle 5 (line 2626)
PASSED the table case (`overflow-x:auto` wrapper around the `<table>`), but
the user objected (line 2851-2856): on the message-card surrounding the table
the **wrapper width does not match the actual rendered content width**, and
on mobile (390×844) **even normal paragraph text overflows the card**. The
correction-section (line 2895-2896) explicitly notes this is "a deeper
layout bug related to markdown container width logic".

A prior commit `a59b3795` (2026-03-25, "fix: table font mismatch and mobile
overflow on web") already added `minWidth: 0` on `messageContent`,
`maxWidth: '100%'` + `overflow: 'hidden'` on `agentMessageContainer`, and
the `min(100%, calc(100vw - 32px))` web-table wrapper. Those changes are
still present in the tree but they were applied **only to agent messages
and the table block**. The remaining wrapper surfaces (`userMessageContainer`,
`toolContainer`, and the static `layout.maxWidth = 800`) were not updated.

## Evidence (Contract A)

- **Observed (verbatim)**: "message-card wrapper max-width mismatches actual
  content width. Mobile viewport (390px) shows even normal paragraph text

- **Measured (live, this BA cycle 2026-04-25T20:18Z)**:
  - `MessageView.tsx:215` declares `maxWidth: layout.maxWidth` on the
    `messageContent` View. `layout.maxWidth` comes from `layout.ts:6-21`
    `getMaxLayoutWidth()` which on web returns the **static literal `800`**
    evaluated **once at module load**. It is NOT a hook, NOT reactive to
    `useWindowDimensions()`, NOT recomputed on resize.
  - At desktop viewport 1440×900 (Playwright + DevTools getComputedStyle),
    `messageContent` has `width=800, scrollWidth=816, clientWidth=800,
    overflowX=visible, maxWidth=800px` — i.e., **child intrinsic width is
    16px wider than the card itself**, and there is NO clipping at this
    layer.
  - At mobile viewport 390×844 (screenshot
    `docs/dev/evidence/ba-20260425-201355-5-8/mobile-conversation.png`),
    the **inline Bash tool-call card** clearly cuts off its command text:
    `$ ls /root/docs/dev/ba-spec-20260423-080` is visibly truncated at the
    right edge of the visible card; output line `ls: cannot access
    '/root/.claude/dev-regist` is similarly clipped.
  - `MessageView.tsx:217-223 userMessageContainer` has `maxWidth: '100%'`
    and the inner `userMessageBubble` has `maxWidth: '100%'`, but neither
    has `overflow: 'hidden'`, so child blocks (inline code, long URLs,
    pre-formatted text) can still extend beyond the bubble.
  - `MessageView.tsx:249-251 toolContainer` has only `marginHorizontal: 8`.
    No `maxWidth`, no `overflow: 'hidden'`. This is the wrapper that
    contains every inline tool-call card (Bash, CronList, etc.) and is
    therefore the surface that lets the Bash command line bleed past the
    viewport on mobile.
  - The component chain inside the **agent message path** (which DOES
    have wrapper protection) showed at viewport 390 a paragraph SPAN at
    `x=16, w=137` and the parent depth-1 `agentMessageContainer` at

    showed `messageContent.width=800, scrollWidth=816` — the 16px overflow
    is intrinsic to children in the table case, but is NOT clipped because
    `messageContent.overflowX = visible`.
- **Expected** (from `/root/happy` production behaviour and from the spec
  acceptance line 1576): every wrapper at every viewport must clip or
  scroll its child to its own bounds. `card.right ≤ viewport.innerWidth` for
  all wrapper types (agent text, user text, tool inline card) at every
  supported breakpoint.
- **Gap**:
  - Desktop: `messageContent` allows 16px child overflow (visible) at the
    table block.
  - Mobile (390): `toolContainer` and `userMessageContainer` have no
    `overflow: hidden`, so inline tool-call cards (Bash command, CronList
    output) can extend past the viewport right edge.
  - Static `layout.maxWidth = 800` at module load means `messageContent`
    will not respond to window resize; on Mac it returns 1400, on web 800,
    on RN phone the largest dimension. None of these are reactive to
    `useWindowDimensions()`.

### Novelty Check
- **This attempt's layer**: **L2 + L3**
  - **L2 (structural / responsive layout)**: replace static
    `layout.maxWidth = 800` (used at `MessageView.tsx:215` for the
    `messageContent` cap) with a hook `useMessageContentMaxWidth()` modeled
    on `useHeaderMaxWidth()`, so the cap reflows on resize and
    sidebar-toggle, and apply `overflow: 'hidden' + maxWidth: '100%'` to
    the missing wrapper styles `userMessageContainer` and `toolContainer`.
  - **L3 (data values)**: tweak the per-wrapper data values:
    `userMessageContainer.overflow: 'hidden'`,
    `userMessageBubble.overflow: 'hidden'`,
    `toolContainer.maxWidth: '100%' + overflow: 'hidden'`. These three
    style-data lines are tier_2_verified pattern-copies of the existing
    `agentMessageContainer` block at `MessageView.tsx:232-239`.
- **Differs from all priors**: yes.
  - Attempt 1 was L1+L3 on the **table** alone; this attempt is L2 on the
    **container framework** + L3 on the missing **wrapper siblings**.

    flagged (line 2896 of monolith).
- **Rationale**: prior attempts mistook a single-element overflow rule for

## Edge Cases & Risks

- **Hook on Mac**: `useHeaderMaxWidth` returns `available` (uncapped) on
  Mac. The new `useMessageContentMaxWidth()` MUST preserve the same Mac
  uncapped behaviour — Mac users run wide windows and expect message text
  to fill them.
- **SSR / first-paint**: `useWindowDimensions()` returns `0×0` during
  the very first SSR render (web). Hook MUST guard against zero/NaN
  (`Math.max(1, available)` or fall back to `WEB_TABLET_MAX_WIDTH_CAP`
  when `windowWidth === 0`).
- **Right-sidebar open on narrow desktop**: when right-sidebar opens at
  windowWidth ≥ 901 the hook subtracts 450; below that the sidebar is a
  full-screen modal so the subtraction must NOT apply (existing
  `useHeaderMaxWidth` already handles this — preserve).
- **`flexBasis: 0` interaction**: `messageContent` has `flexGrow: 1,
  flexBasis: 0, minWidth: 0`. With these, `width = min(parent_flex_share,
  maxWidth)`. Reducing `maxWidth` from a static 800 to a smaller dynamic
  value at narrow viewports MUST not introduce a regression where
  `messageContent` becomes narrower than necessary on desktop. The hook
  formula caps at 800 so desktop is unchanged when sidebars are closed.
- **Tool-call cards with horizontal-scrollable code blocks** (Bash output,
  syntax-highlighted code): adding `overflow: 'hidden'` to `toolContainer`
  must not eat the existing internal `<ScrollView horizontal>` inside
  code blocks. `overflow: 'hidden'` on the wrapper clips visual overflow
  AT the wrapper boundary; nested scroll containers inside still work
  (this is the same pattern `agentMessageContainer` already uses).
- **Pre-existing guards** (Contract — see JSON `pre_existing_guards`):
  the existing `agentMessageContainer.overflow: 'hidden'` and
  `messageContent.minWidth: 0` MUST NOT be removed or weakened.
