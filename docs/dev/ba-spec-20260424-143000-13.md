# BA Specification: Attachment Tray — Layout Inconsistency + Silent Upload Failure (§5.12)

**Request ID**: dev-20260424-143000-13
**Created**: 2026-04-24T14:30:00Z

## Goal

Fix two independent bugs in the message-composer attachment tray: (1) unify the chip layout so file and image thumbnails share a single visual primitive with consistent padding, gutter, and box sizing; (2) surface upload failures (size, network, MIME) to the user with a readable error instead of silently discarding the failed attachment on send.

## Context

The attachment tray (`AttachmentStrip.tsx`) was introduced in commit `f8b208fa` (2026-03-23). In a later auto-commit (`f6f129a1`, 2026-03-25) the strip's padding was changed from `paddingHorizontal: 12 / paddingVertical: 6` to `padding: 12` and the overlay's `left` was changed from `0` to `4`. This created the visual inconsistency reported by the user. The silent-failure path has been present since the initial commit: `pickImage`, `pickDocument`, and `addFileFromPaste` all return silently when `size > MAX_UPLOAD_BYTES` without informing the user; and even when the server returns a 413, the `AttachmentChip` renders an error icon overlay but the `useComposerSend` path ignores error-state attachments and sends the message anyway with `clearAttachments()` silently removing the failed items.

## Evidence (Contract A)

### Bug 1 — Layout Inconsistency

- **Observed**: "文件和图片顶部宽度和左右宽度仍然不统一" (file and image top/side widths are still inconsistent)
- **Measured**:
  - `AttachmentStrip.tsx:59` `strip.padding: 12` (uniform padding, equal top/bottom/left/right) — this gives the strip 12px padding on all four sides
  - `AttachmentStrip.tsx:62-66` `chip { marginRight: 8, width: 72, alignItems: 'center' }` — chip is 72px wide
  - `AttachmentStrip.tsx:67-72` `preview { width: 64, height: 64 }` — image thumbnail is 64px
  - `AttachmentStrip.tsx:73-80` `fileIcon { width: 64, height: 64 }` — file box is 64px (matches image)
  - `AttachmentStrip.tsx:84` `overlay.left: 4` — overlay is shifted 4px right from position 0 inside the chip
  - Gap: chip width (72) minus thumbnail width (64) = 8px, all allocated to `marginRight`. The thumbnail box is left-aligned (no centering), not centered within the chip. The overlay `left: 4` does not align with the thumbnail boundary at `left: 0`.
- **Expected**: thumbnail box centered within the chip with equal side padding; overlay aligned to `left: 0` to cover the thumbnail exactly; strip padding should be `paddingHorizontal: 12, paddingVertical: 8` (asymmetric to match typical chip strips); `chip.marginRight` renamed to a symmetric gutter; a single `THUMB_SIZE = 64` constant used by `preview`, `fileIcon`, `overlay`, and `name` to guarantee type-level alignment.
- **Gap**: `overlay.left` is 4px off from the thumbnail's left edge; chip width is 8px wider than thumbnail with no centering; strip has excess vertical padding (12px vs typical 8px).

### Bug 2 — Silent Oversize Upload Failure

- **Observed**: "文件太大了无法上传并且没有报错" (file too large cannot upload, no error shown)
- **Measured**:
  - `useAttachments.ts:22` `MAX_UPLOAD_BYTES = 10 * 1024 * 1024` (10 MB client constant)
  - `useAttachments.ts:175` `if ((asset.fileSize ?? 0) > MAX_UPLOAD_BYTES) return;` — silently returns, no error surfaced
  - `useAttachments.ts:190` same silent `return` in `pickDocument`
  - `useAttachments.ts:201` same silent `return` in `addFileFromPaste`
  - `v3SessionRoutes.ts:267-269` server also enforces `maxBytes = 10 * 1024 * 1024` and returns HTTP 413 with `{ error: 'File too large (max 10 MB)' }`. If somehow a file reaches the server, the error IS caught in `uploadFile` (lines 157-159) and sets `status: 'error'` on the attachment.
  - `SessionView.tsx:440-447` `useComposerSend`: `att.hasAttachments` is `attachments.length > 0` (includes error-state items), but `att.readyAttachments` filters to `status === 'ready'` only. On send: message goes out, `att.clearAttachments()` removes all items including error-state ones — silent discard.
- **Expected**: when size check fails client-side, show `Modal.alert` with "File exceeds 10 MB limit. Please choose a smaller file." Before clearing attachments on send, check for any `status === 'error'` items and show an alert listing them, blocking send until user removes the failed items.
- **Gap**: three silent-return callsites + one silent-discard on send.

## Requirements (MoSCoW)

### Must Have

**Cluster A — Layout**
- A1. Define a single `THUMB_SIZE = 64` constant in `AttachmentStrip.tsx` and use it for `preview.width/height`, `fileIcon.width/height`, `overlay.width/height`, and `name.width`.
- A2. Set `overlay.left = 0` (align overlay exactly with the thumbnail's left edge).
- A3. Set `chip` to `width: THUMB_SIZE + 8` (72, unchanged) with `alignItems: 'center'` so the thumbnail is centered; OR reduce `chip.width` to `THUMB_SIZE` (64) and move the gutter to `marginRight: 8`. Either is acceptable; must be consistent between image and file chips. The chosen approach must be identical for `preview` and `fileIcon`.
- A4. Set `strip` padding to `paddingHorizontal: 12, paddingVertical: 8` (reduce vertical padding from 12 to 8 to match standard chip-strip proportions).

**Cluster B — Error Surfacing**
- B1. In `pickImage` (line 175), `pickDocument` (line 190), and `addFileFromPaste` (line 201): replace the silent `return` with a `Modal.alert` call showing the user-readable error: title `t('common.error')`, message `t('session.attachmentTooLarge')`. Add the translation key `attachmentTooLarge` to all 9 language files.
- B2. In `useComposerSend` (`SessionView.tsx`): before calling `sync.sendMessage`, check `att.attachments` for any `status === 'error'` items. If any exist, call `Modal.alert` with the error message from the first failed attachment (or a generic "Some files failed to upload. Please remove them before sending.") and return early without sending.
- B3. Add translation key `attachmentUploadFailed` ("Some files failed to upload. Remove them before sending.") and `attachmentTooLarge` ("File exceeds 10 MB limit.") to all 9 language files (`en`, `zh-Hans`, `zh-Hant`, `ru`, `pl`, `es`, `ca`, `it`, `pt`, `ja`).

### Should Have

- S1. When the server returns a 413 (already caught in `uploadFile` catch block and sets `status: 'error'`), the error message stored at `attachment.error` already contains `"File too large (max 10 MB)"` from the server. The `Modal.alert` on send (B2) should prefer `attachment.error` as the message body when available, to surface the server-authoritative text.
- S2. The `AttachmentChip` error overlay currently shows only an icon (`alert-circle`). Add a small text label below the icon reading "Failed" (already-themed `theme.colors.textSecondary`, `fontSize: 8`) to make the error state more discoverable without relying on color alone.

### Could Have

- C1. Add a tap-handler on the error-state chip that shows the full `attachment.error` message in a `Modal.alert`, allowing the user to see the exact reason inline.

### Won't Have (Non-Goals)

- No changes to the server upload route (it already returns the correct 413 + error text).
- No changes to the `MAX_UPLOAD_BYTES` constant value.
- No new animations or transitions on the chip state changes.
- No retry mechanism for failed uploads.

## Edge Cases & Risks

- **pickImage `fileSize` undefined**: `asset.fileSize` may be `undefined` on some image pickers. The silent-return check already guards `(asset.fileSize ?? 0) > MAX_UPLOAD_BYTES`. The `Modal.alert` path must also guard: only show the alert when `fileSize` is known and exceeds the limit; if `fileSize === undefined`, allow the upload to proceed (server will 413 if too large).
- **Concurrent picks**: user may pick multiple files rapidly. Each `pickImage`/`pickDocument` call is independent; the modal alert on one should not block future picks.
- **Translation key naming**: all new keys must be placed inside the `session` namespace (consistent with neighboring keys like `session.inputPlaceholder`) to avoid polluting the top-level namespace.
- **i18n for all 9 languages**: dev must add keys to all 9 translation files. Suggest using the `i18n-translator` agent for the non-English translations.

## Acceptance Criteria

### AC1: Layout — image and file chips are visually identical frames

- GIVEN a pending attachment tray with both an image attachment and a file attachment
- WHEN the tray renders
- THEN both chips have the same visible bounding box, the overlay sits flush over the thumbnail (not offset 4px), and horizontal spacing between chips is uniform

### AC2: Oversize client-side block with modal

- GIVEN the user picks an image or file larger than 10 MB
- WHEN the picker returns the selected asset
- THEN a `Modal.alert` is shown immediately with the translated error message and the chip is NOT added to the tray (silent discard is replaced by a visible block)

### AC3: Send blocked when error-state attachments present

- GIVEN an attachment has status `error` in the tray (due to network failure, server 413, or any other upload failure)
- WHEN the user presses Send
- THEN send is blocked, a `Modal.alert` is shown listing the failed attachment(s) and prompting removal, and no message is dispatched

### AC4: Non-regression — successful attachments unaffected

- GIVEN a successfully-uploaded attachment (status `ready`)
- WHEN the user presses Send
- THEN the message sends normally with the attachment metadata, identical to today's behaviour

## Technical Hints

- **Affected files**:
  - `packages/happy-app/sources/components/AttachmentStrip.tsx` — layout constants (Bug 1)
  - `packages/happy-app/sources/hooks/useAttachments.ts` — silent-return callsites lines 175, 190, 201 (Bug 2)
  - `packages/happy-app/sources/-session/SessionView.tsx` — `useComposerSend` lines 438-448 (Bug 2)
  - `packages/happy-app/sources/text/translations/en.ts` and all 8 other language files (Bug 2 — new translation keys)
- **Import `Modal` from `@/modal`** — already used in `MarkdownView.tsx`, `SettingsView.tsx`, etc. Same pattern.
- **Do NOT import `Modal` in `useAttachments.ts`** — hooks should not import UI-layer alert utilities; the silent-return replacement should either (a) throw a typed error that the caller catches and shows the modal, or (b) return a discriminated result. Best pattern in this codebase: throw `new HappyError(t('session.attachmentTooLarge'))` — `useHappyAction` wraps in a `Modal.alert` automatically. But `pickImage`/`pickDocument`/`addFileFromPaste` are not currently wrapped in `useHappyAction`. Simpler: move the modal call into the calling site in `AgentInput.tsx` or `SessionView.tsx`, and have `useAttachments` expose a callback `onAttachmentRejected?: (reason: string) => void`. Dev may choose either approach as long as a modal appears and the chip is not silently discarded.
- **`useComposerSend` change**: the check `if (msg.trim() || att.hasAttachments)` must be supplemented with a guard for error-state items. Approach: add `att.hasErrorAttachments` to the return value of `useAttachments` (`attachments.some(a => a.status === 'error')`), and check it before dispatching.
- **Translation key path**: `session.attachmentTooLarge` and `session.attachmentUploadFailed`. Both are simple string constants (no parameters needed for the minimal implementation).
