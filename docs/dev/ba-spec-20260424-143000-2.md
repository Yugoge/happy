# BA Specification: CronList Inline Card Simplification (§5.18)

**Request ID**: dev-20260424-143000-2
**Created**: 2026-04-24T14:30:00Z

## Goal

Simplify the CronList tool's inline conversation card to show only a compact summary line (header + icon + input args), and move the full INPUT/OUTPUT verbose rendering exclusively to the right-side sidebar detail panel.

## Context

The CronList tool currently has no entry in `knownTools.tsx` and no view in `toolViewRegistry`. This means the default `ToolContent` renderer in `ToolView.tsx` (lines 301-316) fires for it, rendering full `INPUT` + `OUTPUT` code blocks directly in the conversation. This is the "rendering很烂" state the user reports. The fix follows the Bash/subagent compact-inline pattern already established in the codebase.

- **browser**: Chrome desktop (primary), mobile viewport also applies
- **url_path**: `/session/<sessionId>` (conversation view)

## Requirements (MoSCoW)

### Must Have

- Register `CronList` in `knownTools.tsx` with: `minimal: true`, `icon` (clock or wrench — Ionicons `timer-outline` or `construct-outline`), `title: 'CronList'` (or via i18n), `extractDescription` returning a compact stringification of the input args (e.g., `CronList {}` or `CronList (N jobs)` when N > 0).
- The inline CronList card MUST render only the header row (icon + title + optional one-line description). NO body sections (no INPUT block, no OUTPUT block) in the conversation.
- The sidebar detail panel for CronList MUST continue to show full INPUT + OUTPUT via the existing `SidebarGenericView` fallback (no code change needed in `SidebarContentRenderer.tsx`).
- Add translation key `tools.names.cronList` (e.g. `'CronList'`) and `tools.desc.cronListJobs` (e.g. `({ count }) => \`${count} scheduled jobs\``) to ALL 9 language files (`en`, `ru`, `pl`, `es`, `ca`, `it`, `pt`, `ja`, `zh-Hans`).

### Should Have

- `extractDescription` for CronList shows the number of scheduled jobs when the result is available and parseable (e.g., `0 scheduled jobs` for `No scheduled jobs.`, `N scheduled jobs` when N > 0).
- Description fallback for running state: `CronList {}` (raw input JSON if empty, else truncated arg summary).

### Could Have

- Dedicated icon using `Ionicons name="timer-outline"` (clock) to differentiate from the generic wrench.

### Won't Have (Non-Goals)

- Creating a new `CronListView.tsx` inline component — the `minimal: true` flag in `knownTools` plus the existing default rendering path is sufficient.
- Creating a new `SidebarCronListView.tsx` — `SidebarGenericView` is already correct for this.
- Modifying `SidebarContentRenderer.tsx` — the existing `default` branch already routes unknown tools to `SidebarGenericView`.
- Any changes to `ToolView.tsx`, `ToolFullView.tsx`, `_all.tsx`, or `SidebarContentRenderer.tsx`.

## Edge Cases & Risks

- CronList input may be `{}` (empty object) — `extractDescription` must handle this gracefully (show `CronList {}` or `No arguments`).
- CronList result is a plain string `"No scheduled jobs."` (not a structured object) — `SidebarGenericView` handles string results correctly at line 26.
- i18n: 9 language files must all receive the new keys. Missing any file causes a TypeScript error.
- The `satisfies Record<string, ...>` constraint on `knownTools` means the new entry must satisfy the same interface. `icon` is a required field — must not be omitted.

## Acceptance Criteria

### AC1: Inline card is compact
- GIVEN a conversation contains a CronList tool call (e.g., result `No scheduled jobs.`)
- WHEN the user views the conversation
- THEN the CronList card shows only the header row: wrench/timer icon + "CronList" label + one summary line (e.g., `CronList {}`) with NO INPUT or OUTPUT sections below the header

### AC2: Sidebar shows full detail
- GIVEN a CronList inline card is visible in the conversation
- WHEN the user taps/clicks the card to open the right-side sidebar
- THEN the sidebar shows the full INPUT section (e.g., `{}`) AND the OUTPUT section (e.g., `No scheduled jobs.`) via the existing generic view

### AC3: No regression on Bash compact pattern
- GIVEN the codebase before and after this change
- WHEN a Bash tool call appears in the conversation
- THEN the Bash card still renders in its existing compact form (no regression from the `knownTools` change)
