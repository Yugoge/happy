# Production/Dev Isolation Audit

**Date**: 2026-04-04
**Trigger**: Catastrophic incident -- `npm install -g` from dev worktree killed all production sessions
**Scope**: All possible cross-contamination vectors between happy (production) and happy-dev

---

## Vector 1: Shared Global Binary

**STATUS: RISK (CRITICAL) -- Partially mitigated**

### Finding

All three daemons (default, jade, dev) use the **same global binary**:

```
ExecStart=/usr/bin/happy daemon start
```

`/usr/bin/happy` -> `/usr/lib/node_modules/happy-coder/bin/happy.mjs`
`/usr/lib/node_modules/happy-coder` -> `/root/happy/packages/happy-cli` (symlink)

This is the exact vector that caused the 2026-04-04 incident. The `npm install -g` hook now blocks this from Claude agents, but:

- **Residual risk 1**: The dev daemon systemd service (`happy-daemon-dev.service`) still uses `ExecStart=/usr/bin/happy daemon start`. If a dev agent modifies `/root/happy/packages/happy-cli/` source and triggers a build, the compiled output changes for ALL daemons simultaneously.
- **Residual risk 2**: Auto-upgrade in the daemon checks version mismatch between the binary on disk vs the compiled-in version. If any agent rebuilds happy-cli (even `yarn build` in `/root/happy`), all three daemons detect mismatch and attempt upgrade cascade.
- **Residual risk 3**: The user can still run `npm install -g` manually, but that is intentional and acceptable.

### Mitigation status

- Hook blocks `npm install -g` from agents: **YES** (pretool-bash-safety.sh)
- Hook blocks invoking `/usr/bin/happy` or `happy daemon`: **YES** (pretool-bash-safety.sh)
- Dev daemon uses its own binary copy: **NO** -- still shared

### Recommended fix

Change `happy-daemon-dev.service` to use a dedicated binary:
```
ExecStart=/usr/bin/node /dev/shm/dev-workspace/happy-dev/packages/happy-cli/dist/index.mjs daemon start
```
This completely decouples the dev daemon from the production binary. A rebuild in happy-dev only affects the dev daemon.

**Severity**: CRITICAL (incident already occurred)
**Current protection**: Hook-level only (blocks agent actions, not system-level decoupling)

## Vector 2: Shared Docker Network

**STATUS: RISK (HIGH)**

### Finding

Both `happy-server` (production) and `happy-server-dev` are on the **same Docker network**: `happy-server_happy-network`.

Verified:
```
PROD networks: ['happy-server_happy-network']
DEV networks:  ['happy-server_happy-network']
```

The dev server container can resolve and reach the production database:
```
$ docker exec happy-server-dev getent hosts happy-postgres
172.19.0.9      happy-postgres
```

This means:
- **Risk 1**: A misconfigured `DATABASE_URL` in dev could point to the prod database (`happy-postgres:5432/happydb`). Currently the env var correctly points to `postgres-dev:5432/happydb_dev`, but a single typo or env override would route dev writes to production data.
- **Risk 2**: Dev code bugs that scan the Docker network could discover and interact with production services.
- **Risk 3**: Dev MinIO connects to the **same MinIO instance** (`minio:9000`) -- only separated by bucket name (`happy-storage` vs `happy-storage-dev`). A bucket name typo would read/write production file storage.

### Recommended fix

Create a separate Docker network for dev services:
```yaml
networks:
  happy-network:
    driver: bridge
  happy-dev-network:
    driver: bridge
```
Put `happy-server-dev`, `postgres-dev`, `redis-dev` on `happy-dev-network` only. Share MinIO on both networks (or create a second MinIO). This prevents DNS resolution of `happy-postgres` from dev containers entirely.

**Severity**: HIGH (one env var typo = production data corruption)

## Vector 3: Shared MinIO Instance

**STATUS: RISK (MEDIUM)**

### Finding

Both prod and dev servers use the same MinIO container (`happy-minio:9000`) with the same credentials (`yugeyuge` / `yuge1210yuge`). Isolation is **only by bucket name**:
- Production: `S3_BUCKET: happy-storage`
- Dev: `S3_BUCKET: happy-storage-dev`

No bucket-level access control is configured in MinIO. The dev server has full access to the production bucket.

### Recommended fix

Either:
1. Create a separate MinIO instance for dev, or
2. Configure MinIO IAM policies to restrict the dev service account to only `happy-storage-dev`

**Severity**: MEDIUM (requires code bug or env misconfiguration to trigger)

## Vector 4: Shared Signing Secret (HANDY_MASTER_SECRET)

**STATUS: RISK (MEDIUM)**

### Finding

Both prod and dev servers use the **identical** `HANDY_MASTER_SECRET`:
```
adocKlifsn8A09BTADtSPpb+F0F6Z9atZC5GciycNt0=
```

This means tokens generated by the dev server are valid on the production server and vice versa. Combined with the same account ID (`cmi5mv9eh00wzpg14ph73jj3n`) used by both default daemon and dev daemon, a dev-generated token could authenticate against production.

### Recommended fix

Use a different `HANDY_MASTER_SECRET` for the dev server. This ensures tokens are not cross-valid. However, this would mean the dev account's existing token (in `/root/.happy-dev/access.key`) would need regeneration with the new secret.

**Severity**: MEDIUM (tokens are cross-valid, but dev daemon already points to localhost:3005 not prod)

## Vector 5: Same Account for Default and Dev Daemons

**STATUS: RISK (MEDIUM)**

### Finding

Default daemon and dev daemon use the **same account**: `cmi5mv9eh00wzpg14ph73jj3n`

```
PROD account: cmi5mv9eh00wzpg14ph73jj3n
DEV  account: cmi5mv9eh00wzpg14ph73jj3n
JADE account: cmmu4tj8f4gi5nv14xz4nr6ud (different)
```

Same encryption `publicKey` on both. This means:
- Sessions created by dev daemon appear in the same account's session list
- Machine registrations could conflict (same account, same publicKey, potentially same machine name)
- If the dev daemon's `HAPPY_SERVER_URL` were accidentally changed to the prod URL, it would create sessions, machines, and messages in the production database under the same account

### Current protection

Dev daemon points to `http://localhost:3005` (dev server), not the prod server. This is the primary isolation mechanism.

### Recommended fix

Ideally, create a separate account for the dev daemon. Short-term, the current URL-based isolation is acceptable but fragile.

**Severity**: MEDIUM (single env var change = production contamination)

## Vector 6: Session Recovery Watcher Cross-Home Interaction

**STATUS: RISK (MEDIUM)**

### Finding

The `happy-session-recovery.sh` script operates on ALL three homes simultaneously:
```bash
HAPPY_HOMES=("/root/.happy" "/root/.happy-jade" "/root/.happy-dev")
```

Key interactions:
1. **`save` (ExecStartPre)**: When the dev daemon restarts, `ExecStartPre` runs `save` which scans processes for ALL homes. If production sessions happen to be in a transient state during a dev daemon restart, the scan could produce an inaccurate snapshot for prod homes.
2. **`restore`**: The restore function iterates all homes and uses `globally_spawned` cross-home dedup. If a UUID somehow appears in both prod and dev `session_dirs.txt`, the first home to spawn it "wins" and the other home skips it. Since prod and dev share the same account, this is theoretically possible.
3. **Peak protection**: A dev session count drop could affect the peak protection window calculation that is global across homes.

### Current protection

- `write_snapshot` is per-home (each home gets its own `session_dirs.txt`)
- Restore iterates homes independently but deduplicates by UUID

### Recommended fix

Add `HAPPY_HOME_DIR` filtering to `ExecStartPre` in each daemon service so each daemon only saves/restores its own home:
```
ExecStartPre=/bin/bash -c 'HAPPY_HOMES_OVERRIDE=/root/.happy-dev /root/bin/happy-session-recovery.sh save || true'
```

**Severity**: MEDIUM (theoretical race condition during concurrent daemon restarts)

## Vector 7: Edit/Write Tool Access to Production Files

**STATUS: RISK (HIGH)**

### Finding

The `pretool-bash-safety.sh` hook only applies to the **Bash** tool. It blocks `npm install -g`, `kill`, etc. But there is **NO hook blocking Write/Edit tools from modifying files in `/root/happy/`**.

The `pretool-overnight-hook-guard.py` only activates during overnight sessions with a worktree. During regular dev sessions (non-overnight), there is NO file path restriction on Write/Edit.

A dev agent could:
1. Use `Edit` to modify `/root/happy/packages/happy-cli/src/daemon/run.ts` (production source)
2. The next time the production daemon rebuilds or restarts, it picks up the corrupted code
3. Use `Write` to overwrite `/root/.happy/access.key` or `/root/.happy/session_dirs.txt`

The `pretool-bash-safety.sh` blocks `rsync/cp` from external paths to `/root/happy/packages/`, but the Edit/Write tools completely bypass this protection.

### Recommended fix

Add a PreToolUse hook for `Write|Edit` that blocks file paths under:
- `/root/happy/` (production source)
- `/root/.happy/` (production daemon home)
- `/root/.happy-jade/` (jade daemon home)
- `/usr/lib/node_modules/happy*`
- `/usr/bin/happy*`

Example hook (add to settings.json with matcher `Write|Edit`):
```bash
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | python3 -c "import json,sys; d=json.load(sys.stdin); print(d.get('tool_input',{}).get('file_path',''))" 2>/dev/null)
case "$FILE_PATH" in
  /root/happy/*|/root/.happy/*|/root/.happy-jade/*|/usr/lib/node_modules/happy*|/usr/bin/happy*)
    echo "BLOCKED: Write/Edit to production path is forbidden from dev environment" >&2
    echo "Path: $FILE_PATH" >&2
    exit 2 ;;
esac
exit 0
```

**Severity**: HIGH (completely unprotected vector, could corrupt production source or daemon state)

## Vector 8: Git Remote Cross-Contamination

**STATUS: SAFE (with caveat)**

### Finding

Both `/root/happy` and `/dev/shm/dev-workspace/happy-dev` share the same git remotes:
```
fork    git@github.com:Yugoge/happy.git
origin  git@github.com:slopus/happy.git
```

A `git push` from happy-dev pushes to the same remote branches as production. However:
- Production (`/root/happy`) is on a specific branch/commit and does not auto-pull
- Git push from dev to `origin` or `fork` only affects the remote, not the local `/root/happy` checkout
- No hook blocks `git push --force` from dev to remote (only warns)

### Caveat

If a dev agent force-pushes to `main` on the remote, then someone pulls from that remote into `/root/happy`, the production source would be contaminated. But this requires two steps and the hook warns on force push.

**Severity**: LOW (requires multi-step human error)

## Vector 9: Process/Cgroup Isolation

**STATUS: SAFE**

### Finding

Each daemon runs under its own systemd service with separate cgroup:
- `happy-daemon.service` (MemoryMax=20G)
- `happy-daemon-jade.service` (MemoryMax=16G)
- `happy-daemon-dev.service` (MemoryMax=2G)

Child processes (sessions) are spawned via `systemd-run` which places them in the correct cgroup. Process isolation is handled by systemd.

The hook blocks `kill` with PIDs and `kill -9`, preventing accidental cross-cgroup kills.

**Severity**: LOW (properly isolated by systemd)

## Vector 10: Environment Variable Leaks

**STATUS: SAFE**

### Finding

The dev daemon has proper environment isolation:
```
Environment=HAPPY_HOME_DIR=/root/.happy-dev
Environment=HAPPY_SERVER_URL=http://localhost:3005
```

Production daemons use `HAPPY_SERVER_URL=http://188.245.32.161:3000`. The dev daemon uses `localhost:3005`. These are set in systemd unit files and not overridable by agents.

The session watcher service has no `HAPPY_HOME_DIR` set (operates on all homes by design).

**Severity**: LOW (properly isolated at systemd level)

## Vector 11: Playwright/Browser Production Access

**STATUS: RISK (MEDIUM) -- Partially mitigated**

### Finding

The `pretool-block-production.sh` hook file does **NOT EXIST**:
```
ls: cannot access '/root/.claude/hooks/pretool-block-production.sh': No such file or directory
```

Despite being referenced in CLAUDE.md as "enforced by `pretool-block-production.sh` hook", this hook is missing. The Playwright production URL blocking is only enforced by:
1. CLAUDE.md instructions (soft enforcement, can be ignored by subagents)
2. The `pretool-bash-safety.sh` hook does not check URLs in Playwright MCP tool calls

A subagent could navigate Playwright to `https://life-ai.app` or `http://localhost:8090` (production web) without any hook blocking it.

### Recommended fix

Create the missing `pretool-block-production.sh` hook and register it in `settings.json` for the Playwright MCP tools (browser_navigate, etc.). It should block:
- `life-ai.app` (without `dev.` prefix)
- `localhost:8090`
- `localhost:3000`
- `api.life-ai.app` (without `api-dev.` prefix)

**Severity**: MEDIUM (missing promised hook; incidents already occurred today)

## Vector 12: docker-compose.yml Build Context Points to Production

**STATUS: RISK (LOW)**

### Finding

The `docker-compose.yml` for `happy-server-dev` has:
```yaml
happy-server-dev:
  build:
    context: /root/happy
    dockerfile: Dockerfile.server-slim
```

If someone runs `docker compose build happy-server-dev` from `/root/deploy/`, it builds from `/root/happy` (production source), NOT from `/dev/shm/dev-workspace/happy-dev`. This is documented in CLAUDE.md as a known issue with the workaround of using `docker build` directly.

### Current protection

The hook allows `docker compose build happy-server-dev` (it is in the dev whitelist). This means agents CAN run this command, which builds from production source -- potentially deploying production code to the dev server. This is not dangerous per se (production code on dev is OK), but it defeats the purpose of dev testing if the dev server runs production code.

**Severity**: LOW (wrong direction: prod code -> dev, not dev code -> prod)
